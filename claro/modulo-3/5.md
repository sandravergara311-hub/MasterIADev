# Módulo 3 · Lección 5 — Que el agente lea la spec, y cuándo no usar OpenSpec

Texto original: `original/modulo-3/5.md`  
Obligatoria.

## En una frase

Tener un change no garantiza que el agente lo respete. Hay tres formas de conectarlo, de menos control a más. Y hay cambios para los que OpenSpec sobra.

## Palabras que vas a escuchar

- **TDD rojo / verde.** Primero escribes una prueba que falla. Eso es el rojo. Después, el código mínimo que la hace pasar. Eso es el verde. La prueba define el objetivo antes de que exista la solución.
- **Spike.** Un trabajo corto para responder una pregunta. "¿Esto se puede hacer con esta librería?" No es para dejar código que se quede.
- **Pull request.** La propuesta de integrar un conjunto de cambios. Otra persona la revisa antes de que entren. Es el lugar clásico de la discusión. Por eso importa discutir antes.
- **Invariante.** Una condición que tiene que cumplirse siempre, sin excepciones. "Nunca se sube una credencial al repositorio" es una.
- **Gobernanza.** Quién decide qué, y cómo se controla. Aquí, aplicada a tu configuración: quién puede cambiarla, cómo se revisa, y qué te pasa cuando la herramienta de abajo cambia.

## Caso real: la fecha prometida, otra vez

Elena ya tiene el change de la fecha prometida en el Taller Rueda. Si abre un chat nuevo y dice "implementa la fecha", el agente puede inventar una columna que el `design.md` prohibía.

El change está en disco. Falta hacer que lo lea.

## Tres patrones, de menos control a más

**Patrón A. Referencia explícita en el primer turno.** Es el más usado.

```text
Implementa el change openspec/changes/add-task-due-date/.
Lee primero proposal.md, specs/*.md, design.md y tasks.md.
Sigue tasks.md paso a paso. Pregúntame antes de desviarte
de cualquier requisito de specs/.
```

A favor: cero preparación. Funciona en cualquier herramienta. En contra: tienes que acordarte de la coletilla. Si abres una sesión nueva y se te olvida, el agente puede improvisar.

Con el perfil `core`, `/opsx:apply` ya hace esto por ti. El patrón A sirve cuando trabajas el change a mano.

**Patrón B. Una skill.**

Lo conviertes en un archivo de instrucciones versionado en el repo. El agente lo carga cuando la tarea encaja. Por ejemplo, `.claude/skills/openspec-implement/SKILL.md`.

Le dice: leer los cuatro archivos en orden, implementar tarea por tarea marcando la checklist, detenerse y preguntar ante cualquier desvío de `specs/`, y correr las pruebas al final.

A favor: el flujo es explícito, se puede repetir y se puede auditar. En contra: hay que mantener la skill cuando OpenSpec cambia.

Qué parte de `openspec/` es de solo lectura. `proposal.md`, `design.md` y `specs/` son entrada. El agente los lee y no los toca. `tasks.md` es la excepción. Es la checklist viva. Conforme avanza, el agente cambia `- [ ]` por `- [x]`. No es permiso para reescribir el change. Es el único archivo donde escribir forma parte del trabajo.

**Patrón C. Skill más un hook que valida.**

Agregas un hook Stop. Corre las pruebas que salen de los escenarios. Si fallan, el agente recibe el error y entra a corregir.

A favor: el agente no cierra el turno con las pruebas en rojo sin que te enteres. En contra: hace falta infraestructura de validación. Y el bloqueo no es infinito. Claude Code ignora el hook y cierra el turno después de 8 bloqueos seguidos. Es para que un check mal escrito no deje al agente girando en vacío. Es un tope de seguridad, no un fallo. Significa que un hook que nunca puede pasar termina cediendo. Es para flujos de producción.

Empieza con A, o directo con `/opsx:apply`. Cuando notes que copias la misma coletilla tres veces, pasa a B. C llega cuando el proyecto ya tiene validación automática y quieres que el agente entre en ella.

`/opsx:verify` cae entre B y C. No lo confundas con C. Verify es el agente releyendo tu código y opinando. Puede callarse. El hook de C corre las pruebas y falla. La misma intención, otra garantía. Uno interpreta. El otro se ejecuta. Si de verdad te importa que algo se cumpla, necesitas C aunque tengas verify. Y verify no viene en el perfil `core`. Ese perfil instala seis comandos: propose, explore, apply, update, sync y archive. Para tener verify hay que ampliar el perfil con `openspec config`.

## Cuando OpenSpec sobra, escribe el README antes

El nombre lo puso Tom Preston-Werner, cofundador de GitHub, en 2010. Sigue vivo. Simon Willison armó una herramienta entera así. Primero el README con detalle. Después se lo pasó a Claude Code para que lo implementara con TDD rojo / verde.

La receta: escribe el README o la spec antes de pedir la implementación, con todo el detalle que puedas, incluidos los casos límite. Después pide implementar con TDD rojo / verde a partir de eso.

Es spec-first informal. Sirve para cualquier tamaño. Un script de 50 líneas, no solo un change formal. Útil justo cuando OpenSpec sobra.

No es la misma burocracia con otro nombre. El destinatario cambia. Un change formal produce artefactos que se archivan, se auditan y le sirven a alguien dentro de seis meses. Un README escrito antes solo tiene que servirle a quien implementa a continuación. Puede ser un agente, o puedes ser tú dentro de una hora. Se borra sin ceremonia. No deja un rastro que mantener.

## Cuándo no usar OpenSpec

No lo uses para:

- Cambios acotados. Agregar un filtro por estado a un listado que ya existe. Ajustar un valor por defecto. Meter un log. Eso es delegación directa.
- Bugs donde el cambio es obvio.
- Spikes y prototipos que se van a tirar. Si vas a tirar el código, escribir su spec es desperdicio. Prototipos, scripts de un solo uso y spikes de menos de dos horas no pagan una spec.

El costo de un change (preparación, más los minutos de proponer, revisar y archivar) solo se paga cuando el cambio perdura, toca varias capas o necesita rastro. Para lo demás, camino directo o README primero. Saber elegir es la habilidad. Usar OpenSpec no lo es.

En el taller, el filtro del martes no paga un change. La regla de la orden atrasada, sí.

## Tu flujo se puede llevar

Las herramientas cambian. Planes, precios, versiones con bugs. Lo que está versionado en tu repo es tuyo y se mueve contigo.

`AGENTS.md`, `CLAUDE.md`, `.claude/skills/`, `.claude/agents/`, los hooks y `openspec/`.

Trata esos archivos como código. Van en un pull request. Se revisan. Los hooks, siempre. Ejecutan código en las computadoras del equipo.

Los comandos `/opsx:*` que OpenSpec genera también son archivos del repo, en `.claude/commands/` y `.claude/skills/`. Se clonan con él. Tu compañero los tiene sin instalar nada. Lo único que se queda en tu computadora es la configuración global. Solo decide el perfil por defecto de los proyectos nuevos.

Lo que vive en `AGENTS.md` lo interpreta el modelo. Lo que vive en un hook lo ejecuta el código. Para invariantes de seguridad, siempre hooks.

Tu seguridad no está en el plan que pagas. Está en que tu flujo se pueda llevar. Un `openspec/` versionado y un harness en `.claude/` valen más que cualquier prompt cuando la herramienta tiene un mal día.

## lidr-specboot

El curso mantiene `lidr-specboot`. Es una capa de convenciones sobre OpenSpec.

El paso verificado es `/enrich-us`. Enriquece historias. Confirma que LIDR pone una capa de "historias primero" encima de OpenSpec.

Por encima, specboot orquesta el resto: enriquecer, proponer, aplicar, verificar, revisar, archivar y hacer commit. Por debajo se apoya en los comandos reales: `/opsx:propose`, `/opsx:apply`, `/opsx:archive`.

Entre el apply y el archive, specboot mete verificación y revisión adversarial propias. No da la implementación por buena solo porque las tareas estén marcadas.

No te ocupes de specboot ahora. Basta saber que existe y que por debajo es OpenSpec.

## Preguntas frecuentes

**Si esta herramienta desaparece mañana, ¿qué me queda?**

Sobrevive lo que es texto plano versionado en tu repositorio. Las specs, las instrucciones, las skills y los hooks. Y sobre todo el vocabulario: escribir el contrato antes que el código no es propiedad de nadie. No sobrevive la configuración global de tu computadora ni la memoria de unos comandos concretos. La atadura de verdad no es la herramienta. Es un flujo que solo existe en la cabeza de una persona.

**Si el patrón C es el único que garantiza algo, ¿por qué no empezar ahí?**

Porque un validador se escribe contra criterios que todavía no tienes. Hasta que no has hecho el ciclo a mano un par de veces, no sabes qué querías comprobar. Terminas con un check que falla por motivos que no entiendes. La escala A, B, C no mide tu nivel. Cada escalón se paga cuando el anterior empieza a doler. Antes de eso es costo sin contrapartida.

## Qué hacer

- Asegura que el agente lea la spec. A, o `/opsx:apply`, para empezar. Skill cuando se repita. Hook que valida, para producción.
- README primero cuando OpenSpec sobra, pero igual quieres escribir el contrato antes.
- No uses OpenSpec para lo acotado o desechable.
- Versiona `openspec/` y `.claude/`. Los hooks se revisan siempre.
- `lidr-specboot` es OpenSpec más orquestación. Agrega verificación y revisión entre el apply y el archive.

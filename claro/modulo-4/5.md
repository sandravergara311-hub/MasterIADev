Obligatoria.

## En una frase

La documentación viva no es mantener papeles a mano. Tres artefactos salen de lo que ya existe. El cuarto registra un porqué que no está en ningún otro sitio.

## Palabras que vas a escuchar

- **OpenAPI.** Antes se llamaba Swagger. Es un formato estándar para describir una API: qué rutas tiene, qué recibe cada una y qué devuelve. Es un archivo, no una web. Desde ese archivo se puede generar la documentación navegable y los clientes que la consumen.
- **Structurizr.** Describes la arquitectura una sola vez, en texto, y la herramienta genera todas las vistas. Sirve cuando necesitas varias vistas coordinadas del mismo modelo, no diagramas sueltos.
- **Docs-as-code.** Tratar la documentación igual que el código. Vive en el repositorio, se revisa en el mismo pull request y se regenera sola. No es una herramienta. Es una decisión sobre dónde vive y quién la revisa.
- **GitHub Pages.** El alojamiento de GitHub que convierte una carpeta de documentación en un sitio con dirección propia. Es gratis en repositorios públicos. En privados pide un plan de pago (Pro, Team o Enterprise). Es el caso de la mayoría de los repos de empresa.
- **Spec viva.** El documento del repo que describe cómo debe comportarse cada parte del sistema, en escenarios. Se actualiza en el mismo cambio que el código.
- **CI.** El servicio que, cada vez que subes un cambio, lanza solo un conjunto de tareas. Pruebas, linters y, aquí, también regenerar y publicar la documentación.
- **Harness.** La configuración con la que armas al copiloto para un proyecto: qué lee, qué herramientas puede usar y qué reglas sigue.
- **Delta-spec.** En lugar de reescribir la especificación entera, describes solo lo que cambia con este trabajo. Al aplicarla, esos cambios entran a la spec viva y queda el registro de qué se modificó y cuándo.

Estos cuatro no cubren todo. Se reparten la arquitectura, el contrato de la API y el código. La documentación de operación (qué hacer cuando algo se cae, guardias, cómo se despliega) y el comentario de cada función (el TSDoc) juegan con otras reglas. Las escribe quien está de guardia. Se prueban cuando algo se rompe de madrugada. No se generan de nada. No entran en estos cuatro, y no es un olvido.

Si programas, los cuatro te afectan. El que más tiempo puede ahorrarte es el contrato de la API, porque deja de depender de que alguien lo mantenga a mano.

Si vienes de producto, presta atención al ADR. Es el único que no puede salir del código. Registra por qué se tomó una decisión. Ese contexto solo existe si alguien lo deja escrito. Es el que más se extraña cuando falta. Llega el día en que alguien pregunta por qué el sistema hace algo de una forma, y la única respuesta es "nadie se acuerda".

Si no programas, quédate con una idea. Tres de estos documentos se generan. Uno se decide.

## Caso real: por qué un préstamo devuelto no está atrasado

En la Biblioteca del Barrio, Sofía ya tiene el código del filtro y de la fecha de devolución. Don Ramiro pregunta por qué un libro devuelto, con la fecha vencida, no sale como atrasado. El código calcula el campo. No dice por qué se eligió calcularlo al leer, en lugar de guardarlo.

Tres documentos pueden salir del código: el diagrama del sistema, el contrato de la API y el README del módulo. El cuarto, el ADR, lo escribe Sofía a partir de la decisión que el equipo ya tomó. Si le pide al agente que invente el porqué, va a sonar convincente y nadie lo decidió.

## 1. Arquitectura: C4 y Mermaid

Mermaid es texto en un bloque de código. GitHub y GitLab lo dibujan como diagrama. C4, de Simon Brown, organiza la arquitectura en cuatro niveles. De ahí el nombre: Contexto, Contenedor, Componente y Código. El cuarto casi nunca se dibuja, porque a ese nivel el código ya es el diagrama. El resultado vive en el repo, se ve en el diff y se mantiene al día junto con el código.

Se genera leyendo la estructura del proyecto:

```text
Analiza la estructura de este proyecto (controladores, modelos, capa de datos,
frontend) y genera un diagrama de contenedores estilo C4 en Mermaid.
Guárdalo en la carpeta de documentación del proyecto.
```

En una aplicación con API en AdonisJS y frontend en React, nadie lo dibujó. Salió de leer el código.

Usa Mermaid cuando el diagrama es suelto, vive en un README o en un ADR, y no necesita vistas coordinadas. Usa Structurizr cuando sí necesitas varias vistas del mismo modelo a la vez, o cuando la arquitectura es un entregable formal. Con una sola vista, Mermaid en el README alcanza.

## 2. ADR: la memoria del porqué

Un Architecture Decision Record registra una decisión técnica importante. Contexto, opciones consideradas y por qué se eligió una. Captura lo único que el código nunca te cuenta.

Criterio práctico de cuándo escribir uno. Si una persona nueva viera este código, ¿se preguntaría "por qué lo hicieron así"? Si sí, hay un ADR pendiente.

El formato original es el de Nygard. Cinco apartados: título, contexto, decisión, estado y consecuencias. El estado evita que un ADR se edite. Cuando la decisión cambia, se marca como reemplazado y se escribe otro. Una variante muy usada es MADR. Agrega "opciones consideradas", con pros y contras. Es más útil cuando lo llena un agente. Usa el que adopte tu equipo. El curso trabaja con el de Nygard.

El flujo útil no es escribir el ADR. Es pasar a ese formato una decisión que ya tomaste. Si está en un hilo o en la descripción de un pull request, pégala.

```text
Mi equipo ha decidido usar las delta-specs (la descripción de lo que cambia en el
comportamiento del sistema, en vez de reescribir la spec entera) como fuente de
verdad viva del proyecto. Genera el ADR que registra esa decisión: contexto, las
alternativas que se consideraron y por qué se eligió esta. Guárdalo junto a las
demás decisiones de arquitectura.
```

El agente no se lo inventa. Lo redacta desde las decisiones que ya tomaste y que están escritas en el repo, en el hilo o en el pull request. El ADR lo revisas tú. La IA redacta el registro. La decisión y su validez son humanas.

## 3. API: OpenAPI desde el código

El contrato de la API sale del código. No de un documento que alguien tenga que mantener a mano.

Con un generador de OpenAPI instalado, en AdonisJS por ejemplo un paquete de la comunidad y no del núcleo, como `@foadonis/openapi`, solo necesitas configurarlo y registrar su ruta. A partir de ahí, el spec se construye desde las rutas y los controladores reales. Qué endpoints existen, qué parámetros reciben y qué respuestas devuelven.

Antes de comprometerte con un generador, mira si declara tu versión. Un paquete que no dice con qué versiones del framework funciona no te va a avisar cuando deje de hacerlo. Simplemente va a generar algo incompleto, o va a dejar de generar. En npm eso se lee en sus peer dependencies. Un paquete con esa lista vacía no es más compatible. Es menos honesto. Míralo también en la fecha del último commit.

Sobre la API de tareas del curso, el spec muestra el listado con su filtro por estado, que rechaza con un error de validación un estado que no existe, y el campo calculado que marca una tarea como vencida solo si su fecha pasó y no está terminada. Cada uno con su tipo, sus valores admitidos y sus respuestas, tal como el código los expone hoy. Si el código cambia, regeneras y el contrato se actualiza. Un frontend, un cliente de celular o un partner lo consume sin preguntarte.

Puedes pedirle al harness que contraste el OpenAPI generado con los escenarios de `openspec/specs/`. ¿Algún endpoint documentado se desvía de la spec? La documentación no solo describe. Verifica. Code-first y design-first son válidos los dos. Hoy se hace code-first porque ya hay código. El patrón de tratar la doc como código es el mismo.

## 4. README por módulo

Qué hace cada módulo y cómo se usa, generado desde su código:

```text
Genera un README para el módulo de tareas: propósito, endpoints, cómo correrlo
y probarlo. Guárdalo junto al código de ese módulo.
```

## Publicar sin que alguien se acuerde

Los cuatro artefactos viven dentro del repo, junto al código que describen, y se confirman con la función, en el mismo pull request. Y se publican solos.

Un sitio de docs, MkDocs o Docusaurus, da igual para empezar, construye un sitio estático. Un job de CI regenera y publica en GitHub Pages en cada push.

Nadie tiene que acordarse de actualizar la doc. El pipeline lo hace, igual que un hook de formato deja el código ordenado sin que se lo pidas. Son rieles, no buena voluntad.

## Preguntas frecuentes

**¿Tengo que armar los cuatro para empezar?**

No. Intentar armar los cuatro de golpe es una buena manera de terminar sin ninguno. El orden depende de qué necesitas responder. Si la pregunta es cómo se consume la API, empieza por el contrato generado. Si la pregunta es por qué el sistema hace algo de una forma, empieza por el ADR. El diagrama es el que más impresiona a primera vista, y también el que menos suele urgir al principio.

**Cuatro documentos vivos suenan a cuatro cosas más que mantener.**

Solo una lo es. Tres se regeneran. El diagrama, el contrato de la API y el README salen del código cada vez. Mantenerlos al día es un comando en CI, no trabajo manual. El ADR es el único que alguien escribe a mano. Aun así no se mantiene en el sentido habitual. Cuando la decisión cambia, no se edita el ADR anterior. Se escribe uno nuevo y el anterior queda marcado como reemplazado. Así el porqué queda fechado.

**¿Y si el diagrama o el contrato que genera están mal?**

Pueden estarlo. La diferencia con una doc escrita a mano es esta. Como estos tres salen del código, el error se reproduce en cuanto regeneras. O lo arreglas en el código, o lo arreglas en la spec. No hay un tercer lugar donde pueda quedar sin corregir. Un documento manual equivocado se queda equivocado hasta que alguien lo lee con atención, y eso casi nunca pasa.

## Qué hacer

- Mermaid y C4: el diagrama es texto, nace del código y se actualiza con él. Structurizr solo si necesitas varias vistas.
- ADR: transcribe la decisión que ya tomaste. El porqué lo pones, y lo revisas, tú.
- OpenAPI desde el código. El contrato no depende de un documento a mano. Se puede contrastar contra la spec.
- README por módulo: qué hace y cómo se usa, generado desde el código de ese módulo.
- Los cuatro viven en el repo, se revisan en el pull request, y CI regenera y publica lo que se genera. La spec viva es el ancla que los mantiene honestos.

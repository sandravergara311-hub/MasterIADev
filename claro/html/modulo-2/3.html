Módulo 2 · Lección 3 — Cada documento responde una sola pregunta

Texto original: original/modulo-2/3.md
Obligatoria.

En una frase

PRD, épica, historia, ticket y spec no son sinónimos. Cada uno es un nivel de zoom. Mezclarlos es la causa más común de especificaciones que no sirven.

Caso real: el PRD que hablaba de tablas

Luis, en Inmobiliaria Calle, escribe un "PRD" de doce páginas. En la página 2 ya están POST /reportes, la tabla tickets y el nombre de la clase. En la página 9 todavía se discute si el usuario es el inquilino o también el dueño.

El agente, al programar, trata las dos discusiones como órdenes. Crea la tabla y, de paso, un rol de dueño que nadie había decidido. El documento no tenía un nivel. Tenía todos al mismo tiempo.

La regla es esta: cada nivel hereda del de arriba y no vuelve a abrir su pregunta.

Nivel Qué pregunta responde Qué no debe hacer
PRD Qué producto y por qué Hablar de rutas o de tablas
Épica Qué territorio grande entra en el MVP Ser el prompt que le pasas al agente
Historia Qué necesita una persona, en un pedazo que cabe en una sesión Volver a discutir si el producto tiene sentido
Ticket Qué unidad de trabajo se hace ahora Inventar criterios nuevos
Spec ejecutable Cómo se comporta el sistema, ya con detalle técnico Volver a discutir el alcance

Si escribes tickets sin PRD, cada ticket vuelve a discutir el alcance. Si metes la visión de producto dentro de un cambio técnico, la herramienta no tiene dónde ponerla.

El prompt correcto para el agente es la historia, no la épica. "Gestión de reportes" es un territorio. Pedirle que programe la épica completa gasta contexto y devuelve algo aproximado. La historia, del tamaño de uno o dos días de una persona, es donde el agente rinde.

Qué responde un PRD útil

Define qué MVP se construye y por qué, antes del cómo. No es arquitectura ni una lista de tareas. Responde:

  • qué problema duele, y a quién,
  • qué entra,
  • qué no entra, y por qué,
  • qué tiene que poder hacer el sistema, en un lenguaje que se pueda comprobar,
  • cómo sabremos que funcionó.

La sección más subestimada es lo que queda afuera. Sin ella, cada sesión agrega un regalo.

Mal: "no haremos funciones avanzadas".

Bien: "el primer entregable no avisa por WhatsApp ni le asigna el trabajo al plomero de forma automática. Eso no comprueba si el inquilino deja de llamar a la oficina. Se mira después".

Un "esto no entra" útil nombra la cosa y el motivo.

Si todavía no hay tecnología elegida

El PRD sigue siendo de producto. Elegir la base de datos o armar el despliegue no son épicas de producto. No tienen un usuario ni entregan un valor que se pueda ver.

Eso es una fase de arquitectura aparte. O un esqueleto mínimo que solo demuestra que el sistema atraviesa de punta a punta. En este máster la tecnología ya viene del módulo 1. No la vuelvas a abrir dentro del PRD.

El PRD y la spec no se pisan

Son el mismo hilo, con distinto zoom.

  • El PRD y el backlog dicen qué se entrega y por qué. Viven en el proyecto y en el administrador de trabajo. Los escribe quien decide el producto, con el equipo.
  • La spec dice cómo se comporta exactamente. Vive junto al código, con historial. La escribe quien programa, a partir de la historia.

"El inquilino puede abrir un reporte" es producto. "Dado un reporte abierto, cuando recepción lo marca resuelto, el inquilino ve el estado resuelto" es la regla. La ruta, el código HTTP y el nombre del campo bajan un nivel más, cuando se programa. Es la misma regla, con más precisión. No es el mismo párrafo copiado.

La palabra "spec" se usa para demasiadas cosas. En sentido amplio, cada documento es una spec de su nivel. En sentido estricto, lo que un framework llama "la spec" es el último eslabón: el requisito con escenarios que el agente lee para construir y verificar. El PRD y las historias alimentan esa spec. No la reemplazan.

El PRD vive en el repositorio

El error de siempre es un documento de Google que nadie vuelve a abrir. En este método el PRD va en el proyecto, por ejemplo en docs/prd/..., y se revisa en un pull request. Cuando el producto cambia, cambia el documento, y Git guarda el cambio.

Es contexto cuidado. Es el pilar 2 del módulo 1. No es burocracia.

La IA cuestiona. No redacta sola

El error típico: "escríbeme un PRD de una app de fallas" y aceptar lo que salga. Sale genérico y lleno de suposiciones.

La forma de trabajar de este curso es usarla para encontrar huecos en el producto.

  • ¿Qué usuarios estoy dejando afuera?
  • ¿Qué parte de este alcance debería quedar fuera de un primer entregable, y por qué?
  • ¿Este requisito es esencial o es un gusto disfrazado?
  • ¿Qué estoy dando por cierto sin evidencia?

El criterio de producto sigue siendo tuyo. La IA acelera y señala huecos. Un MVP no necesita cuarenta páginas. Necesita el problema, el alcance, requisitos que se puedan comprobar y una forma de saber si funcionó.

Quien programa encuentra aquí la ocasión de decidir qué se construye, no solo cómo. Quien viene de producto encuentra el lugar donde esa decisión se vuelve algo que un agente puede ejecutar. El PRD es el punto donde se cruzan.

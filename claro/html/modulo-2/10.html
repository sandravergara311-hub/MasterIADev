Módulo 2 · Lección 10 — Ejercicio: recorta el MVP hasta poder defenderlo

Texto original: original/modulo-2/10.md
Obligatoria. Fecha límite: lunes 28 de septiembre de 2026, al final del día.
Repositorio: FlowSync.

En una frase

No se entrega un alcance largo. Se entrega lo que quedó afuera: qué dejaste fuera y por qué esa exclusión comprueba mejor la hipótesis.

Leerla es poco. Hacerla toma bastante más. Todo lo que hay que traer está aquí, y solo aquí.

El mismo gesto, en la inmobiliaria

A Luis, en Inmobiliaria Calle, la IA le mete en el primer entregable WhatsApp, chat con el plomero y estrellas. Un alcance largo lo escribe cualquiera. La IA lo escribe larguísimo.

Lo que cuesta es decir "esto no" de algo que suena razonable, y sostener el porqué.

"No alcanza el tiempo" no sirve. Mañana el calendario cambia y la excusa desaparece. El porqué que sí sirve: el WhatsApp no comprueba si el inquilino deja de llamar a la oficina. El reporte en la pantalla de recepción sí lo comprueba.

El ejercicio del curso hace ese recorte sobre FlowSync. Tiene un párrafo de partida fijo y una ficha de hechos que no debes inventar.

Cómo aprovechar el módulo

  1. Lo intentas tú, con reloj. Aunque quede a medias.
  2. Lo ves en la clase en vivo, sin escribir. El mentor parte del mismo párrafo vago.
  3. Lo repites con los prompts escritos. El agente no da siempre el mismo texto. Cambian la redacción, el orden de las preguntas y cuántas cosas propone. Se repite la forma, no el texto.

Deja el ambiente listo (5 a 10 minutos)

El proyecto funciona en macOS, en Linux y en Windows dentro de WSL. En PowerShell no. Los atajos del Makefile están escritos para una terminal de Linux o de Mac.

Si trabajas en Windows, haz el clon, Node y make dentro de Ubuntu en WSL. Lo que instales en Windows no existe dentro de WSL, y al revés. Clona en tu carpeta de Linux (~/…), no en /mnt/c. Desde ahí, npm install va muy lento.

Si no tienes WSL, instálalo con wsl --install desde PowerShell como administrador.

  • Node 24 o superior. Con la 20, make setup se detiene con Unknown file extension ".ts". Con la 22 arranca y avisa EBADENGINE. La versión LTS de nodejs.org cumple.
  • make --version responde. En macOS: xcode-select --install. En Linux y en Ubuntu dentro de WSL: sudo apt install make.
  • Tu fork de LIDR-academy/flowsync-ai4devs-202609-1, rama s2/start. Ya trae el harness: CLAUDE.md / AGENTS.md, un skill, un subagente, un hook y el MCP de Jira.

Si ya tienes el fork y upstream apunta al curso:

git fetch upstream
git checkout -b s2/start upstream/s2/start

Si empiezas de cero, trabaja sobre un fork. En el repositorio del curso no puedes hacer push.

# 1. Fork en https://github.com/LIDR-academy/flowsync-ai4devs-202609-1
# 2. Clona TU fork
git clone git@github.com:<tu-usuario>/flowsync-ai4devs-202609-1.git
cd flowsync-ai4devs-202609-1
git remote add upstream git@github.com:LIDR-academy/flowsync-ai4devs-202609-1.git
git remote -v

git fetch upstream
git checkout -b s2/start upstream/s2/start
git push -u origin s2/start

Si ya habías clonado el del curso, haz esto: git remote rename origin upstream y git remote add origin hacia tu fork. Si SSH dice Permission denied (publickey), sube la clave o usa HTTPS.

  • Desde la raíz del proyecto:
make setup   # solo la primera vez
make start   # backend en el puerto 3333 y frontend en el 5173

make start ocupa la terminal. Ctrl-C detiene los dos. Revisa en otra terminal: curl -s localhost:3333/ devuelve {"hello":"world"}. http://localhost:5173 muestra FlowSync.

Si cambias el puerto del backend, cambia VITE_API_URL en frontend/.env.

Fallas típicas: make no existe. Node es anterior a la 22. Te saltaste make setup. El puerto 3333 o el 5173 ya está ocupado.

Sin make, los mismos pasos a mano. npm install en backend/ y en frontend/. Copia cada .env.example a .env. En backend, corre node ace generate:key y node ace migration:run. Después, npm run dev en cada uno, en dos terminales.

  • Claude Code arranca y ve CLAUDE.md / AGENTS.md. El MCP de Jira sigue conectado, para crear los tickets en el tablero FLOW.
  • No instales ningún framework de specs. Hoy no se usan.

La tarea, unos 45 minutos

Guarda cada prompt tal como lo lanzaste, desde el primero. No sirven reconstruidos.

El párrafo de partida es el mismo de la clase:

Quiero que FlowSync sea una herramienta para que los equipos remotos sepan en qué está trabajando cada uno, sin tener que hacer reuniones de sincronización. Algo tipo tareas compartidas, pero más en tiempo real y con menos complicación que Jira.

"Más en tiempo real" y "con menos complicación que Jira" son sensaciones, no requisitos. El trabajo es exprimirlas hasta un alcance que se pueda defender. Va en docs/prd/alcance-mvp-<tus-iniciales>.md, no en el chat.

Cuando suene el reloj, paras. Tres exclusiones bien argumentadas dicen hasta dónde llegaste. Un documento completado de memoria diez minutos después no se distingue del bueno, y no sirve.

1. Lo que ya existe (3 a 5 líneas)

Antes de especificar, pídele al agente que te devuelva qué capacidades ya hay y cómo es el modelo de datos. Resume eso por escrito. Sirve para no volver a definir lo que ya está hecho.

2. Una sola ronda de preguntas

Pídele que pregunte antes de proponer. Que haga las cinco preguntas que más bajarían la incertidumbre sobre el problema, los usuarios y el alcance.

Una sola ronda. Prohíbele bajar al modelo de datos o a las rutas. Si no lo limitas, abre tres rondas más y se te va la tarde.

No inventes las respuestas. Copia y pega esta ficha completa, de una vez. Son las mismas decisiones que usa el mentor en la clase. Así tu recorte y el de la sesión hablan del mismo producto.

Si pregunta algo que la ficha no cubre, que lo decida ella y lo marque como supuesto. Lee esos supuestos. Ahí se cuelan los huecos.

  • Qué duele hoy: la daily de sincronización y el "¿en qué estás?" constante por Slack o por chat. Nadie ve el estado del equipo sin interrumpir a alguien.
  • Quién recibe el valor: los compañeros, no un líder. No hay un reporte hacia arriba. Le duele a quien descubre tarde que iba a lo mismo que otra persona, y a quien interrumpe para preguntar.
  • Episodio concreto: dos personas tocaron el mismo módulo la misma semana, porque una empezó sin que la otra lo supiera. Se perdieron dos días.
  • Qué reunión desaparece, sin venderlo de más: la daily no desaparece completa. Desaparece la ronda de "¿en qué estás?", que hoy se come la mitad de los 15 minutos. Los bloqueos siguen, y este MVP no los resuelve.
  • Usuarios: equipos remotos pequeños, de 3 a 10 personas. En el MVP, todos ven y editan lo mismo. No hay jerarquía de permisos.
  • Caso de estudio, no un cliente real: un equipo de 6 personas de producto en una empresa SaaS, en 3 zonas horarias. Hoy usa un administrador de tareas pesado y una daily de 15 minutos.
  • Límites: un espacio único compartido, sin una entidad llamada "equipo". Varios equipos, o una persona en más de uno, queda afuera. Se anota como supuesto. No se construye.
  • "Tiempo real" es ver los cambios de estado de las tareas sin refrescar ni preguntar. No es chat, ni videollamada, ni editar el mismo documento al mismo tiempo.
  • El estado es de la tarea, no de la persona. Nada de "quién está conectado". Eso es vigilancia, y se rechaza a propósito.
  • La señal espera. No interrumpe. El caso es llegar en la mañana y ver qué se movió. Sin notificaciones push.
  • Qué decisión cambia: no empezar algo que otra persona ya está tocando, y elegir lo siguiente sabiendo qué está libre. "Sentirse informado" no justifica el costo.
  • El estado lo escribe quien hace la tarea, en segundos. Sacarlo de Git, de los pull requests o del calendario queda afuera. Eso ya es otro producto.
  • Se sostiene porque son dos clics sobre una lista que ya está abierta. Sin campos obligatorios, sin sprint y sin estimación. Quien lo escribe también lo usa como su propia lista de trabajo.
  • Si la información se queda vieja, el producto pierde el sentido. Es el riesgo número uno, no un detalle. La forma de bajarlo es que actualizar cueste dos clics, no obligar a nadie.
  • Reemplaza al administrador de tareas. No convive con él. Convivir exigiría anotar lo mismo en dos lugares.
  • Se renuncia a sprints, estimaciones, épicas, backlog priorizado e informes. Un equipo que necesite eso no es el usuario.
  • "Con menos complicación que Jira" significa crear una tarea y cambiarle el estado en segundos, sin configuración y sin campos obligatorios.
  • Una tarea del MVP tiene título, responsable, estado y fecha de vencimiento.
  • La lista se usa filtrando por estado.
  • Éxito para el usuario: dejar de hacer la ronda de "¿en qué estás?", porque el estado se ve de un vistazo.
  • A la semana: el equipo cancela esa ronda y nadie pide que vuelva. Si la siguen haciendo igual, no funcionó.
  • Se construye un corte delgado y usable de punta a punta. No tres capacidades a medias.

Fuera del MVP, por si la IA empuja funcionalidades: notificaciones push, integración con Slack, roles y permisos avanzados, analítica y comentarios en las tareas.

3. Cinco bloques, y después recortas tú

Problema, usuarios, propuesta de valor, alcance y lo que queda afuera. Pídele que proponga recortando con fuerza, y que justifique cada exclusión.

Después recorta otra vez. Va a proponer de más. Ese segundo recorte es tuyo, y es lo que se revisa.

El error caro parece rigor. Si la dejas seguir, el alcance crece solo hacia el modelo de datos, los diagramas y los requisitos numerados. Eso ya es otro documento.

Un documento de producto no lleva tablas, ni rutas, ni arquitectura. Ese detalle sale del código y se pone viejo enseguida. Si aparece, súbelo de nivel o quítalo, y anótalo.

Parte B. Tres líneas, debajo, en el mismo archivo

  1. Dos números, sin redondear. Cuántas cosas propuso meter. Cuántas quedaron adentro después de tu recorte.
  2. Tres cosas que dejaste afuera, y por qué. El porqué dice qué hipótesis no ayudan a comprobar. "No alcanza el tiempo" no sirve.
  3. La exclusión de la que menos seguro estás, y qué tendría que pasar para que entrara. Mejor cuanto más incómoda. "Lo tengo todo claro" es la respuesta de quien aceptó la primera propuesta.

Si la IA te discutió una decisión y tenía razón, anótalo aunque ninguna de las tres líneas lo pida. Por ejemplo: el documento pide algo que él mismo prohíbe, o promete algo que su propio alcance impide cumplir. Eso es un error tuyo, y es lo más útil de la sesión.

Cómo saber que quedó bien

  • Lo que quedó afuera ocupa tanto como lo que quedó adentro, o más.
  • Cada exclusión tiene su porqué al lado.
  • Las tres líneas son concretas.
  • No hay ni una tabla ni una ruta.
  • Cabe en una pantalla larga. Un MVP de diez páginas no es un MVP.

Entrégalo con lo que tenga.

Cómo se entrega

El archivo va en docs/prd/alcance-mvp-<tus-iniciales>.md, con los tres tramos y las tres líneas. Si la carpeta no existe, créala.

git checkout -b alcance-<tus-iniciales>
git add docs/prd prompts.md
git commit -m "alcance: MVP + prompts"
git push -u origin alcance-<tus-iniciales>

El pull request va contra el repositorio del curso. Lleva solo ese archivo y prompts.md. La rama de partida trae la plantilla. Pega los prompts tal cual, con el modelo y la herramienta. Incluye también los que fallaron.

Sin ese archivo no se distingue un alcance flojo pedido bien de uno pedido mal.

Antes de la clase hay comentarios de tu TA. Después se marca como recibido y no se revisa.

Antes de conectarte

  • Estás en la rama de partida, sobre tu fork, y git push funciona.
  • make start enciende el proyecto y el agente lee el contexto.
  • Traes el archivo, aunque esté a medias, con las tres líneas.
  • prompts.md está lleno.
  • El pull request está abierto.

Si el reloj aprieta, prioriza las tres líneas honestas. Valen más que un alcance largo sin recortar. De la teoría, prioriza las lecciones 2, 3 y 5.

Qué te llevas del módulo

Una spec viva que manda. No es "el análisis de siempre, con un chatbot encima". Una cadena en la que cada escalón responde una pregunta distinta. Un criterio del negocio, que se puede comprobar, distinto del escenario ejecutable. Y el hábito de usar la IA para encontrar huecos en lo escrito, no para redactarlo.

En el proyecto queda el PRD con historial, con lo que quedó afuera escrito de forma explícita, y tu archivo de recorte con el argumento de lo que dejaste fuera.

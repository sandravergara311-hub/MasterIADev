Módulo 8 · Lección 8 — Fuentes sobre sistemas repartidos en varios repositorios

Texto original: original/modulo-8/8.md
Opcional. El archivo original no trae el ejercicio que anuncia el mapa del módulo. Trae esta lista de fuentes.

En una frase

Cada enlace de esta lección se apoya en una frase concreta de la fuente. Cuando la fuente es quien fabrica la herramienta, sirve muy bien para saber qué hace. Sirve con interés propio para decidir si te conviene.

Caso real: cuando las reservas ya no caben en un solo sitio

Nora, en el Cowork La Mesa, tiene hoy la aplicación de reservas en un solo proyecto. Estas fuentes son las que el original deja a mano si ese sistema se reparte en varios repositorios y hay que saber qué regla se carga, desde dónde, y qué se queda fuera.

Para saber qué gobierna al agente y qué no

How Claude remembers your project, documentación oficial de Anthropic. Es la referencia de cómo se descubren los archivos de instrucciones. Trae los dos apartados que más faltan aquí.

El primero: «CLAUDE.md and CLAUDE.local.md files in the directory hierarchy above the working directory are loaded in full at launch». Explica por qué un archivo que vive por encima de tus repositorios acaba gobernando sin estar dentro de ninguno.

El segundo, en la sección de directorios adicionales: «By default, CLAUDE.md files from these directories are not loaded». Trae además la variable de entorno que lo cambia. Conviene leer dónde se pone, porque es tu máquina y no el proyecto.

Esta página describe la versión de hoy. Lo mismo sirve para cualquier documentación de una herramienta viva. Lo que no cambia es la pregunta con la que hay que leerla. ¿Qué se carga, desde dónde, y qué se queda fuera?

Para lo que no pertenece a ningún repositorio

El repositorio Fission-AI/OpenSpec, licencia MIT. Interesa su idea de planificar en un repositorio propio. El README lo describe así: «Planning in a repo of its own. The same openspec/ shape you already know (specs and changes), shared by git push like anything else». Léelo con esta condición delante. Lo que se publica con git push es el contenido. La parte que resuelve qué almacén es cuál se queda en tu computadora.

TechDocs, documentación de Backstage. El ejemplo mejor documentado de reunir al leer: «Engineers write their documentation in Markdown files which live together with their code». El sitio se construye encima. Sirve para ver cómo es centralizar la consulta sin mover la fuente, aunque no vayas a montarlo.

Git Tools: Submodules, libro Pro Git, capítulo oficial. Si te planteas traer un repositorio dentro de otro, empieza aquí y no por un tutorial. La frase que explica de dónde salen la mitad de los sustos: «Instead, Git sees it as a particular commit from that repository». Un submódulo no apunta a una rama. Apunta a un commit concreto. Quien no lo sepa va a pasar una tarde entendiendo por qué su compañero ve otra cosa.

Para el cambio que cruza dos repositorios

Parallel Change, de Danilo Sato. Es el nombre canónico de lo que en el módulo anterior se contó como ventana de compatibilidad. Conviene conocerlo porque es el término con el que vas a encontrar el resto del material. Su definición, literal: «a pattern to implement backward-incompatible changes to an interface in a safe manner, by breaking the change into three distinct phases: expand, migrate, and contract». Las tres fases son expandir, migrar y contraer.

Versionado semántico, la especificación, en español. Es corta y conviene leerla entera una vez. La regla que sostiene el resto: «La versión mayor (X.y.z X > 0) DEBE ser incrementada solamente si se introducen cambios incompatibles con la versión anterior del API público». Es la convención que convierte «cambié algo» en una señal que el consumidor puede leer sin hablar contigo.

Un ejercicio de quince minutos

Elige un sistema tuyo repartido en varios repositorios y abre su historial de los últimos tres meses. Recorre los cambios que se integraron y márcalos con una de dos etiquetas. Entró solo, o tuvo que entrar acompañado de un cambio en otro repositorio.

No necesitas herramientas ni precisión. Una pasada rápida por treinta cambios, sin medir cada uno al detalle, ya da la señal.

Si el segundo grupo es una minoría clara, tus fronteras describen bien el sistema y no hay nada que tocar. Si se acerca a la mitad, acabas de convertir una discusión de arquitectura que llevaba meses sin resolverse en un número que se puede mirar. En los dos casos habrás hecho lo que casi nadie hace. Comprobar una decisión vieja, en vez de defenderla.

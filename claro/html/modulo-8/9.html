Módulo 8 · Lección 9 — Mide una regla que creías cumplida

Texto original: original/modulo-8/9.md
Obligatoria. Es lo único que necesitas traer preparado. La fecha límite es Miercoles 11 De Noviembre 2026 al final del día. Repositorio: Flowsync. Calcula unos 45 minutos.

En una frase

Vas a medir, en el proyecto del curso, si una regla que lleva meses en el archivo de instrucciones del agente se cumple de verdad. Guardas cada pedido (prompt) tal como lo enviaste. El proceso importa más que el resultado.

Caso real: la regla de las salas

Nora, en el Cowork La Mesa, ya tiene reglas escritas para el agente. Esta lección no mide esas reglas del cowork. Mide una regla del proyecto del curso, FlowSync, con el mismo encargo y el mismo archivo de salida que usará el mentor en la clase en vivo. Tú decides cómo formular los pedidos (prompts).

El ejercicio tiene dos partes. La medición (Parte A) y tres líneas de reflexión (Parte B).

Cómo funciona este módulo

  1. Lo intentas tú. Trabajas sobre el proyecto de abajo, con tu agente y el tiempo que tengas. Entregas lo que hayas conseguido, aunque esté incompleto. No se evalúa si terminaste todo. Podrás resolver dudas siguiendo la clase en vivo o preguntando al mentor por las diferencias entre tus resultados y los de la sesión.

  2. Lo ves resuelto en la clase en vivo. El mentor mide la misma regla, con el mismo encargo y el mismo proyecto. Después muestra cómo automatizar los cinco intentos y sus comprobaciones, para que puedas ejecutar la medición de nuevo sin repetir cada paso ni revisar los resultados a mano. Esa automatización no forma parte de tu ejercicio previo. Si no conseguiste terminar, podrás ver cómo resolverlo. Conviene observar sin intentar repetir cada paso.

  3. Lo replicas. Recibirás por escrito los pedidos (prompts) del mentor. Con ellos vuelves a tu ambiente y repites el proceso con calma.

En el paso 3 no esperes resultados idénticos. El agente no es determinista. Con el mismo encargo pueden cambiar los nombres, la redacción e incluso si el README de la capability queda actualizado. Esa variabilidad es lo que se quiere estudiar. Por eso el ejercicio pide cinco intentos, no uno. Lo que debes repetir es el procedimiento, no el texto generado.

Deja el ambiente listo

1. Comprueba los requisitos

Verifica cada requisito con su comando. También tienes el error que puede aparecer si falta o no tienes la versión adecuada.

Node 24 (versión con soporte a largo plazo): node -v debe responder v24.x. Con Node 20, make setup falla con ERR_UNKNOWN_FILE_EXTENSION ".ts". Con Node 22 aparecen numerosos avisos EBADENGINE.

make: make --version. Si falta, verás command not found: make.

git: git --version. Si falta, verás command not found: git.

Claude Code, instalado y con la sesión iniciada: claude --version debe mostrar una versión. No necesitas una versión específica para este ejercicio.

Sistemas compatibles: macOS y Linux directamente. En Windows debes usar el Subsistema de Windows para Linux (WSL) y hacer todo dentro de él: clonar el repositorio, instalar Node y ejecutar make. Las herramientas instaladas en Windows no están disponibles automáticamente en WSL. No utilices PowerShell. El Makefile del proyecto usa comandos como cp, test y rm, propios de los entornos de shell de macOS y Linux.

El ejercicio consume recursos de tu plan de Claude. Cada intento implica una ejecución completa del agente y necesitas hacer cinco. Para evitar consumo innecesario, anota cada resultado antes de repetir un intento.

# 1. Forkea https://github.com/LIDR-academy-temp/flowsync-ai4devs-202609-1 desde la interfaz de GitHub.

3. Comprueba que el proyecto funciona

Ejecuta los tests antes de continuar. Así no confundes un problema del proyecto con un fallo de la medición.

(cd backend && npm test)    # tiene que terminar en verde

Mantén los paréntesis. Permiten ejecutar el comando dentro de backend/ y volver automáticamente a la raíz del proyecto. Sin ellos, si entras a mano en esa carpeta, puedes acabar lanzando los siguientes comandos desde un directorio donde no está CLAUDE.md.

La tarea

Parte A: medir la regla del README de la capability

La regla está en la sección de reglas de proceso del archivo CLAUDE.md y dice literalmente:

«Un cambio que toque rutas, controladores, validadores o transformers de una capability se cierra en el mismo commit con el documento OpenAPI y el README de esa capability al día.»

Vas a comprobar en qué proporción de los intentos se actualiza el README de la capability tasks con este encargo:

«Añade a la capability tasks el endpoint DELETE /api/v1/tasks/:id, que borra una tarea y devuelve 204 sin cuerpo. Impleméntalo en el controlador que ya existe y declara su ruta junto a las demás de tasks.»

Sigue estos cinco pasos en orden.

  1. Anota tu predicción antes de empezar. ¿En cuántos de los cinco intentos crees que el README de la capability quedará actualizado? Escríbelo antes de ejecutar el primero, para poder comparar tu expectativa con el resultado.

  2. Envía el encargo exacto en una sesión nueva. Cópialo completo y no le recuerdes la regla al agente. Queremos medir si la sigue sin recibir instrucciones adicionales.

  3. Haz las dos comprobaciones de cada intento, en este orden.

    • Control: ¿quedó declarada la ruta DELETE? Si no, el agente no completó el encargo y ese intento no cuenta para medir el cumplimiento del README.
    • Resultado: ¿el archivo docs/capabilities/tasks/README.md menciona el endpoint nuevo?

  4. Devuelve el proyecto a su estado inicial para que el siguiente intento empiece en las mismas condiciones.

git checkout -f s8/start            # vuelve a la rama de partida, descartando cambios
git reset --hard upstream/s8/start  # deshace lo que el agente haya commiteado
git clean -fd                       # borra los archivos nuevos que dejó

Verifica el resultado con git status -sb. Debe mostrar únicamente la línea que empieza por ## s8/start. Si aparecen más cambios, todavía no has recuperado el estado inicial.

  1. Repite el proceso hasta completar cinco intentos y registra las dos comprobaciones de cada uno.

git restore . no es suficiente y puede dejar cambios sin que lo notes. El archivo CLAUDE.md también indica al agente que debe crear una rama y hacer un commit al terminar. Si lo hace, git restore . no deshace esos commits. Incluso puedes ver el estado limpio en git status y seguir en la rama del intento anterior, con sus cambios guardados. En ese caso, el siguiente ensayo partiría de un estado diferente y los resultados dejarían de ser comparables.

Puedes ignorar las ramas feat/… que genere cada intento. No interfieren con la medición. Lo importante es que todos comiencen desde el mismo estado.

La repetición es parte del ejercicio. Medir el cumplimiento de una regla exige ejecutar el mismo encargo varias veces y registrar los resultados. Ahora lo harás a mano. En la clase en vivo verás cómo automatizarlo.

Parte B: las tres líneas

Esta es la parte principal de la revisión. No necesitas completar los cinco intentos para responderla. Puedes explicar lo que observaste aunque la medición haya quedado incompleta.

  • Tu predicción y el resultado obtenido. Si no completaste los cinco intentos, indica cuántos hiciste.
  • Qué harías con ese resultado: eliminar la regla, reescribirla o convertirla en una comprobación automática. Explica por qué tomarías esa decisión.
  • Algo que tu medición no está comprobando. Identifica al menos una limitación de los resultados.

Guarda ambas partes en docs/evals/<tus-iniciales>.md, dentro del proyecto.

La IA no es determinista y esa variabilidad es lo que se está midiendo. Si repites el encargo y obtienes resultados distintos, no significa que hayas hecho algo mal. Al repetir el ejercicio con los pedidos (prompts) del mentor tampoco obtendrás necesariamente las mismas respuestas. Lo importante es seguir el mismo procedimiento.

Cómo saber que la has hecho bien

  • Escribiste tu predicción antes del primer intento y no la modificaste después de ver los resultados.
  • Todos los intentos empezaron desde el mismo estado. Si alguno partió de los cambios del anterior, su resultado no es comparable. Compruébalo con git status -sb antes de ejecutarlo.
  • Registraste las dos comprobaciones de cada intento: control y resultado. Los intentos donde el agente no declaró la ruta están marcados como no contados.
  • Respondiste las tres preguntas con información concreta. Si en la tercera afirmas que la medición lo comprueba todo, revisa qué aspectos quedan fuera.
  • Anotaste cada resultado antes de repetir un intento. Así evitas perder información y consumir recursos innecesarios.

Entrega lo que hayas conseguido, aunque esté incompleto.

Cómo se entrega

Tu rama

Créala después de terminar los intentos, cuando vayas a preparar la entrega. Si la creas antes, los comandos de limpieza te devolverán a s8/start entre ejecuciones.

Partiendo de la rama inicial, con el proyecto limpio:

git checkout s8/start
git checkout -b evals-<tus-iniciales>

Utiliza esta rama para guardar los archivos de entrega.

El pull request

Abre un pull request desde tu fork, con estos dos archivos:

  • docs/evals/<tus-iniciales>.md, con las partes A y B.
  • prompts.md, en la raíz del proyecto, con todos los pedidos (prompts) enviados. Guarda cada uno en su propio bloque de código e indica el modelo y la herramienta utilizados.
git add docs/evals prompts.md
git commit -m "evals: medicion de la regla + prompts"
git push -u origin evals-<tus-iniciales>

Después del push, GitHub mostrará la opción de crear un pull request. Debe dirigirse al repositorio del curso (github.com/LIDR-academy-temp/flowsync-ai4devs-202609-1), no a tu fork. Comprueba que ese sea el repositorio base.

El plazo

Plazo: antes de la clase en vivo. Lo que llega a tiempo recibe comentarios antes de la sesión, y así puedes compararlo con lo que veas en vivo. Lo que llega tarde se marca como recibido y no se revisa.

Si vas justo de tiempo

Prioriza las lecciones sobre por qué una regla escrita no garantiza su cumplimiento y por qué una métrica necesita una línea base de comparación. Son las dos que más te ayudarán a interpretar la tabla de intentos. Las otras tres podrás seguirlas durante la clase en vivo.

Si apenas te queda tiempo para el ejercicio, céntrate en las tres líneas de la Parte B. Tres respuestas concretas basadas en dos intentos aportan más que cinco intentos sin analizar.

Antes de conectarte, comprueba

  • Trabajaste sobre tu fork, desde la rama de partida, y git push funciona.
  • node -v responde v24.x, y make --version funciona en la terminal donde trabajas (en Windows, dentro de WSL).
  • claude --version funciona y tienes la sesión iniciada.
  • Sabes dónde está la regla dentro de CLAUDE.md y la has leído completa.
  • Tienes docs/evals/<tus-iniciales>.md, con la tabla de intentos (aunque esté incompleta) y las tres líneas de la Parte B.
  • prompts.md contiene los pedidos (prompts), con el modelo y la herramienta utilizados.
  • Tu rama se llama evals-<tus-iniciales> y el pull request está abierto contra el repositorio del curso.

Trae los archivos tal como quedaron, sin ocultar errores ni pasos incompletos. También sirven para aprender.

Qué te llevas del módulo 8

El modelo mental:

  • Una regla escrita en un archivo de instrucciones no garantiza que el agente la cumpla.
  • Para conocer su porcentaje de cumplimiento necesitas repetir el mismo encargo varias veces.
  • Ese resultado solo tiene sentido si lo comparas con lo que ocurre sin la regla, porque el modelo podría hacer parte del trabajo igualmente.
  • Cada intento necesita una evaluación, de preferencia con código cuando sea posible.
  • Si utilizas un juez basado en IA, debes calibrarlo antes de confiar en sus puntuaciones.
  • También necesitas validar la propia medición. Una comprobación que nunca has visto fallar no demuestra que detecte errores.

Lo que queda en el proyecto: tu medición guardada en docs/evals/, con el encargo, las dos comprobaciones de cada intento, los resultados y tu decisión sobre la regla. Tendrás una referencia para comparar futuras modificaciones del modelo o del archivo de instrucciones. Sin un resultado anterior, no podrás saber si los cambios mejoraron el cumplimiento.

Según de dónde vengas:

  • Si desarrollas: trata las comprobaciones como código de producción. Empieza por una validación sencilla sobre un archivo y comprueba que detecta errores introducidos a propósito.
  • Si vienes de producto o gestión: ante una métrica de calidad, pregunta «¿qué resultado obtenemos sin esta configuración?» y «¿han comprobado que la evaluación detecta fallos?». Sin esas respuestas, el porcentaje puede llevar a conclusiones equivocadas.
  • Si no tienes experiencia técnica: piensa en una alarma de incendios. Que esté instalada no garantiza que funcione. Hay que probar que suena cuando detecta humo. Con una evaluación ocurre lo mismo. Debes comprobar que detecta los errores que buscas.

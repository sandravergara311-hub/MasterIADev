Módulo 4 · Lección 6 — Ejercicio: mide qué está probado de verdad

Texto original: original/modulo-4/6.md
Obligatoria. Fecha límite: lunes 12 de octubre de 2026, al final del día.
Repositorio: FlowSync.

En una frase

El entregable que importa son tres líneas honestas, no una matriz completa. La matriz dice, escenario por escenario, si el requisito del responsable de la tarea tiene una prueba que de verdad lo cubre.

Leerla son nueve minutos. Hacerla lleva más. Unos 10 de ambiente, unos 45 de la tarea, y 5 más si abres las lecturas. No la dejes para la noche anterior.

Caso real, y después el proyecto del curso

En la Biblioteca del Barrio, Sofía creía que el caso "devuelto y con fecha pasada" estaba probado porque la suite estaba en verde. No lo estaba. Este ejercicio hace ese mismo gesto sobre FlowSync, sobre un requisito concreto de las tareas.

Cómo aprovechar el módulo

  1. Lo intentas tú, con reloj. Entregas lo que salga, aunque esté a medias. Este paso no se califica por terminarlo.
  2. Lo ves en la clase en vivo, sin escribir. El mentor hace este mismo trabajo, sobre este mismo proyecto.
  3. Lo repites con los prompts escritos. El agente no da siempre el mismo resultado. Con el mismo prompt y el mismo código pueden cambiar los nombres, la redacción y hasta el número de filas de una tabla. Se repite la forma del recorrido, no el texto.

Deja el ambiente listo

El proyecto funciona en macOS, en Linux y en Windows a través de WSL. En PowerShell no. Los atajos del Makefile están escritos para macOS y Linux.

Si trabajas en Windows, haz el clon, Node y make dentro de la terminal de WSL. WSL es un ambiente separado. Lo que tengas instalado en Windows no está disponible dentro de él, y lo que instales dentro no afecta a Windows. Clona en tu carpeta de Linux (~/…), no en /mnt/c. Desde ahí npm install va muy lento. Si no tienes WSL: wsl --install desde PowerShell como administrador.

1. Node.js 24 o superior

node -v tiene que responder v24 o más. Con la 20 el proyecto no arranca. make setup se detiene con Unknown file extension ".ts". Con la 22 arranca y avisa EBADENGINE, porque el proyecto pide la 24. La LTS de nodejs.org/en/download cumple.

2. make

make --version tiene que responder. Si no: en macOS, xcode-select --install. En Linux y en WSL, sudo apt install make.

3. Tu fork, en la rama de partida

Necesitas el proyecto en la rama s4/start, sobre tu propio fork de github.com/LIDR-academy/flowsync-ai4devs. Si clonas el repo del curso tal cual, no tendrás permiso de push.

# 1. Fork en github.com/LIDR-academy/flowsync-ai4devs-202609-1

# 2a. Si AÚN NO has clonado: clona TU fork (no el del curso)
git clone git@github.com:<tu-usuario>/flowsync-ai4devs-202609-1.git
cd flowsync-ai4devs
git remote add upstream git@github.com:LIDR-academy/flowsync-ai4devs-202609-1.git

# 2b. Si YA clonaste el del curso: no vuelvas a clonar, recoloca los remotos
git remote rename origin upstream
git remote add origin git@github.com:<tu-usuario>/flowsync-ai4devs-202609-1.git

# 2c. Si ya venías trabajando sobre tu fork: solo comprueba que están los dos
git remote -v          # origin = TU fork · upstream = el repo del curso

# 3. Trae las ramas nuevas del curso y colócate en la de este módulo
git fetch upstream
git checkout -b s4/start upstream/s4/start

# 4. Comprueba que el fork quedó bien montado: esto tiene que funcionar
git push -u origin s4/start

Un fork es una foto del momento. El curso sigue publicando ramas. Las que todavía no se publicaron no existen en tu fork, y tu fork no se actualiza solo. Por eso el git fetch upstream va antes del checkout. Si el comando responde pathspec did not match, casi siempre es porque esa rama todavía no existe en tu fork. O no se ha publicado aún, o te faltó el git fetch upstream. Si responde 'upstream' does not appear to be a git repository, falta el git remote add del paso 2. Si el push del paso 4 te rechaza por permisos, origin sigue apuntando al repo del curso. Vuelve al 2b.

Si sale Permission denied (publickey), es SSH, no el fork. Los comandos de arriba usan direcciones git@github.com:…. Necesitan una clave subida a tu cuenta. Súbela, o cambia las direcciones por HTTPS (https://github.com/<tu-usuario>/flowsync-ai4devs.git y https://github.com/LIDR-academy/flowsync-ai4devs.git).

4. El proyecto enciende

Desde la raíz. Conviene hacerlo hoy. Descubrir que algo no compila con la clase empezada es el peor momento.

make setup   # solo la primera vez
make start   # backend en el puerto 3333 y frontend en el 5173

make start ocupa la terminal. Ctrl-C detiene los dos. Si uno se cae, se lleva al otro. make solo lista los atajos. En otra terminal, curl -s localhost:3333/ tiene que devolver {"hello":"world"}. http://localhost:5173 tiene que mostrar FlowSync. El frontend espera el backend en http://localhost:3333. Si lo arrancas en otro puerto, actualiza VITE_API_URL en frontend/.env.

Fallas típicas: make no existe. Node anterior a la 22 (Unknown file extension ".ts"). Te saltaste make setup. El puerto 3333 o el 5173 ya está ocupado.

Sin make, a mano. npm install dentro de backend/ y de frontend/. Copia .env.example a .env en cada una. Desde backend/, node ace generate:key y después node ace migration:run. Arranca cada parte con npm run dev, en dos terminales.

5. La suite corre y sale en verde

Lánzala desde backend/ con npm test. Si estás en la raíz, usa (cd backend && npm test). Los paréntesis hacen que vuelvas a la raíz al terminar. Todas las pruebas tienen que pasar. Si algo falla, es un problema de ambiente. Resuélvelo ahora.

6. Abre openspec/specs/

Busca la spec viva de la gestión de tareas. Cada carpeta dentro de openspec/specs/ es una capability. Un ámbito del comportamiento del sistema, descrito como debe comportarse, no como está implementado. Adentro están los requisitos y, asociados a cada uno, los escenarios. Familiarízate con la estructura antes de empezar. La tarea parte de ahí.

7. Claude Code arranca y lee tu contexto

Abre .claude/agents/ y anota qué subagentes tienes ya, aunque la respuesta sea "ninguno". Es la carpeta donde vas a trabajar. Si no tienes ninguno de revisión, no es un problema. Un subagente es un archivo Markdown con su propio prompt y sus permisos. Crearlo lleva un minuto.

8. Crea tu rama

git checkout -b trazabilidad-<tus-iniciales>

Todo lo que produzcas va en esa rama.

La tarea

Vas a trabajar el requisito «Lo que cada tarea muestra de su responsable», que está en openspec/specs/tasks/spec.md. Es el mismo sobre el que trabajará el mentor en la clase. Lo intentas tú primero, con tus propios prompts. El objetivo es una matriz de trazabilidad. Revisar, escenario por escenario, si cada uno tiene una prueba que lo cubre, y escribir las que falten. La primera parte va con reloj. La segunda, sin él, para pensar lo que encontraste.

Guarda cada prompt tal como lo lanzaste, desde el primero. Se entregan junto con la matriz. No se aceptan reconstruidos.

Dónde va cada cosa:

  • La matriz y las tres líneas van juntas en docs/verificacion/<tus-iniciales>.md. Es una carpeta nueva. La crea tu archivo.
  • Las pruebas que escribas van en backend/tests/functional/tasks/, siguiendo el estilo de las que ya hay en backend/tests/functional/auth/. No toques nada fuera de backend/tests/.
  • Trabaja en la rama que creaste al dejar el ambiente listo.

Reserva unos 45 minutos y pon el reloj. Si lo dejas para la noche anterior, es fácil llenar la matriz de memoria, sin mirar cada respuesta. La tarea quiere que notes la diferencia entre completar la matriz por cumplir y dedicarle el tiempo para que sirva.

Parte A. La matriz y las pruebas que faltan, con reloj

Tres términos de esta parte:

  • Requisito. Una regla de comportamiento del sistema. Define qué debe ocurrir en una situación concreta.
  • Scenario. Un ejemplo concreto asociado a un requisito, con su par de cuándo y entonces, contra el que se comprueba esa regla.
  • Capability. Un grupo de requisitos que cubre un ámbito de comportamiento completo.

Con un agente, trabaja solo el requisito «Lo que cada tarea muestra de su responsable». Produce dos entregables. Déjalos en archivos del repositorio, no en el chat.

No cubras la capability entera, aunque quepa o el agente se ofrezca. La unidad es el requisito, porque es lo que cabe en el tiempo. Este en particular tiene peso real. Define qué datos de una persona aparecen junto a cada tarea. Es lo primero que se rompe sin que nadie lo note.

A.1. La matriz.

Mapea, escenario por escenario, si el requisito está cubierto por las pruebas. El formato no se negocia. Una fila por escenario y cuatro columnas. Encima, dos números: cuántos escenarios tiene el requisito y cuántos resultaron cubiertos. El primero se anota al empezar. El segundo, al terminar.

  • El escenario, en una línea. Qué se espera y en qué situación. Si no cabe en una línea, estás juntando dos.
  • Qué prueba lo cubre, con el nombre exacto que aparece en la suite. Sin el nombre concreto, la columna va vacía. "Seguro que algo lo cubre" no es una fila.
  • Cubierto, no cubierto, o no lo sé. Los tres estados son válidos. El tercero no es un fallo. Es el resultado más informativo de los tres.
  • Si pusiste "no lo sé", qué te faltó para decidirlo. Media línea. Suele ser una de dos. No encontraste dónde se comprueba, o encontraste algo que se le parece y no dice exactamente lo mismo.

Los dos números van encima. El primero antes de empezar. El segundo al terminar.

Scenarios en el requisito: 4 · Cubiertos: ___

| Scenario | Test que lo cubre | Estado | Qué te faltó |
| --- | --- | --- | --- |
| La tarea muestra el nombre del responsable cuando tiene uno asignado | show_assignee_name_when_present | Cubierto | — |

El nombre de una prueba no es prueba de cobertura. Una prueba puede llamarse igual que el escenario y comprobar otra cosa, o solo la mitad. Para marcar cubierto hay que abrir la prueba y leer lo que afirma. Es la columna que más caro sale llenar de memoria. Es justo la que esta tarea quiere que mires.

A.2. Las pruebas que faltan.

Por cada fila en "no cubierto", escribe la prueba que falta. Una por escenario. Sigue el estilo de las que ya existen. Sin tocar nada fuera de la carpeta de pruebas. Cuando las tengas, ejecútalas.

Pase lo que pase, no arregles el código ni ajustes la prueba para que pase. Si algo se pone en rojo, se queda en rojo y se entrega en rojo. El objetivo es saber qué está mal, no ocultarlo. Quien verifica no arregla, porque quien arregla deja de ver.

Cuando suene el reloj, paras. Aunque esté a medias. Aunque falten filas, aunque haya pruebas sin escribir, aunque justo ibas a comprobar una cosa.

Una matriz con cuatro filas llenas y el resto en blanco es información. Dice hasta dónde llegaste. Una fila completada de memoria diez minutos después no se distingue de la buena, y no sirve.

Parte B. Las tres líneas

Van en el mismo archivo que la matriz, docs/verificacion/<tus-iniciales>.md, justo debajo. Una línea cada una. No más. No en un archivo separado. No en el chat. Esta parte es obligatoria. Es lo mínimo que hay que entregar.

  1. Cuántos escenarios creías cubiertos antes de mirar, y cuántos lo estaban. El primer número se anota antes de lanzar el primer prompt, sin abrir nada todavía. El segundo, al terminar. Los dos exactamente como quedaron, sin redondear ni explicar.
  2. El escenario en el que no supiste si faltaba una prueba o faltaba la regla en la spec. Cuál fue y qué te hizo dudar. Las dos opciones se confunden. En un caso la regla existe pero nadie la comprobó. En el otro, la regla no está escrita en ninguna parte. La estabas definiendo tú.
  3. Algo que el escenario no determinaba y tuviste que decidir al escribir la prueba. Un valor concreto, un límite, qué pasa cuando el dato viene vacío. Casi ningún escenario determina su prueba del todo. El hueco que cubriste sin notarlo es lo que más se parece a un defecto futuro.

Ninguna de las tres tiene una respuesta correcta. La segunda y la tercera son más útiles cuanto más incómodas sean. Un "no sabía si esto me correspondía decidirlo a mí", dicho con honestidad, aporta más que una matriz completa llena de certezas inventadas.

Cómo saber que quedó bien

  • Las tres líneas están escritas y son concretas. Si la tercera dice "el escenario lo decidía todo", vuelve a mirar la prueba que escribiste. Los valores que pusiste vinieron de algún sitio, y ese sitio eras tú.
  • Los dos números de la primera línea no coinciden. Casi nunca coinciden. Eso no es un fallo. Es el dato entero de la tarea.
  • Hay al menos un "no lo sé" en la matriz. Significa que abriste las pruebas en lugar de fiarte de sus nombres.
  • La matriz cabe en una pantalla. Si no cabe, saliste del requisito y estás cubriendo la capability entera otra vez.
  • Hay alguna prueba tuya en rojo, o sabes decir por qué no la hay. Las dos respuestas sirven. Lo que no sirve es no haberlo mirado.

Cómo se entrega

El entregable principal son las tres líneas de la parte B, no completar toda la matriz. Puedes escribirlas aunque la matriz esté a medias. Si se acaba el tiempo, deja la matriz como esté y pasa a escribir esas tres líneas.

Que la matriz no tenga ningún "no lo sé" no significa que esté bien hecha. Puede ser una señal de alerta. Cuando examinas un requisito de verdad, es normal que aparezcan dudas.

Todo va en la rama que creaste.

Un pull request desde tu fork, con tres cosas y nada más:

  • Tu archivo de docs/verificacion/, con la matriz y las tres líneas.
  • Las pruebas que hayas escrito, tal como quedaron. En verde, en rojo o a medias.
  • prompts.md, en la raíz.
git add docs/verificacion backend/tests prompts.md
git commit -m "trazabilidad: responsable de la tarea + prompts"
git push -u origin trazabilidad-<tus-iniciales>

El pull request va contra el repositorio del curso, no contra tu fork.

prompts.md es la mitad de lo que se revisa. Un resultado flojo con un prompt bueno y uno flojo con un prompt vago se corrigen distinto. Sin ese archivo no se distinguen. Pega los prompts tal cual, con el modelo y la herramienta. Incluye también los que no funcionaron.

Lo que llegue antes de la clase recibe comentarios de tu TA. Ahí es cuando te sirve. Si llegas tarde, el pull request queda registrado y no recibe comentarios.

Si vas justo de tiempo

Repasa las lecciones de verificación, trazabilidad y revisión adversarial.

Revisa la plantilla MADR para ver cómo se estructura un ADR. Con 5 minutos alcanza. Es la variante extendida. El curso trabaja con los cinco apartados del formato original.

Mira la sintaxis de diagramas de flujo en Mermaid. Con entender cómo se declara un nodo y cómo se conecta con una flecha es suficiente. El resto está en la lección de recursos.

Antes de conectarte

  • Estás en la rama de partida, sobre tu fork, y git push funciona.
  • El proyecto enciende y la suite corre en verde.
  • Traes el archivo de la tarea, con su matriz, aunque esté a medias, y sus tres líneas.
  • Las pruebas que escribiste están confirmadas en Git tal como quedaron, sin maquillar.
  • prompts.md está lleno, con modelo y herramienta en cada bloque.
  • El pull request está abierto.

Qué te llevas del módulo

Pruebas en verde no son lo mismo que correcto. Una prueba verde comprueba lo que pregunta, no lo que ignoró. Verificar es trazar cada criterio hasta su prueba y su código. La revisión adversarial refuta en lugar de validar. Un subagente independiente contrasta el resultado contra la spec viva.

La documentación viva vive en el repo. El diagrama, el contrato de la API y el README se generan del código. El ADR se decide y se escribe una vez. Lo que se genera se regenera en CI. El ancla de todo es la spec viva. Mientras esté al día, lo que cuelga de ella también.

En el proyecto queda una matriz que dice qué criterio tiene prueba y cuál no. Y las fallas que el revisor cazó con la suite en verde, corregidas y con su prueba agregada.

Si programas, lo nuevo no es escribir pruebas. Es cruzar cada criterio con la suya y dejar de tratar "la suite pasa" como respuesta. Y tienes una pieza que armas hoy: un revisor con permisos recortados y un encargo escrito para refutar, no para aprobar.

Si vienes de producto, el criterio de aceptación que escribes es lo que aquí se comprueba. Uno vago no se puede verificar ni a mano ni con IA. Pide evidencia: archivo, línea y regla rota. No un "lo revisé". Exige que el porqué de cada decisión quede escrito. Es el único documento que no se puede sacar del código.

Si no programas, "está en verde" es una afirmación sobre lo que alguien decidió probar. No sobre lo que se pidió. El movimiento de fondo es separar a quien construye de quien critica.

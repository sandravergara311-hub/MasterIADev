Módulo 5 · Lección 6 — Ejercicio: audita las reglas que escribiste

Texto original: original/modulo-5/6.md
Obligatoria. Fecha límite: martes 27 de octubre de 2026, al final del día.
Repositorio: FlowSync.

En una frase

El entregable que importa son tres líneas honestas, no una tabla completa. La tabla dice, regla por regla, si las reglas de proceso de FlowSync se cumplen en los últimos 15 commits.

Leerla son once minutos. Hacerla lleva más. No la dejes para la noche anterior.

Se organiza en cuatro partes. Cómo funciona el módulo. El ambiente. La tarea, que es la que más tiempo lleva. Cómo entregar.

Caso real, y después el proyecto del curso

En la Farmacia Sol, Lucía tenía escrita la regla de crear una rama antes de tocar código. Se cumplió durante semanas. Cuando cambió el modelo, dejó de cumplirse y nadie lo notó. Este ejercicio hace ese mismo gesto sobre FlowSync: contrastar las reglas de proceso con el historial, en lugar de darlas por cumplidas.

Cómo aprovechar el módulo

  1. Lo intentas tú, sobre el proyecto, con tu agente y con el reloj. Entregas lo que salga, tal como esté. No pasa nada si queda a medias. Este paso no se puntúa por completarlo.
  2. Lo ves en la clase en vivo, sin escribir. El mentor hace esta misma auditoría, sobre este mismo proyecto. Si no te salió, ahí ves que se puede y cómo.
  3. Lo repites con los pedidos (prompts) escritos del mentor. Vuelves a tu ambiente y rehaces el recorrido. Ahí es donde se asienta.

Cuando repitas el recorrido, los resultados no serán exactamente iguales. No es una falla tuya. El agente no produce el mismo resultado dos veces. Con el mismo prompt y el mismo repositorio pueden cambiar la redacción, el orden de las filas y hasta cuántas devuelve. Se repite la forma del recorrido, no el texto.

Deja el ambiente listo

El proyecto funciona en macOS, en Linux y en Windows a través de WSL. En PowerShell no. Los atajos del Makefile están escritos para macOS y Linux.

Si trabajas en Windows, haz el clon, Node y make dentro de la terminal de WSL. WSL es un ambiente separado. Lo que tengas instalado en Windows no está disponible dentro de él, y lo que instales dentro no afecta a Windows. Clona en tu carpeta de Linux (~/…), no en /mnt/c. Desde ahí npm install va muy lento. Si no tienes WSL: wsl --install desde PowerShell como administrador.

1. Node.js 24 o superior

node -v tiene que responder v24 o más. Con la 20 el proyecto no arranca. make setup se detiene con Unknown file extension ".ts". Con la 22 arranca y avisa EBADENGINE, porque el proyecto pide la 24. La LTS de nodejs.org/en/download cumple.

2. make

make --version tiene que responder. Si no: en macOS, xcode-select --install. En Linux y en WSL, sudo apt install make.

3. Tu fork, en la rama de partida

Necesitas el proyecto en la rama s5/start, sobre tu propio fork de github.com/LIDR-academy/flowsync-ai4devs-202609-1. Si clonas el repo del curso tal cual, no tendrás permiso de push.

# 1. Fork desde la web: botón "Fork" en github.com/LIDR-academy/flowsync-ai4devs-202609-1

# 2a. Si AÚN NO has clonado: clona TU fork (no el del curso)
git clone git@github.com:<tu-usuario>/flowsync-ai4devs-202609-1.git
cd flowsync-ai4devs
git remote add upstream git@github.com:LIDR-academy/flowsync-ai4devs-202609-1.git

# 2b. Si YA clonaste el del curso: no vuelvas a clonar, recoloca los remotos
git remote rename origin upstream
git remote add origin git@github.com:<tu-usuario>/flowsync-ai4devs-202609-1.git

# 2c. Si ya venías trabajando sobre tu fork: solo comprueba que están los dos
git remote -v          # origin = TU fork · upstream = el repo del curso

# 3. Trae las ramas nuevas del curso y colócate en la de este módulo
git fetch upstream
git checkout -b s5/start upstream/s5/start

# 4. Comprueba que el fork quedó bien montado: esto tiene que funcionar
git push -u origin s5/start

Un fork es una foto del momento. El curso sigue publicando ramas. Las que todavía no se publicaron no existen en tu fork, y tu fork no se actualiza solo. Por eso el git fetch upstream va antes del checkout. Si el comando responde pathspec did not match, casi siempre es porque esa rama todavía no existe en tu fork. O no se ha publicado aún, o te faltó el git fetch upstream. Si responde 'upstream' does not appear to be a git repository, falta el git remote add del paso 2. Si el push del paso 4 te rechaza por permisos, origin sigue apuntando al repo del curso. Vuelve al 2b.

Si sale Permission denied (publickey), es SSH, no el fork. Los comandos de arriba usan direcciones git@github.com:…. Necesitan una clave subida a tu cuenta. Súbela, o cambia las direcciones por HTTPS (https://github.com/<tu-usuario>/flowsync-ai4devs.git y https://github.com/LIDR-academy/flowsync-ai4devs.git).

4. El proyecto enciende

Desde la raíz. Conviene hacerlo hoy. Descubrir que algo no compila con la clase empezada es el peor momento.

make setup   # solo la primera vez
make start   # backend en el puerto 3333 y frontend en el 5173

make start ocupa la terminal. Ctrl-C detiene los dos. Si uno se cae, se lleva al otro. make solo lista los atajos. En otra terminal, curl -s localhost:3333/ tiene que devolver {"hello":"world"}. http://localhost:5173 tiene que mostrar FlowSync. El frontend espera el backend en http://localhost:3333. Si lo arrancas en otro puerto, actualiza VITE_API_URL en frontend/.env.

Fallas típicas: make no existe. Node anterior a la 22 (Unknown file extension ".ts"). Te saltaste make setup. El puerto 3333 o el 5173 ya está ocupado.

Sin make, a mano. npm install dentro de backend/ y de frontend/. Copia .env.example a .env en cada una. Desde backend/, node ace generate:key y después node ace migration:run. Arranca cada parte con npm run dev, en dos terminales.

5. La suite corre y sale en verde

Desde backend/, ejecuta npm test. Si estás en la raíz, usa (cd backend && npm test). Los paréntesis hacen que vuelvas a la raíz al terminar. Todas las pruebas tienen que pasar. Si alguna falla, resuélvelo antes de la clase en vivo.

6. Abre las reglas de proceso

El archivo es CLAUDE.md, en la raíz del proyecto. Busca la sección con las reglas de proceso. Ahí se indica qué hacer antes de modificar código, cuándo crear commits y qué debe hacerse al cerrar el trabajo.

Léelas completas. No hace falta memorizar cada detalle. Lo importante es saber dónde están y qué tipo de instrucciones contienen. Forman parte de la tarea.

7. El agente puede consultar el historial

Abre Claude Code en el proyecto y pídele que resuma los últimos commits. Si no puede ejecutar comandos de Git, resuelve ese acceso antes de la clase en vivo. Parte de la sesión depende de que pueda consultar el historial.

8. Crea tu rama

git checkout -b auditoria-<tus-iniciales>

Todo lo que produzcas va en esa rama.

La tarea

Guarda cada prompt tal como lo envías, desde el primero. Se entregan junto con la tabla. No los reconstruyas después. Los cambios que harías al revisarlos también forman parte de lo que se quiere analizar.

El entregable no es la tabla. Son las tres líneas de la parte B. Puedes escribirlas aunque la tabla todavía no esté completa.

El resultado no depende de ti. Lo determina el historial del repositorio. Puede mostrar que varias reglas se incumplen, que muchas no se pueden comprobar o que todas se cumplen. Cualquiera de esos resultados es válido. Lo importante es que puedas justificarlo con evidencia.

Si todas las reglas se cumplen, la pregunta sigue siendo útil. ¿Lo sabías antes de revisar el historial, o lo dabas por hecho?

Vas a auditar las reglas de proceso que localizaste en el paso 6. Para comprobar si se cumplen, contrástalas con los últimos 15 commits del mismo repositorio. Es la misma auditoría que hará el mentor en la clase en vivo. Aquí la intentas antes, con tus propios prompts.

Reserva unos 45 minutos y usa un temporizador. Cuando se acabe el tiempo, detente aunque la tabla no esté completa. La tarea también muestra qué puedes comprobar con evidencia dentro de un tiempo limitado.

Parte A. La auditoría, con reloj

Antes de empezar, registra tu expectativa.

Abre el archivo de instrucciones del agente y localiza las reglas de proceso. Son las que indican qué hacer antes de modificar código, cuándo crear commits y qué debe hacerse al cerrar el trabajo.

Sin comprobar todavía el historial, marca cuáles crees que se están cumpliendo. Basta una palabra por regla: sí, no o ni idea.

Te lleva unos treinta segundos. El objetivo es dejar constancia de lo que pensabas antes de revisar la evidencia. Así podrás comparar tu expectativa con lo que muestra el historial.

La tabla.

Con ayuda del agente, contrasta las reglas con los últimos 15 commits del repositorio y el estado actual de los archivos del proyecto. Guarda el resultado en docs/auditoria/<tus-iniciales>.md, no en el chat.

Una fila por regla. Cinco columnas:

  • Qué pide la regla. Resúmela en una frase, con tus palabras. Si necesitas varias frases, puede que estés mezclando más de una regla.
  • Qué se revisó para comprobarla. El comando ejecutado o el archivo consultado. Sin esto no hay forma de saber en qué se apoya el veredicto.
  • Veredicto. Solo puede ser se cumple, no se cumple o no se puede comprobar con la información disponible. Este último también es un resultado válido. Significa que la regla no deja suficiente evidencia para verificarla.
  • Evidencia. Una línea. Si la regla no se cumple, indica dónde se incumple. Si no se puede comprobar, explica qué información falta.
  • Qué harías con ella. Una opción: dejarla, borrarla o convertirla en una comprobación automática.

Esto es una auditoría, no una corrección. Indícale al agente que no modifique ningún archivo. Si empieza a corregir lo que encuentra, cambia el estado que estás analizando y pierdes parte de la evidencia original.

Cuando termine el tiempo, detente aunque la tabla esté incompleta. No completes después las filas de memoria. Una fila parcial también aporta información, porque muestra hasta dónde llegaste. Completarla después sin volver a comprobar la evidencia puede hacer que el resultado parezca más sólido de lo que es.

Parte B. Las tres líneas

Van debajo de la tabla, en el mismo archivo. Esta parte es obligatoria y debe estar completa.

  1. La regla en la que más te equivocaste. Compara tu expectativa inicial con el veredicto final y elige la que más se alejó de lo que pensabas. Si acertaste todas, indícalo y explica en una frase en qué te apoyaste. Si solo era una impresión, déjalo escrito.
  2. Una regla que no se puede comprobar con la información disponible. Explica en una frase qué tendría que cambiar para poder verificarla. Puede ser reformularla, convertirla en una comprobación automática o aceptar que no deja una evidencia clara.
  3. La regla que eliminarías y por qué. Hay dos casos habituales. Una regla que ya garantiza otra herramienta. O una que nadie sigue y que tampoco aporta valor. Elige una y explica a cuál de los dos casos pertenece.

No hay una respuesta correcta para estas tres líneas. Lo importante es que reflejen lo que descubriste, incluso si contradice lo que esperabas al empezar.

Cómo saber que quedó bien

  • Tu expectativa está escrita antes que la tabla y no la cambiaste después de ver el resultado.
  • Las tres líneas están completas y son concretas.
  • Comprobaste por tu cuenta la evidencia de al menos una fila, revisando el historial y no solo el resumen del agente.
  • No hay archivos modificados aparte del tuyo. Si los hay, el agente cambió el estado que estabas auditando y el resultado deja de reflejar el punto de partida.
  • La tabla sigue siendo breve y fácil de revisar. Si creció demasiado, comprueba que no hayas incluido cosas que no sean reglas de proceso.
  • Entrégalo tal como esté cuando termine el tiempo.

Cómo se entrega

Todo queda en la rama que creaste al preparar el ambiente.

Un pull request desde tu fork, con solo estos dos archivos:

  • Tu archivo de auditoría, docs/auditoria/<tus-iniciales>.md, con la tabla y las tres líneas. El directorio se crea al añadir el archivo.
  • prompts.md, en la raíz. El archivo ya contiene la plantilla que debes completar.
git add docs/auditoria prompts.md
git commit -m "auditoria: reglas de proceso + prompts"
git push -u origin auditoria-<tus-iniciales>

El pull request va contra el repositorio del curso, no contra tu fork.

prompts.md forma parte de la revisión. No se mira solo el resultado de la auditoría. También cómo se lo pediste al agente. Dos resultados parecidos pueden tener causas distintas si uno parte de un prompt claro y otro de uno demasiado vago. Guarda los prompts tal cual, con el modelo y la herramienta. Incluye también los que no funcionaron.

Lo que llegue antes de la clase recibe comentarios de tu TA. Ahí es cuando te sirve. Llegas sabiendo qué revisar y aprovechas la clase en vivo buscando exactamente eso. Si llegas tarde, el pull request queda registrado y no recibe comentarios.

Si vas justo de tiempo

Prioriza dos lecciones de este módulo: la diferencia entre una regla escrita y un guardarraíl que se ejecuta, y qué se puede automatizar y qué solo lo parece. Son las que necesitas para entender el resto.

Las otras dos se pueden seguir durante la clase en vivo.

El material de apoyo está en la lección de recursos y es opcional.

Antes de conectarte

  • Estás en la rama de trabajo de tu fork y git push funciona.
  • El backend y el frontend encienden.
  • La suite se ejecuta y todas las pruebas pasan.
  • Sabes dónde están las reglas de proceso en el archivo de instrucciones del agente y las leíste.
  • Tu agente puede ejecutar comandos de Git y consultar el historial.

Qué te llevas del módulo

Una regla escrita en un archivo es un pedido, no una garantía. Puede cumplirse tanto tiempo que dejes de comprobarla. Cada regla se coloca según cómo falla. Si puede fallar en silencio, conviene moverla a una capa que la ejecute y la verifique.

Automatizar la generación de algo no significa automatizar su utilidad. Muchas veces, lo primero que compensa automatizar es lo más repetitivo: comprobar que lo generado sigue coincidiendo con su fuente.

Un agente puede revisar cambios sin que nadie lo llame. Su utilidad no depende solo del modelo. También importa dónde aparecen los hallazgos, quién los revisa y quién toma la decisión final.

Un guardarraíl también puede dejar de ser útil aunque acierte. Si genera demasiados avisos poco relevantes, el equipo termina ignorándolos. Conviene calcular su costo por ejecución y observar cuántos hallazgos terminan provocando cambios reales.

En el proyecto queda una auditoría de sus reglas de proceso. Muestra cuáles se cumplen, cuáles no y cuáles no se pueden comprobar.

También queda una comprobación automática y repetible que verifica que el contrato versionado de la API sigue coincidiendo con el código. Y se comprueba que puede fallar cuando existe una diferencia, en lugar de asumir que funciona solo porque aparece en verde.

Los trabajos de integración continua ejecutan esa comprobación y activan el revisor automático cuando se propone un cambio.

Por último, queda un archivo de calibración. Define qué se considera grave y cuántas sugerencias menores puede generar el agente. Junto a eso, el informe de la primera revisión automática y los problemas que detectó por sí solo.

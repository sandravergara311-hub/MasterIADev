Módulo 7 · Lección 5 — Un cambio que cruza dos repositorios no es un solo cambio

Texto original: original/modulo-7/5.md
Obligatoria. Léela antes de la clase en vivo.

En una frase

Git no integra dos repositorios a la vez. Para cambiar el formato de un dato sin romper el sistema, hace falta una ventana de compatibilidad: ofrecer lo nuevo antes de retirar lo viejo, con fecha de cierre y evidencia.

Palabras que vas a escuchar

  • Productor y consumidor. El productor proporciona el dato. El consumidor lo utiliza. En el colegio, el servicio de noticias es el productor y el buscador es el consumidor.
  • Publicación o release. Poner a disposición una versión nueva. Cada servicio tiene su propio ciclo.
  • Ventana de compatibilidad. El periodo en el que se mantiene el formato anterior mientras se adopta el nuevo. Puede exigir que el productor ofrezca ambos formatos, o que el consumidor sepa interpretar los dos, según el orden de actualización.
  • Cambio incompatible. Una modificación que rompe el funcionamiento de un consumidor existente si este no se adapta. Sustituir una cadena de texto por un objeto en el mismo campo puede provocar ese fallo.

Caso real: el autor deja de ser un texto

El servicio de noticias del Colegio Los Álamos devuelve las notas con un campo autor que contiene el nombre como una cadena de texto. El buscador, en otro repositorio, consume ese campo y lo guarda para mostrarlo en los resultados.

Ahora se necesita enlazar a la página del autor. Se decide convertir autor en un objeto con nombre y slug.

Cada repositorio tiene su propio ciclo de publicación. Integrar uno de los cambios no garantiza que el otro también se haya integrado o desplegado.

Si el servicio de noticias empieza a devolver autor como un objeto mientras el buscador todavía espera una cadena de texto, el buscador puede dejar de procesar los datos.

La ventana

En un solo repositorio, un PR permite integrar juntas las modificaciones de quien proporciona los datos y de quien los utiliza. La integración es conjunta. Eso no garantiza que ambos servicios se desplieguen al mismo tiempo.

Con dos repositorios, los cambios se integran por separado. Aceptar el PR del servicio de noticias no integra el del buscador. Los despliegues también son independientes.

Para evitar el corte, se establece una ventana de compatibilidad.

  1. Primero se actualiza el buscador para que pueda interpretar tanto la cadena de texto como el objeto.
  2. Después, el servicio de noticias empieza a devolver el formato nuevo.
  3. Cuando se comprueba que los datos almacenados y los servicios que los consumen ya utilizan el objeto, se retira el soporte para la cadena de texto.

Así, cada servicio puede actualizarse por separado sin romper el contrato durante la transición. La ventana debe tener un inicio y un criterio de cierre, para que el soporte del formato anterior no se mantenga indefinidamente.

Los pasos no son lo difícil. Lo difícil es seguir el orden. Ofrecer el formato nuevo de autor sin retirar el anterior hasta que todos los consumidores hayan migrado. Mantener ambos un tiempo va contra el impulso de dejar el código limpio.

En cada paso importa qué es cierto del sistema en ese momento, no solo qué archivo tocaste. Durante el primer paso, el sistema ofrece dos formatos del mismo dato. Durante el tercero, sigue ofreciendo uno que los consumidores ya han dejado de usar. Ambos estados son correctos, transitorios y deliberados. Hay que documentarlos para que quien los encuentre entienda que forman parte de la migración y no los confunda con una falla.

El paso que suele faltar en los planes es el cuarto. Comprobar con evidencia que ningún consumidor utiliza ya el formato anterior. Que el buscador haya migrado no basta para retirarlo. Otros servicios o aplicaciones pueden seguir dependiendo del campo de texto, incluidos consumidores que el equipo haya perdido de vista con los años.

Retirar lo viejo también se planifica

El último paso puede romper producción si todavía queda algún consumidor del formato anterior. También suele aplazarse, porque retirar lo viejo no añade ninguna función.

Los cuatro primeros pasos tienen una necesidad inmediata. Permiten completar el cambio. El quinto puede esperar porque el sistema sigue funcionando sin él. Así, una ventana prevista para dos semanas puede acabar abierta durante dos años.

Mantenerla tiene un costo. Hay que seguir ofreciendo el formato anterior, probarlo y explicar por qué sigue ahí. Si se acumulan varias migraciones sin cerrar, un servicio puede terminar manteniendo tres versiones de un campo. Después, nadie se atreve a retirar ninguna porque no está claro quién utiliza cada una.

Para evitarlo, define la fecha de cierre al abrir la ventana, junto con la evidencia necesaria para retirar el formato anterior. Si esa evidencia no llega, revisa el plazo antes de eliminarlo.

Las specs del productor y del consumidor describen el comportamiento esperado al terminar la migración. Uno ofrece el campo nuevo y el otro lo utiliza. Esos estados finales no explican solos cómo pasar de la versión actual a la nueva sin romper la compatibilidad.

Durante la transición hay estados intermedios deliberados. Se ofrecen ambos formatos. Algunos consumidores ya migraron y otros todavía no. Esa convivencia también debe quedar documentada.

El plan del cambio recoge qué formato se ofrece en cada paso, en qué orden se actualizan los servicios, cuándo se retirará el anterior y qué evidencia permite hacerlo. Las specs describen el resultado. El plan explica cómo llegar a él.

La frecuencia mide el acoplamiento

Este procedimiento exige cinco pasos, cambios en dos repositorios, coordinación y seguimiento de una fecha de cierre. Para una migración ocasional, ese costo puede compensar las ventajas de desplegar cada servicio por separado.

Si necesitas coordinar una migración así cada semana, revisa el acoplamiento entre los servicios y si la separación entre repositorios sigue siendo adecuada.

Si cada cambio en el servicio de noticias exige modificar también el buscador y coordinar ambos despliegues, los dos servicios apenas pueden evolucionar por separado. El equipo mantiene dos repositorios y dos ciclos de publicación, y sigue necesitando trabajar sobre ambos para completar cada cambio. Conviene revisar cómo se reparten las responsabilidades y el contrato, para entender por qué necesitan cambiar juntos con tanta frecuencia.

Qué hacer

  • No cuentes con una integración atómica entre dos repositorios. Planifica una ventana de compatibilidad para que los servicios puedan actualizarse por separado.
  • Ofrece el formato nuevo antes de retirar el anterior.
  • Documenta la ventana en el plan del cambio. Indica qué formato se ofrece en cada paso, hasta cuándo y qué evidencia permite retirar el anterior. Las specs del estado final no describen solas esa transición.
  • Define la fecha de cierre al abrir la ventana. Si no se cumplen las condiciones para cerrarla, revisa el plazo. No retires el formato anterior sin comprobar su uso.
  • Usa la frecuencia de estas migraciones para evaluar el acoplamiento. Los cambios coordinados ocasionales son esperables. Si se repiten cada semana, revisa las responsabilidades y el contrato entre los servicios.

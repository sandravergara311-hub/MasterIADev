Repositorio: Blog Legacy.

En una frase

El entregable que importa son tres líneas honestas, no una lista ordenada. La lista audita solo la funcionalidad de comentarios del blog heredado, con un criterio que otra persona podría repetir.

Leerla son diez minutos. Hacerla, cerca de una hora. Todo lo que hay que traer a la clase en vivo está aquí, y solo aquí.

Cuatro partes. Cómo funciona el módulo. El ambiente. La tarea. Cómo se entrega.

Caso real, y después el proyecto del curso

En el Diario La Esquina, Camila no puede responder de memoria qué se rompe si quita el correo del autor de una respuesta. Este ejercicio hace ese mismo gesto sobre un blog que no escribiste: auditar solo los comentarios, comprobar cada fila y ordenarla sin que el orden sea un gusto.

Cómo aprovechar el módulo

  1. Lo intentas tú, sobre el proyecto de abajo, con tu agente y con el reloj. Entregas lo que salga, con lo que tenga. La entrega a medias no es un problema. Este paso no se puntúa por completarlo.
  2. Lo ves en la clase en vivo, sin escribir. El mentor ejecuta esta misma auditoría, sobre este mismo proyecto. Si no te salió, ahí ves que se puede y cómo.
  3. Lo repites con los pedidos (prompts) escritos del mentor. Vuelves a tu ambiente y rehaces el recorrido. Ahí es donde se asienta.

En el paso 3 no esperes salidas idénticas. No es una falla tuya. El agente no es determinista. Con el mismo prompt y el mismo código cambian los nombres de las variables, la redacción y hasta cuántos hallazgos devuelve. Se repite la forma del recorrido, no el texto.

Deja el ambiente listo

Todo lo necesario para levantar el proyecto está aquí, en orden. Esta lección y el README.md del repositorio cuentan lo mismo. Con leer una de las dos basta.

1. Comprueba lo que necesita tu máquina

Funciona en macOS y en Linux, tal cual. En Windows, dentro de WSL, y no en PowerShell. Los atajos del proyecto están escritos para la terminal de macOS y Linux. Usan cp, test y rm. En PowerShell fallan aunque consigas instalar make.

Si trabajas en Windows, haz todo lo de esta lección dentro de la terminal de Ubuntu de WSL: el clon, Node y make. Lo que tengas instalado en Windows no existe dentro de WSL, y al revés. Un node -v que responde en PowerShell no dice nada sobre WSL. Si no tienes WSL: wsl --install desde PowerShell como administrador.

Tres comprobaciones, en la terminal donde vas a trabajar.

Node.js 24 o superior. node -v tiene que responder v24 o más. Con la 20 el proyecto no arranca. make setup se detiene con Unknown file extension ".ts". Con la 22 arranca y llena la pantalla de avisos EBADENGINE, porque el proyecto pide la 24. La LTS de nodejs.org/en/download cumple.

make. make --version tiene que responder con un número. Si no: en macOS, xcode-select --install. En Linux y en WSL con Ubuntu, sudo apt install make.

git y Claude Code. Git con acceso a GitHub, por SSH o por HTTPS. Claude Code instalado y con sesión iniciada. claude --version responde.

2. Haz fork y clona

Es un blog pequeño con posts, autores, categorías, etiquetas y comentarios. Es un monorepo, con la API y la web dentro.

Haz fork de github.com/LIDR-academy-temp/blog-legacy-ai4devs-202609-1 con el botón Fork, y clona tu fork. Sobre un clon del repositorio del curso no tienes permiso de escritura. Aquí vas a crear una rama y confirmar cambios.

# 1. Clona TU fork
git clone git@github.com:<tu-usuario>/blog-legacy-ai4devs-202609-1.git
cd blog-legacy-ai4devs

# 2. Añade el repositorio del curso como "upstream"
git remote add upstream git@github.com:LIDR-academy-temp/blog-legacy-ai4devs-202609-1.git
git fetch upstream

# 3. Sitúate en la rama de partida, traída del curso
git checkout -b s6/start upstream/s6/start

La rama de partida se trae del curso, no de tu fork. Un fork es una foto del momento. Además, el formulario de Fork de GitHub trae marcada la casilla de copiar solo la rama por defecto. Si la dejas así, tu copia se lleva main y nada más. Trayéndola de upstream funciona en los dos casos, hayas marcado lo que hayas marcado. Si git checkout responde error: pathspec … did not match, te saltaste el git remote add upstream.

Si sale Permission denied (publickey), es SSH, no el fork. Es el fallo más común de este paso y no tiene que ver con los permisos del repositorio. La guía oficial está en docs.github.com/es/authentication/connecting-to-github-with-ssh.

3. Instálalo y enciéndelo

Este proyecto no tiene package.json en la raíz. La API vive en backend/. La web vive en frontend/. El Makefile de la raíz ya invoca los comandos de cada una. Si escribes make solo, lista todos los atajos.

En una primera terminal, desde la raíz y en este orden:

make setup    # instala las dependencias de la API y de la web, y prepara backend/.env
make db       # crea la base de datos SQLite y la siembra con los datos de ejemplo
make api      # levanta la API en http://localhost:3401 y se queda corriendo

make api ocupa la terminal. No la cierres.

En una segunda terminal, también desde la raíz:

make web      # levanta la web en http://localhost:5401 y se queda corriendo

Comprueba las dos antes de seguir. La tarea las necesita vivas.

  • La API: curl -s localhost:3401/posts en una tercera terminal tiene que devolver una lista de posts en JSON.
  • La web: abre http://localhost:5401 en el navegador y entra en un post. Al final de la página están sus comentarios. Esa es la parte del blog que vas a auditar.

Los dos puertos son fijos. La web busca la API exactamente en el 3401. No sirve levantarla en otro.

Fallas típicas:

  • make: command not found. Falta make. Vuelve al paso 1.
  • Unknown file extension ".ts" durante make setup. Tu Node es anterior a la 22. Instala la 24 y repite make setup.
  • make api o make web dicen que el puerto está en uso. Tienes algo corriendo en el 3401 o en el 5401, casi siempre una ejecución anterior de este mismo proyecto. Ciérrala y vuelve a lanzar.
  • El curl no devuelve nada, o la web carga sin posts. Falta make db, o se cerró la terminal de make api.

4. Corre la suite y anota lo que salga

make test

Apunta el resultado tal como salga, incluido lo que esté en rojo. No lo arregles.

Ese apunte es tu punto de partida. La única forma honesta de saber si un cambio empeora algo es comparar contra lo que ya pasaba antes, no contra un ideal.

5. El agente puede trabajar aquí

Abre tu sesión de Claude Code en el proyecto y pídele dos cosas. Que te resuma los últimos commits. Y que busque en qué archivos aparece una palabra cualquiera del dominio. Si no puede ejecutar git o no puede buscar por el proyecto, resuélvelo antes. Sin eso no se audita nada.

6. Crea tu rama

git checkout -b auditoria-<tus-iniciales>

Ahí va todo lo que produzcas. El directorio docs/auditoria/ ya existe. Ahí va el archivo de la tarea, y ahí se queda. Una auditoría es un artefacto versionado, no una conversación.

La tarea

Son unos 45 minutos y hay que ponerles un reloj. Lee el encuadre entero antes de empezar. El entregable no es el que parece.

El entregable no es la lista ordenada. Son las tres líneas de la parte B. Esas se escriben igual de bien con la lista a medias.

Si terminas con una lista ordenada y estás seguro del orden, vuelve a mirarla. Casi nadie lo está en la primera pasada, y el motivo no es la herramienta.

El reloj tampoco es un castigo. En una auditoría real tampoco te dan tiempo infinito. Te dan la tarde que hay antes de la reunión. Lo que sale en 45 minutos es la parte que depende de tener criterio, no la que depende de tener una herramienta mejor.

Ve guardando cada prompt tal como lo lanzas, desde el primero. Se entregan junto con la tabla. No sirven reconstruidos. El prompt que arreglas mentalmente diez minutos después no es el que lanzaste, y es justo la diferencia que interesa mirar.

Parte A. La auditoría

Con un agente, produce la auditoría priorizada de la funcionalidad de comentarios y déjala escrita en docs/auditoria/comentarios.md, no en el chat.

Una funcionalidad del blog es de punta a punta: sus rutas en la API, su tabla en la base de datos y lo que la web enseña de ella. Este blog tiene cinco: posts, comentarios, autores, categorías y etiquetas. La tuya es comentarios: crear, editar, borrar y listar, en esas tres capas. Es la misma que audita el mentor en la clase en vivo.

Solo esa funcionalidad. No el sistema entero, aunque quepa y aunque el agente se ofrezca.

El orden usa el mismo criterio que el mentor. Primero la precedencia: lo que abarata o desbloquea a otro hallazgo va antes. Dentro de cada nivel, el daño dividido por el radio. Si un hallazgo tiene el daño más alto y la precedencia más baja a la vez, se parte en dos filas. Una contención que corta el daño hoy, y el arreglo de fondo que espera su turno. Las propuestas que nadie ha medido todavía van fuera de la tabla, con lo que habría que medir escrito al lado.

El formato no se negocia. Una fila por hallazgo, con estas seis casillas.

  • Qué es. Una frase. Si necesitas tres, es que hay dos hallazgos.
  • Dónde está, con la línea que lo demuestra. Sin esta casilla, la fila no se escribe.
  • Qué se rompe, y quién lo nota. El efecto concreto y a quién le llega. «Nadie todavía» es una respuesta válida y buena.
  • Cuántos sitios hay que tocar. Contados, no estimados.
  • ¿Se deshace con un revert? Sí o no. Si es que no, por qué no.
  • ¿Bloquea o desbloquea a otro hallazgo? Nombrando al otro. «A ninguno» es la respuesta más frecuente.

Cuando suene el reloj, paras. Aunque esté a medias. Aunque falten filas, aunque haya casillas en blanco, aunque justo ibas a comprobar una cosa.

Una fila con tres casillas llenas y tres en blanco es información. Dice exactamente hasta dónde llegaste. Una fila completada de memoria diez minutos después es ruido con formato, y encima no se distingue de la buena.

Parte B. Las tres líneas

Van debajo de la tabla, en el mismo archivo. Esta parte no se puede fallar. Es la que hay que traer sí o sí.

  1. Cuántos hallazgos devolvió el agente, y cuántos comprobaste tú abriendo el archivo. Los dos números, tal como salieron. No los redondees ni los expliques.
  2. El hallazgo del que no supiste decidir la prioridad, y en una frase, por qué. Lo que interesa es qué dos cosas se contradecían. Lo grave contra lo que bloquea. Lo urgente contra lo caro. Lo que te pedían contra lo que veías.
  3. Algo que el agente afirmó y no pudiste verificar. El matiz importa. No es lo que dijo mal. Es lo que no pudiste comprobar ni a favor ni en contra, y te tocó dejar en el aire.

Ninguna de las tres tiene respuesta correcta. La segunda y la tercera sirven más cuanto más incómodas sean. Un «no supe decidir entre estos dos», dicho con honestidad, pesa más que una lista ordenada con seguridad fingida.

Cómo saber que quedó bien

  • Las tres líneas están escritas y son concretas. Si la tercera dice «nada, todo era verificable», vuelve a mirar. Es la respuesta de quien comprobó leyendo el hallazgo en vez de abriendo el archivo.
  • El número de comprobados es menor que el de devueltos. Casi siempre lo es, y eso no es una falla tuya. Es el dato.
  • Hay al menos una casilla en blanco. Significa que respetaste el reloj y que no llenaste de memoria.
  • La tabla cabe en una pantalla. Si no cabe, te saliste de comentarios y estás auditando el sistema entero otra vez.

Cómo se entrega

Un pull request desde tu fork, con dos cosas dentro y nada más.

  • Tu archivo de auditoría en docs/auditoria/, con la tabla y las tres líneas.
  • prompts.md, en la raíz. Ya está ahí con la plantilla puesta.
git add docs/auditoria prompts.md
git commit -m "auditoria: comentarios + prompts"
git push -u origin auditoria-<tus-iniciales>

El pull request va contra el repositorio del curso, no contra tu fork.

prompts.md es la mitad de lo que se revisa. No se mira solo lo que te salió. Se mira cómo lo pediste. Un resultado flojo con un prompt bueno y un resultado flojo con un prompt vago necesitan respuestas distintas. Sin ese archivo no se distinguen. Pega los prompts tal cual, con su modelo y su herramienta. Incluye también los que no funcionaron. Suelen ser los más útiles de leer.

Lo que llegue antes de la clase recibe comentarios de tu TA. Ahí es cuando te sirve. Llegas sabiendo dónde fallaste y miras la sesión buscando eso. Lo que llegue después se marca como recibido y ya no se revisa.

Entrégalo con lo que tenga, y sin maquillarlo. Lo que le falta es la mitad de lo interesante.

Si vas justo de tiempo

Prioriza la lección de cómo se ordena una auditoría sin que el orden sea arbitrario. Es el andamiaje de todo lo demás. Y la que trata por qué el cuello de una auditoría es comprobar y no encontrar. Las otras dos se siguen sobre la marcha.

El material de apoyo está en la lección de recursos y es opcional.

Antes de conectarte

  • Estás en la rama de partida, sobre tu fork, y git push funciona.
  • node -v responde v24 o más, y make --version responde, en la terminal donde trabajas. En Windows, la de WSL.
  • Corrieron make setup, make db, make api y make web. curl -s localhost:3401/posts devuelve datos y http://localhost:5401 enseña el blog.
  • Ejecutaste make test una vez y tienes anotado lo que salió, en verde o en rojo.
  • Tu agente puede ejecutar comandos de git y buscar por todo el proyecto.
  • Traes el archivo de la tarea, con su tabla aunque esté a medias y sus tres líneas.
  • prompts.md está lleno, con modelo y herramienta en cada bloque.
  • El pull request está abierto.

Si quieres llevártelo al trabajo

Cuando hayas hecho el paso 3, repite el recorrido sobre un proyecto tuyo de verdad. Uno del trabajo, que lleve años en marcha y que no escribieras tú entero. No hace falta que sea grande. Hace falta que sea un sistema sobre el que no puedas responder de memoria «si cambio esto, qué se rompe».

Eso es opcional y no se entrega. Ahí esto deja de ser un ejercicio. Los prompts son los mismos.

Qué te llevas del módulo

Heredado no es viejo. Es lo que nadie puede explicar. La medida útil no es un porcentaje de sector. Es cuánto tardas en responder, con evidencia que otro pueda comprobar, qué se rompe si tocas algo.

El cuello de una auditoría es comprobar, no encontrar. El presupuesto de verificación es el que manda. El tamaño de la lista es propiedad de cómo cortaste el trozo, no del sistema.

Lo más grave no va primero. Ordenar por gravedad produce retrabajo. Cuando el daño y la precedencia se contradicen, la salida es partir el hallazgo en contención y arreglo.

Un encargo de una línea no es vago. Es uno cuyo contexto vive escrito en el harness. En un sistema heredado hay que escribirlo a mano, porque el código dice de dónde viene y nunca hacia dónde va.

En el proyecto queda un archivo de auditoría versionado de una sola funcionalidad, la de comentarios. Una lista corta, comprobada una a una. Una fila por hallazgo, con dónde se demuestra, qué se rompe y quién lo nota, cuántos sitios hay que tocar, si lo deshace una vuelta atrás y a qué otro hallazgo bloquea. Las casillas que nadie pudo responder quedan en blanco a propósito. Las propuestas sin medir van fuera de la tabla, con su experimento escrito al lado. Debajo, las tres líneas: dónde se te acabó el tiempo, qué no supiste priorizar y qué no pudiste verificar.

También quedan pruebas de caracterización. Fijan el comportamiento de hoy, fallas incluidas, para poder cambiar algo sin descubrir por accidente qué dependía de ello.

Si programas, un agente encuentra y cuenta bien cuántos sitios toca cada hallazgo. Quién usa eso y qué hay alrededor lo pones tú. Antes de cambiar nada heredado, fija con pruebas lo que hace hoy, fallas incluidas.

Si vienes de producto, ahora te llega una lista de cuarenta cosas producida en cuatro minutos por algo que no sabe cuáles importan. Tu trabajo no es elegir las graves. Es preguntar, en cada una, cuántos sitios hay que tocar a la vez y qué tiene que ir antes. Esas dos respuestas deciden el calendario.

Si no vienes de tecnología, heredado no significa viejo. Significa que nadie lo puede explicar. Una casa antigua cuyos planos se perdieron. Y lo más grave no siempre va primero.

Módulo 3 · Lección 6 — Ejercicio: escribe la spec de lo que ya funciona

Texto original: original/modulo-3/6.md
Obligatoria. Fecha límite: lunes 5 de octubre de 2026, al final del día.
Repositorio: FlowSync.

En una frase

No propones nada y no cambias código. Lees cuentas y acceso, que ya funcionan, y escribes lo que el sistema hace hoy. El entregable que importa son tres listas, no la spec perfecta.

Leerla son unos doce minutos. Hacerla, unos 70. Diez de ambiente, quince de instalación y sandbox, 45 de la tarea. No la abras la noche anterior.

Este módulo instala una herramienta. Llega con OpenSpec instalado y funcionando. Si algo falla, avísale a tu TA antes. No lo dejes para el minuto 1 de la clase.

Caso real, y después el proyecto del curso

En el Taller Rueda, Elena ya vio la diferencia. Una spec de la lista de órdenes no es lo mismo que un delta de la fecha prometida. Este ejercicio es el otro gesto. Decir, en WHEN / THEN, lo que un código que ya funciona hace hoy.

Lo vas a hacer sobre FlowSync, no sobre el taller. La superficie es cuentas y acceso. Registro, inicio de sesión, sesión y perfil.

Cómo aprovechar el módulo

  1. Lo intentas tú, con reloj. Entregas lo que salga, aunque esté a medias. Este paso no se califica por terminarlo.
  2. Lo ves en la clase en vivo, sin escribir. El mentor hace este mismo ejercicio, sobre este mismo proyecto y sobre la misma superficie.
  3. Lo repites con los prompts escritos. El agente no da siempre el mismo texto. Cambian la redacción, el orden y hasta cuántos requisitos escribe. Se repite la forma, no el texto.

Deja el ambiente listo

Aquí dejas el ambiente y te familiarizas con OpenSpec en una carpeta desechable. No en el repo del proyecto. La tarea de más abajo no necesita OpenSpec instalado. La clase sí. Este paso no se salta.

1. Ambiente base (10 minutos)

El proyecto funciona en macOS, en Linux y en Windows dentro de WSL. En PowerShell no. Los atajos del Makefile están escritos para una terminal de Linux o de Mac.

Si trabajas en Windows, haz el clon, Node y make dentro de la terminal de Ubuntu de WSL. Lo que instales en Windows no existe dentro de WSL, y al revés. Clona en tu carpeta de Linux (~/…), no en /mnt/c. Desde ahí npm install va muy lento. Si no tienes WSL: wsl --install desde PowerShell como administrador.

  • Node.js 24 o superior. node -v responde v24 o más. Con la 20 el proyecto no arranca. make setup se detiene con Unknown file extension ".ts". Con la 22 arranca y avisa EBADENGINE, porque el proyecto pide la 24. La LTS de nodejs.org/en/download cumple. OpenSpec, que instalas en el paso 2, pide la 20.19. Con la 24 alcanzas para los dos.
  • make --version responde con un número. En macOS: xcode-select --install. En Linux y en Ubuntu dentro de WSL: sudo apt install make.
  • Trabaja sobre tu propio fork. Si GitHub te rechazó un push, no es un fallo tuyo. No tienes permiso de escritura sobre el repo del curso, y no deberías tenerlo.
# 1. Fork en https://github.com/LIDR-academy/flowsync-ai4devs-202609-1

# 2a. Si AÚN NO has clonado: clona tu fork
git clone git@github.com:<tu-usuario>/flowsync-ai4devs-202609-1.git
cd flowsync-ai4devs
git remote add upstream git@github.com:LIDR-academy/flowsync-ai4devs-202609-1.git

# 2b. Si YA clonaste el del curso: no vuelvas a clonar, solo recoloca los remotos
git remote rename origin upstream
git remote add origin git@github.com:<tu-usuario>/flowsync-ai4devs-202609-1.git

# 2c. Si YA clonaste tu propio fork: solo te falta el upstream
git remote add upstream git@github.com:LIDR-academy/flowsync-ai4devs-202609-1.git

# Comprueba: origin = tu fork, upstream = el del curso
git remote -v

# 3. Trae las ramas del curso y colócate en la de hoy
git fetch upstream
git checkout -b s3/start upstream/s3/start

# 4. A partir de aquí tus cambios van a TU fork
git push -u origin s3/start

Si sale Permission denied (publickey), es SSH, no el fork. Los comandos de arriba usan direcciones git@github.com:…. Necesitan una clave subida a tu cuenta. Súbela, o cambia las tres direcciones por HTTPS (https://github.com/<usuario>/flowsync-ai4devs.git). Lo que no sirve es descubrirlo el día de la clase.

Un fork es una foto del momento. El curso sigue publicando ramas. Las que todavía no se publicaron no existen en tu fork, y tu fork no se entera solo. Antes del trabajo de cada módulo, corre git fetch upstream y saca la rama nueva desde ahí (git checkout -b sN/start upstream/sN/start). Si un checkout responde pathspec did not match, casi siempre es esto. Se arregla con un fetch.

  • Rama s3/start en tu fork. Trae el harness del proyecto, el PRD y el backlog del equipo.
  • Abre docs/backlog/. Están las historias del equipo, repartidas en épicas, con sus criterios. Algunas traen además los tickets. Es el artefacto que dirige la implementación. Lo tienes entero en el repo.
  • Abre también docs/backlog/README.md y busca el orden priorizado. Mira cuál va primera y qué razón da el propio README para ponerla ahí.

El backlog trae más historias de las que se afinan en una clase. No te falta nada. Una demo enseña que algo es posible y cómo se hace. No produce delante de ti el inventario completo. Afinar un backlog entero en vivo serían horas de repetir el mismo gesto.

  • Claude Code arranca y lee tu contexto.
  • El proyecto enciende entero, backend y frontend, y puedes iniciar sesión en la interfaz. Desde la raíz. Compruébalo ahora.
make setup   # solo la primera vez
make start   # backend en el puerto 3333 y frontend en el 5173

make start ocupa la terminal. Ctrl-C detiene los dos. Si uno se cae, se lleva al otro. make solo lista los atajos. En otra terminal, curl -s localhost:3333/ devuelve {"hello":"world"}. http://localhost:5173 muestra FlowSync. El frontend busca el backend en http://localhost:3333. Si lo levantas en otro puerto, cambia VITE_API_URL en frontend/.env.

Fallas típicas: make no existe. Node anterior a la 22 (Unknown file extension ".ts"). Te saltaste make setup. El puerto 3333 o el 5173 ya está ocupado.

Sin make, a mano: npm install en backend/ y en frontend/. Copia cada .env.example a .env. En backend, node ace generate:key y node ace migration:run. Después, npm run dev en cada uno, en dos terminales.

Si vas a buscar las historias en un tablero, no las busques. Manda el repositorio. Las historias y sus tickets se crearon en su momento como issues en el tablero FLOW. Un tablero compartido se limpia entre sesiones. El propio backlog lo deja escrito en docs/backlog/README.md: las issues y subtareas vienen marcadas como "hay que recrearlas". Si el tablero y el repositorio se contradicen, manda el repositorio. Un tablero sirve para seguir el trabajo. Los criterios viven en el repo. Si quieres tu propio seguimiento en Jira, recréalos tú con el MCP que ya tienes conectado.

2. Instalar OpenSpec y mirarlo en un sandbox (15 minutos)

No lo inicialices en FlowSync. Crea una carpeta desechable, fuera del repo.

# 1. Instalar la CLI
npm install -g @fission-ai/openspec@latest
openspec --version          # debe responder con un número de versión

# 2. Sandbox desechable, FUERA de cualquier proyecto
cd ~                        # imprescindible: vienes de dentro de flowsync-ai4devs
mkdir openspec-sandbox && cd openspec-sandbox
openspec init               # elige "Claude Code". Acepta el resto.

# 3. Mira la estructura que creó
ls -R openspec/             # dos carpetas (specs/ y changes/) y un config.yaml

El cd ~ no es adorno. Vienes del paso 1, dentro de flowsync-ai4devs. Sin salir, openspec init inicializaría el repo del proyecto. Escribiría openspec/ y .claude/commands/opsx/ adentro. Es justo lo que este paso dice que no hagas todavía. Si ya te pasó, borra esas dos carpetas del repo y vuelve a empezar en ~.

  • Abre Claude Code dentro de openspec-sandbox/. Escribe / y confirma que aparecen /opsx:propose, /opsx:apply y /opsx:archive. Tiene que ser dentro del sandbox. openspec init instala los comandos en el .claude/ de ese proyecto, no en tu computadora. Si abres Claude Code en otra carpeta no vas a ver ninguno, y no será un fallo de instalación. Si estás dentro y aun así no aparecen, reinicia Claude Code por completo. Los comandos de barra se cargan al arrancar.
  • Fíjate en las dos carpetas y en que specs/ nace vacía. specs/ es la verdad de cómo se comporta el sistema. changes/ es lo que está en curso. Esa separación sostiene el vocabulario propose, apply, archive. Junto a ellas hay un config.yaml. Ahí después se le cuenta a OpenSpec el stack y las convenciones. Si un tutorial habla de openspec/project.md, ya no existe. Se retiró en la 1.0. No es un fallo de tu instalación.

3. Crea tu rama

Sal del sandbox y vuelve a tu fork de FlowSync. La rama va en el proyecto, no en el sandbox.

git checkout -b spec-viva-<tus-iniciales>

Ahí va todo lo que produzcas.

La tarea

Guarda cada prompt tal como lo lanzaste, desde el primero. Se entregan junto con la spec. No sirven reconstruidos.

Vas a escribir la spec de un código que ya está escrito y ya funciona. No propones nada. No cambias una línea. Lees lo que hay y escribes lo que hace hoy.

Suena a documentación. No lo es. Intentar decir en WHEN / THEN lo que hace un código es la forma más barata de auditarlo. Te obliga a decidir, requisito a requisito, qué es contrato y qué es casualidad. Unas cuantas veces no vas a poder decidir. Esas veces son el ejercicio.

El entregable no es la spec. Son las tres listas de la parte B. Se escriben igual de bien con la spec a medias.

El reloj existe porque la spec de un sistema entero no cabe en una tarde. El ejercicio va sobre una superficie pequeña. Lo que sale en 45 minutos es la parte que depende del criterio, no de tener una herramienta mejor.

Para la tarea no hace falta OpenSpec. No lo inicialices en el proyecto. No se lanza ningún comando de la herramienta y no se toca la configuración. Solo se lee código que ya está ahí y se escribe un archivo con el formato de una spec viva. El openspec init sobre el proyecto de verdad llega en la clase. Hacerlo antes te deja carpetas a medias que después estorban.

La superficie es el vertical de cuentas y acceso. Registro, inicio de sesión, sesión y perfil. Entero, en las dos capas, igual que lo hace el mentor. En el backend: rutas, controladores, el modelo de usuario, validadores y middlewares. En el frontend: las pantallas de acceso, el estado de sesión y la protección de rutas. Los prompts los escribes tú.

Se deja en docs/spec-viva/<tus-iniciales>.md. La carpeta todavía no existe. La crea tu archivo.

Son unos 45 minutos y hay que pararlos.

Parte A. La spec, con reloj

Con un agente, escribe la spec de lo que el sistema hace hoy. Déjala en un archivo del proyecto, no en el chat.

Las dos capas, y solo ese vertical. Lo que pasa por la API y lo que se ve en pantalla. Nada que no sea cuentas y acceso, aunque el agente se ofrezca a seguir. Que el agente escriba las dos capas es rápido. Lo que no cabe en el reloj es comprobarlo todo después. Ahí está el ejercicio. Cuenta con no llegar a comprobar cada requisito. La parte B existe para decir hasta dónde llegaste.

El formato no se negocia.

  • Arriba, un ## Purpose de una o dos frases. Para qué existe esta capability.
  • Debajo, ## Requirements. Colgando, ### Requirement: en los que el sistema SHALL hacer algo.
  • Bajo cada requisito, al menos un #### Scenario: de cuatro almohadillas, con dos viñetas: **WHEN** y **THEN**. No hay casilla para el GIVEN. La condición previa va dentro del WHEN.
  • En español, salvo las mayúsculas de la RFC.

Tres reglas duras:

  • Nada de ADDED, MODIFIED ni REMOVED. Eso es el vocabulario de un delta. Esto no es un delta. Es la verdad actual del sistema. Si tu archivo tiene una de esas secciones, escribiste otra cosa.
  • Solo comportamiento que se puede ver desde afuera. Ni un nombre de clase, ni un nombre de archivo, ni una ruta de código. En la API, observable es la petición y la respuesta. En la pantalla, observable es lo que una persona ve y puede hacer.
  • No toques el código. Ni siquiera para arreglar lo que encuentres. Sobre todo para eso. Lo que encuentres es material de la parte B.

Cuando suene el reloj, paras. Aunque esté a medias. Aunque falten requisitos, aunque haya escenarios sin THEN, aunque justo ibas a comprobar una cosa.

Una spec en la que comprobaste seis requisitos y dejaste dos a medias es información. Dice hasta dónde llegaste. Una spec completada de memoria diez minutos después no se distingue de la buena, y no sirve.

Parte B. Las tres listas

Debajo de la spec, en el mismo archivo. Esta parte hay que traerla sí o sí.

  1. Cuántos requisitos escribió el agente, y cuántos comprobaste tú abriendo el código. Los dos números, tal cual. No los redondees ni los expliques. Comprobar significa haber ido a mirar si el código hace eso. Leer el requisito y que suene razonable no cuenta.
  2. Las incoherencias que aparecieron al escribirla. Una línea cada una, con dónde se ve. No las busques a propósito. Aparecen solas. Una regla que se cumple en casi todas partes canta en cuanto intentas escribirla como si se cumpliera siempre.
  3. Lo que no supiste decidir si era un bug o el contrato. Al menos una. En una frase, qué dos lecturas se contradecían. Esta es la lista que importa. No es lo que estaba mal. Es lo que podría estar bien o mal según a quién le preguntes, y no había forma de decidirlo leyendo el código.

La tercera lista siempre tiene algo adentro, y eso no es un fallo tuyo. Una spec dice lo que el sistema hace visto desde afuera. Hay comportamiento que desde afuera no se distingue. Dos sistemas que por dentro tratan el mismo dato de formas distintas pueden responder igual. Hay otro que no se puede confirmar sin ejecutarlo y esperar, porque solo aparece al cabo de un rato o cuando algo se llena. Y hay un tercer grupo, el interesante. Se ve perfecto y aun así no sabes si alguien lo decidió o simplemente salió así.

Dejar eso marcado es la respuesta correcta. Un contrato que se calla donde no sabe sirve más que uno que rellena con seguridad fingida.

Ninguna de las tres tiene respuesta correcta. La segunda y la tercera son mejores cuanto más incómodas.

Cómo saber que quedó bien

  • Las tres listas están escritas y son concretas. Si la tercera está vacía, vuelve a mirar. Es la respuesta de quien aceptó la spec en lugar de contrastarla contra el código.
  • El número de comprobados es menor que el de escritos. Casi siempre lo es. No es un fallo. Es el dato.
  • En la spec no aparece ni un nombre de archivo ni un nombre de clase. Si aparecen, describiste la implementación, no el comportamiento. Esa spec no sobrevive al primer refactor.
  • La spec es del acceso y de nada más. Si aparecen requisitos de las tareas o de cualquier otra parte, te saliste del vertical.

Entrégalo con lo que tenga.

Cómo se entrega

Todo va en la rama que creaste, spec-viva-<tus-iniciales>.

Un pull request desde tu fork, con dos cosas y nada más:

  • Tu archivo en docs/spec-viva/, con los requisitos y las tres listas.
  • prompts.md, en la raíz. Ya está ahí con la plantilla. Pega los prompts tal cual, con el modelo y la herramienta. Incluye también los que no funcionaron.
git add docs/spec-viva prompts.md
git commit -m "spec viva: cuentas y acceso + prompts"
git push -u origin spec-viva-<tus-iniciales>

El pull request va contra el repositorio del curso, no contra tu fork.

prompts.md es la mitad de lo que se revisa. Un resultado flojo con un prompt bueno y uno flojo con un prompt vago se corrigen distinto. Sin ese archivo no se distinguen.

Lo que llegue antes de la clase recibe comentarios de tu TA. Ahí es cuando te sirve. Lo que llegue después se marca como recibido y ya no se revisa.

Si vas justo de tiempo

Repasa las lecciones de los dos caminos y de OpenSpec por dentro.

OpenSpec, Getting started, unos 10 minutos, en el repo oficial.

Telemetría: OpenSpec envía estadísticas anónimas. Nombres de comandos y versión. Para apagarla en la terminal actual:

export OPENSPEC_TELEMETRY=0

o

export DO_NOT_TRACK=1

Eso dura lo que dure la terminal. Para apagarla de forma permanente, mete ese export en tu .zshrc o .bashrc, o agrega "telemetry": { "enabled": false } al config global de OpenSpec (~/.config/openspec/config.json). No hay un subcomando de la CLI que lo haga por ti.

Antes de conectarte

  • Estás en la rama de partida, sobre tu fork, y git push funciona.
  • El proyecto enciende entero, backend y frontend, y puedes iniciar sesión.
  • openspec --version responde, y los comandos aparecen dentro del sandbox.
  • Traes el archivo de la tarea, con su spec, aunque esté a medias, y sus tres listas.
  • prompts.md está lleno, con modelo y herramienta en cada bloque.
  • El pull request está abierto.

Trae el archivo tal como quedó. Lo que le falta es la mitad de lo interesante.

Qué te llevas del módulo

Dos caminos, directo o OpenSpec, y el criterio para elegir, sobre tres casos. El loop explorar, planear, ejecutar, con el freno humano en el plan. OpenSpec como spec viva más delta, como Git para requisitos. El momento humano es revisar el contrato antes del código.

Y una lección de backlog. Un trabajo fácil que todavía no puedes construir no es lo primero. El orden real lo fijan el valor y la dependencia.

En el proyecto queda una spec viva en openspec/specs/, con sus changes archivados. Se puede leer qué se decidió, cuándo y por qué.

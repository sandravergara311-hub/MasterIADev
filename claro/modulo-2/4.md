# Módulo 2 · Lección 4 — Escribe el PRD por capas, no de un tirón

Texto original: `original/modulo-2/4.md`  
Obligatoria. Es la lección práctica.

## En una frase

El PRD se construye en cinco pasadas. En cada una, la IA cuestiona una decisión. El primer borrador no se acepta.

## Caso real: de "algo para las fallas" a un límite que se puede defender

Inmobiliaria Calle. La frase de partida es esta: "una app para que los inquilinos reporten fallas, con fotos, chat con el plomero, calificación con estrellas y aviso por WhatsApp".

Eso es una lista de soluciones, no un problema. Luis no le pide al agente que redacte el documento. Le pide que trabaje por capas.

**1. El problema, sin solución.**

"Reescribe esto como el problema de una persona, sin mencionar ninguna tecnología."

Sale esto: los inquilinos llaman a la oficina, el recado se anota en un cuaderno y el encargado se entera tarde. El WhatsApp y el chat todavía no existen. Bien.

**2. Quién es el usuario, y quién no.**

"¿Qué usuario estoy dejando afuera? ¿Quién no es el usuario?"

Luis decide: el usuario es el inquilino y el encargado del edificio. El dueño que vive en otra ciudad no entra en el primer entregable. El plomero externo tampoco. Hoy se le llama por teléfono cuando el encargado ya vio el reporte.

**3. Qué entra y qué no.**

Luis lista candidatos y pide: "de esto, ¿qué debería quedar fuera de un primer entregable que ya se pueda usar? Justifica cada recorte".

Entran: abrir un reporte con título y foto, verlo en la recepción del edificio y marcarlo resuelto.

Quedan afuera: WhatsApp, chat, estrellas y asignación automática al plomero. No porque "no alcance el tiempo". Porque no comprueban la hipótesis. La hipótesis es: "dejan de llamar a la oficina".

Una forma de ordenar el montón se llama MoSCoW:

- imprescindible,
- importante, pero el primer entregable sobrevive sin ello,
- agradable si sobra tiempo,
- y fuera a propósito.

En un MVP, lo "agradable" suele ser alcance disfrazado. Lo "fuera" es el no-alcance con otro nombre.

**4. Requisitos que se puedan comprobar.**

El agente propone: "el sistema debe ser rápido y fácil de usar". Eso es un deseo.

Luis lo reescribe: "el encargado ve un reporte nuevo en la pantalla de recepción sin recargar la página, con hasta cien reportes abiertos".

La IA redacta. Tú exiges que se pueda comprobar.

**5. Cómo sabremos que funcionó, y una pasada final.**

"Revisa el documento. ¿Qué di por cierto sin evidencia? ¿Dónde se coló algo que no justificamos?"

La métrica no es "muchos usuarios". Es esta: "en la primera semana, un edificio deja de usar el cuaderno para las fallas nuevas".

El valor está en esas vueltas, no en el primer texto.

## Dónde tener la conversación

Si el producto ya está decidido y hay repositorio, hazlo dentro del harness. En el curso, FlowSync ya tiene cuentas y login. El agente lee lo que ya existe y no se inventa el acceso otra vez.

El harness no decide el producto por ti. Es el lugar donde bajas la conversación a tierra.

Si partes de cero y todavía no sabes qué producto es, a veces conviene explorar primero en un chat limpio. Sin código que te empuje a "lo fácil de programar". Solo después traes la idea al proyecto.

## Si el sistema ya existe y es grande

No escribas un PRD del producto completo desde cero. Ese formato es para definir algo nuevo.

Hazlo en dos tiempos. Primero pide un mapa de lo que ya hay: capacidades y entidades. Solo lo justo para el cambio que tienes delante. Después especifica el cambio, no el sistema completo.

Una spec sacada de un volcado de todo el código se desfasa. Si construyes encima, rompes lo que ya funcionaba. Las propias herramientas de este método lo dicen: no documentes todo para empezar. Las specs crecen cambio a cambio.

FlowSync es un caso intermedio. Ya tiene cuentas y acceso. A partir de ahí se especifica el producto que falta.

## El MVP de FlowSync, en claro

FlowSync es un administrador de tareas para equipos pequeños. La base técnica ya funciona: cuentas y perfil.

El documento se organiza por épicas. El no-alcance del curso, que tienes que poder defender, es este:

- notificaciones e integración con Slack, porque esa infraestructura no valida el núcleo,
- roles y permisos avanzados, porque el MVP asume un equipo donde todos tienen el mismo acceso.

Cualquier "regalo" que aparezca se juzga contra esa lista. Todavía no hay identificadores de ticket ni rutas. Aquí se fija el qué y el porqué. La épica de tareas se partirá en historias en la lección siguiente.

## Errores típicos

- Aceptar el primer borrador.
- Meter el cómo: tablas, rutas, nombres de clase. Eso es de más adelante.
- Olvidar lo que queda afuera.
- Dejar el PRD fuera del proyecto. En dos semanas nadie lo abre.
- Métricas de vanidad. "Muchos usuarios" no se puede comprobar.

## Preguntas frecuentes

**¿No es más lento que ponerme a programar?**

Más lento el primer día. Más rápido el primer mes. El "casi correcto" suele nacer de una spec ambigua.

**¿Solo se puede hacer en Claude Code?**

No. Es un patrón de preguntas, más un archivo con historial. El harness lo hace más repetible. El método sirve también en Cursor o en Copilot.

Siguiente lección: bajar de la épica a historias con criterios, y usar la IA para encontrar lo que falta. No para redactar el camino feliz.

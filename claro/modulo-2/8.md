# Módulo 2 · Lección 8 — Hay varias herramientas. El orden no cambia

## En una frase

SDD es la forma de trabajar. OpenSpec es una herramienta que la implementa. En este módulo todavía no se instala. Primero el producto. La herramienta de implementación llega cuando hay tickets que atender.

## Caso real

Luis encuentra un hilo que dice: "instala OpenSpec y tendrás las specs". Lo instala sobre la carpeta vacía del portal de fallas y le pide el producto.

La herramienta le habla de cambios sobre capacidades que no existen. Luis concluye que "SDD es un lío".

El lío era de orden. OpenSpec está pensada para un sistema que ya existe y va a cambiar. No para inventar el producto desde cero. El PRD y las historias van antes. El cambio técnico va después.

## El mapa, sin memorizar nombres

En 2026 hubo varias herramientas con uso real y formas distintas de pensar. Quédate con el criterio, no con el catálogo. Una de ellas, Tessl, cambió de rumbo a principios de 2026. Ya no es una herramienta de este método, aunque el nombre siga circulando.

Para elegir, hazte cuatro preguntas.

- ¿Arma el contexto inicial, o lo escribes tú a mano?
- ¿La estructura de archivos se sostiene cuando el producto crece?
- ¿Sirve para hacer evolucionar algo que ya existe, o solo para el primer flujo?
- ¿Se conecta de forma nativa a la herramienta que ya usas?

El curso recomienda OpenSpec para empezar. Es liviana y sirve tanto en un proyecto nuevo como en uno que ya tiene código. La mayoría del trabajo profesional es de lo segundo. FlowSync también: ya tiene cuentas y acceso, y a partir de ahí se hace evolucionar.

Encima de la herramienta se montan convenciones. LIDR mantiene las suyas, con el nombre Specboot. Agregan estándares, plantillas de pull request y un paso previo que completa las historias antes de la spec.

La herramienta da el flujo: proponer, aplicar, archivar. También da las carpetas. Las convenciones agregan el criterio del equipo. No compiten.

## Por qué no se instala en este módulo

OpenSpec, en su modelo, no usa PRD, historias ni tickets. Su unidad es el cambio sobre una capacidad que ya existe. Se ubica después del documento de producto.

Casi todas las herramientas de esta familia (Spec Kit, Kiro, OpenSpec) arrancan en una spec de funcionalidad o en una propuesta de cambio. La excepción es BMAD. Es un método de ciclo completo. Su agente de producto sí escribe un PRD, y por eso pesa más para arrancar.

El curso hace la parte de producto con lo más simple que funciona. Reserva OpenSpec para cuando haya que programar.

La cadena es esta: PRD, épica, historia, ticket, y solo entonces el cambio o spec-delta.

Si empiezas por OpenSpec en una carpeta vacía, le pides a una herramienta de sistemas existentes que defina el producto. No está pensada para eso.

Hoy no instales nada de OpenSpec. En este módulo, el PRD y el backlog se trabajan con Claude Code y el harness del proyecto. `openspec init` y los comandos de cambios entran cuando ya tengas tickets.

## Preguntas frecuentes

**¿Tengo que aprender OpenSpec ya?**

No. Hoy toca el documento de producto y el backlog.

**¿Por qué no empezar por el framework más grande?**

Potente no es lo mismo que liviano para arrancar. El curso prioriza el eslabón que casi ningún framework te da, el PRD, y una herramienta que no estorbe. Lo grande se puede mirar por tu cuenta.

**Mi equipo ya usa otra. ¿Esto me sirve?**

Sí. Primero el producto. Spec viva. La herramienta se puede cambiar. El orden, no.

## Qué llevarte

- Hay varios frameworks. OpenSpec es la recomendación del curso, y no entra en el módulo 2.
- El orden es PRD, épica, historia, ticket, cambio.
- Este módulo hace los cuatro primeros.

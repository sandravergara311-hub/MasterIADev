 El agente no se inventa las columnas, se inventa los valores 🔴 — 22 min
Antonio Perez
⌛Tiempo estimado: 22 minutos

Una operadora de internet registra las averías de sus clientes en una tabla llamada incidencias. Cada fila tiene un estado, que solo admite cuatro valores: abierta, en_curso, resuelta y descartada. También hay una columna cerrada_en, con la fecha y la hora de cierre. Tanto las incidencias resueltas como las descartadas se consideran cerradas y llevan esa fecha, pero esa regla no está documentada fuera de la base.

Alguien pide un informe: cuántas incidencias se cerraron el mes pasado. El agente escribe la consulta, una persona la revisa y la aprueba porque parece correcta. El informe dice cero.

La consulta filtraba por WHERE estado = 'cerrada'. Ese valor no existe en la columna. La base acepta la consulta, pero no encuentra ninguna coincidencia. El error puede pasar inadvertido porque cerrada parece una elección razonable para responder al encargo.

👥 Cómo leer esta lección según tu perfil.

Si eres dev: distinguir entre supuestos que causan errores de ejecución y los que generan resultados incorrectos sin avisar. También identificar qué información debe consultar el agente para evitar ambos casos.

Si vienes de producto o gestión: entender por qué un informe puede estar mal aunque la consulta se ejecute sin errores, y qué conviene comprobar cuando alguien dice que lo ha revisado.

Si no tienes formación técnica: reconocer que la base de datos ejecuta literalmente las condiciones de la consulta. No interpreta que, en este negocio, «cerrada» incluye las incidencias resuelta y descartada.

Lo que un agente deduce del código y lo que necesita comprobar en la base de datos
Los archivos de un proyecto pueden describir buena parte de la estructura de la base: qué tablas hay, cómo se llaman sus columnas, qué tipos de datos utilizan y cómo se relacionan. El agente puede consultar esa información en las migraciones y en los modelos del código.

Pero esos archivos describen la estructura prevista. Para saber si coincide con la base sobre la que va a trabajar, necesita comprobarla. También hay información que puede no estar en el repositorio:

Qué valores admite una columna y cuáles aparecen en los datos. Una migración puede definir los estados permitidos, pero también puede declarar estado como texto sin más restricciones. Hay que distinguir los valores que la base permite de los que se han utilizado: consultar los datos no demuestra que sean los únicos admitidos.

Qué migraciones se han aplicado. El repositorio puede contener doce archivos de migración y la base tener aplicados once. Leer los archivos no basta para saber qué cambios se han ejecutado en ese entorno.

Qué índices existen. Los índices previstos en el código pueden no coincidir con los de la base. Esa diferencia puede afectar al rendimiento de las consultas.

Cuántas filas hay. Una consulta que funciona bien con mil filas puede tardar demasiado con diez millones. El código no indica por sí solo el volumen actual de datos.

Qué cambios se hicieron fuera de las migraciones. Alguien añadió una columna directamente desde la consola hace ocho meses para resolver un problema puntual, pero el cambio no quedó registrado en ninguna migración.

Al consultar el código, el agente puede responder a «¿cómo se llama la columna?». Al consultar la base de datos, puede comprobar «¿qué valores contiene?». Son preguntas distintas: conocer el nombre de una columna no permite saber qué datos hay en ella.

Un error es más fácil de detectar
No todas las suposiciones equivocadas se detectan de la misma manera. Algunas hacen que la base rechace la consulta; otras permiten ejecutarla y devuelven un resultado que parece válido. Conviene distinguirlas para saber qué debe comprobar la revisión:

image.png
Fíjate en la diferencia entre las dos filas del medio. El mismo valor inventado produce resultados distintos según se utilice para leer o para escribir. Si intentas guardar 'cerrada' en estado, la restricción de la tabla lo rechaza y la operación falla. Si lo usas para filtrar, esa restricción no impide ejecutar la consulta: la base compara el valor con los datos, no encuentra coincidencias y devuelve cero filas.

Estos ejemplos muestran cómo responde PostgreSQL a las tres suposiciones sobre la tabla de incidencias. Primero, una columna inventada, fecha_cierre en vez de cerrada_en:

SELECT count(*) FROM incidencias WHERE fecha_cierre >= '2026-08-01';
ERROR:  column "fecha_cierre" does not exist
Después, el valor inventado usado para escribir:

UPDATE incidencias SET estado = 'cerrada' WHERE id = 1;
ERROR:  new row for relation "incidencias" violates check constraint "incidencias_estado_check"
Y el mismo valor usado para leer, que es la consulta del informe:

SELECT count(*) AS cerradas_en_agosto
FROM incidencias
WHERE estado = 'cerrada'
  AND cerrada_en >= '2026-08-01' AND cerrada_en < '2026-09-01';
 cerradas_en_agosto
--------------------
                  0
Los dos primeros casos producen mensajes que identifican el error. El tercero devuelve un cero con la misma forma que tendría un resultado correcto.

💡 Por qué este error puede pasar inadvertido: un cero también parece una respuesta válida.

Cuando una consulta falla, el mensaje de error indica que hay algo que corregir. Cuando devuelve un número, ese resultado puede incorporarse a una diapositiva y utilizarse para tomar una decisión sin más comprobaciones.

Un cero, además, puede tener una explicación de negocio plausible. «El mes pasado no se cerró ninguna incidencia» podría atribuirse a un equipo desbordado o a un cambio de proceso. Si esa explicación resulta convincente, es fácil dejar de comprobar si el número refleja lo que ocurrió o si procede de un filtro equivocado.

Por qué una revisión humana puede pasar por alto un valor inventado
Porque leer la consulta no basta para detectar este error. La sintaxis es válida, los nombres de las columnas existen y el filtro parece coherente con el informe solicitado. Para detectar que 'cerrada' es incorrecto, quien revisa necesita contrastarlo con los cuatro valores que admite estado.

Revisar más despacio no basta si falta la información necesaria para comprobar la consulta. Si quien revisa se basa en los mismos archivos que el agente, puede aceptar la misma suposición equivocada. Además de atención, necesita conocer los valores y las reglas que utiliza esa base.

Con los valores reales de la tabla, la primera corrección también puede estar mal
Una consulta permite empezar a comprobar esos valores y esas reglas. Esta cuenta, para cada valor de estado, cuántas incidencias hay y cuántas tienen fecha de cierre:

SELECT estado, count(*) AS incidencias, count(cerrada_en) AS con_fecha_de_cierre
FROM incidencias
GROUP BY estado;
Sobre una muestra de diez incidencias, devuelve esto:

   estado   | incidencias | con_fecha_de_cierre
------------+-------------+---------------------
 abierta    |           1 |                   0
 descartada |           2 |                   2
 en_curso   |           2 |                   0
 resuelta   |           5 |                   5
El resultado aporta dos pistas. La primera: cerrada no aparece en la muestra y se observan los cuatro estados del ejemplo. La segunda: las incidencias descartadas también tienen fecha de cierre. Esto coincide con la regla de negocio del escenario, aunque observarlo en una muestra no basta por sí solo para demostrar que se cumple en todos los casos.

Si solo se corrige el valor inventado, la primera solución puede ser sustituirlo por resuelta:

WHERE estado = 'resuelta'
  AND cerrada_en >= '2026-08-01' AND cerrada_en < '2026-09-01'
En los datos del ejemplo, devuelve 4. El resultado parece razonable, pero sigue siendo incorrecto: deja fuera las dos incidencias descartadas de agosto. El informe pregunta cuántas incidencias se cerraron. Según la regla de este escenario, la fecha de cierre permite identificarlas sin excluir ni las resueltas ni las descartadas:

WHERE cerrada_en >= '2026-08-01' AND cerrada_en < '2026-09-01'
Devuelve 6, la cifra correcta para el ejemplo. La diferencia importa: un cero puede despertar dudas, mientras que un cuatro puede aceptarse sin más comprobaciones. Una corrección incompleta puede hacer que el error resulte menos evidente. Para evitarlo, hay que contrastar el resultado con los datos y con la regla de negocio antes de dar la consulta por corregida.

🔎 Cómo se llama este error en la investigación. El error de 'cerrada' corresponde a una categoría denominada violating value specification: utilizar en una consulta un valor que incumple las especificaciones de una columna. El estudio de Shen y otros lo describe, entre otros casos, en columnas con valores enumerados o con formatos estrictos, como fechas y horas. En sus evaluaciones, es el error más frecuente entre los de convención (alrededor del 70 % de ellos), que a su vez suponen cerca del 13 % del total. Fuente: Understanding, Detecting, and Repairing Real-World In-Context-Learning-Based Text-to-SQL Errors (Entender, detectar y reparar errores reales de texto a consulta basados en aprendizaje en contexto). Otros trabajos proponen consultar el contenido de la base y proporcionar al modelo los valores pertinentes (database content retrieval). Esto ayuda a reducir estas suposiciones, aunque no garantiza que interprete correctamente la regla de negocio.

Darle al agente el esquema real en vez de pedirle que lo recuerde
Un servidor que implementa Model Context Protocol (MCP) permite ofrecer al agente operaciones sobre un sistema externo, acompañadas de una descripción de lo que hace cada una. En una integración con una base de datos, esas operaciones pueden incluir listar tablas, consultar sus columnas y restricciones, listar índices y ejecutar consultas de lectura. Las capacidades concretas dependen del servidor y de sus permisos.

El cambio está en qué información respalda la propuesta del agente. Sin consultar los valores permitidos o los datos, puede elegir 'cerrada' porque parece encajar con el encargo. Con acceso a la base, puede comprobar qué estados se utilizan antes de escribir el filtro. Tener ese acceso, sin embargo, no garantiza que haga la comprobación: hay que incorporarla a la tarea.

También importa qué devuelve cada operación. En el servidor MCP de PostgreSQL con el que se probó este ejemplo (crystaldba/postgres-mcp), la operación que describe una tabla devuelve sus columnas y el nombre de cada restricción, como incidencias_estado_check, pero no su definición. Ese resultado permite saber que existe una restricción, pero no qué valores admite. Para comprobarlos, se puede ejecutar una consulta de lectura. Una opción es pedir a la base la definición de la restricción:

SELECT pg_get_constraintdef(oid) AS definicion
FROM pg_constraint
WHERE conname = 'incidencias_estado_check';
                                               definicion
---------------------------------------------------------------------------------------------------------
 CHECK ((estado = ANY (ARRAY['abierta'::text, 'en_curso'::text, 'resuelta'::text, 'descartada'::text])))
La otra opción es consultar los datos, como en la sección anterior. Ambas comprobaciones aportan información distinta: la restricción indica qué estados se admiten; los datos muestran cuáles aparecen y cuáles tienen fecha de cierre. Esto último ayuda a investigar la regla de negocio, pero no sustituye su confirmación. Para que esa comprobación ocurra, la petición al agente debe ser concreta: «Antes de filtrar por un valor, enséñame la consulta con la que lo has comprobado».

Para este trabajo, el acceso se organiza así:

Lectura con permisos limitados. El agente puede consultar el esquema y los datos necesarios para la tarea. Aunque no modifique registros, una lectura puede consumir recursos o exponer información, por lo que también necesita límites.

Escritura mediante un procedimiento separado. Poder consultar la base no implica tener permiso para modificarla. Las escrituras y las migraciones requieren revisar qué afectarán y cómo se recuperaría la información si algo sale mal.

Una copia de desarrollo adecuada para la tarea. Para este ejemplo, el agente necesita un esquema actualizado y datos de prueba que representen los estados y las reglas relevantes. Una copia desactualizada o una muestra incompleta puede llevarlo a conclusiones equivocadas. Utilizar datos ficticios o debidamente anonimizados permite hacer estas comprobaciones sin exponer innecesariamente datos de clientes.

❓ Preguntas que quizá te estás haciendo

«¿Esto no lo resuelve ya el mapeador de objetos a tablas, el Object-Relational Mapper (ORM)?» El ORM puede describir nombres de tablas y columnas, tipos de datos, valores permitidos e índices, según cómo esté configurado. Esa información ayuda al agente a entender la estructura prevista. Para saber qué restricciones e índices existen en ese entorno y qué migraciones se han aplicado, necesita contrastar el modelo con la base.

«¿No basta con pegar el esquema en el prompt?» Puede servir si el esquema está actualizado y contiene la información que requiere la tarea. Si la base cambia, tendrás que actualizar la copia. Además, en una base con cuarenta tablas, incluir el esquema completo añade información que el agente quizá no necesite. Si la consulta solo afecta a una tabla, puedes empezar por consultar su estructura y los valores pertinentes.

«Si el agente puede ejecutar consultas, ¿no puede causar problemas?» Sí. Incluso una consulta de solo lectura puede consumir muchos recursos si recorre una tabla grande. Para este trabajo, utiliza una base de desarrollo, una conexión con permisos propios de solo lectura y un límite de tiempo por consulta.

📖 Glosario exprés

Structured Query Language (SQL) es el lenguaje que se utiliza para consultar y modificar bases de datos relacionales. SELECT recupera información, WHERE establece las condiciones del filtro e INSERT añade filas.

Esquema es la estructura declarada de la base de datos. Incluye las tablas, sus columnas, los tipos de datos y las restricciones.

Restricción es una regla que la base de datos hace cumplir. En el ejemplo, una restricción impide guardar en estado un valor que no esté entre los permitidos.

Migración es un archivo versionado que define un cambio en la base de datos. Permite aplicar ese mismo cambio en distintos entornos.

Model Context Protocol (MCP) es un protocolo que permite ofrecer a un agente operaciones sobre sistemas externos. Un servidor MCP conectado a una base de datos puede permitirle consultar el esquema o los datos, según las operaciones disponibles y los permisos configurados.

Qué te llevas de esta lección
Si una consulta devuelve un cero inesperado, comprueba el filtro. Una consulta agrupada por estado, como SELECT estado, count(*) … GROUP BY estado, te muestra qué valores aparecen en los datos. Si necesitas saber cuáles admite la columna, consulta también su restricción.

Antes de cambiar el filtro, confirma qué debe contar el informe. Sustituir cerrada por resuelta devuelve un número plausible, pero deja fuera las incidencias descartadas. En el ejemplo, la fecha de cierre permite incluir ambos estados.

Pídele al agente que muestre cómo lo comprobó. Puedes decirle "Antes de escribir la consulta, dime qué valores admite esa columna y de dónde lo has sacado".

Dale acceso de solo lectura a un esquema actualizado. Utiliza una base de desarrollo separada de la de producción, con permisos propios para el agente y datos de prueba que representen los casos relevantes.

Distingue un error de ejecución de un resultado incorrecto. Si aparece un mensaje como column does not exist, la consulta no se ha podido ejecutar y debes revisar el nombre de la columna, la tabla o el esquema. Si la consulta se ejecuta sin errores, todavía debes comprobar que los filtros, las condiciones y el resultado responden realmente a la pregunta del informe.

Esta es la última lección del módulo y la que más tiempo requiere de lo que parece: leerla son nueve minutos, hacerla lleva bastante más — unos 10 de entorno e instalación, unos 45 de la tarea, más 5 si abres las lecturas recomendadas. No la dejes para la noche anterior.

Se organiza en cuatro partes. La primera explica cómo funciona el módulo — vale la pena aunque vayas con prisa. La segunda deja el entorno listo. La tercera es la tarea, la que más tiempo lleva. La cuarta explica cómo entregar.

🔁 Cómo funciona este módulo
Tiene tres momentos. Conocerlos de antemano cambia cómo aprovechas cada uno.

1. Lo intentas tú. Sobre el proyecto, con tu agente y con el reloj puesto. Entregas lo que te salga tal como esté. No pasa nada si queda a medias: este paso no se puntúa por completarlo.

2. Lo ves resuelto en el directo. El mentor hace este mismo trabajo, sobre este mismo proyecto. Si no te salió, ahí ves que se puede y cómo. Por eso conviene mirar sin teclear: lo vas a repetir con calma después.

3. Lo replicas. Los prompts que use el mentor te llegan por escrito. Con ellos vuelves a tu entorno y rehaces el recorrido, que es donde se asienta.

⚠ Cuando repitas el recorrido en el paso 3, los resultados no serán exactamente iguales. No es un fallo tuyo. El agente no produce el mismo resultado dos veces: con el mismo prompt y el mismo código pueden cambiar los nombres de variables, la redacción y hasta el número de filas de una tabla. Lo que se repite es la forma del recorrido, no el texto exacto.

🛠 Deja el entorno listo
Primero, lo que necesita tu máquina. El proyecto funciona en macOS, en Linux y en Windows a través de WSL (Windows Subsystem for Linux: un entorno Linux que corre dentro de Windows). En PowerShell no: los atajos del Makefile están escritos para macOS y Linux, y en PowerShell fallan aunque consigas instalar make.

🪟 Si trabajas en Windows, haz todo lo de esta lección dentro de la terminal de WSL — el clon, Node y make. WSL es un entorno separado: lo que tengas instalado en Windows no está disponible dentro de él, y lo que instales dentro no afecta a Windows. Clona el proyecto en tu carpeta de Linux (~/…), no en /mnt/c: desde ahí npm install va muy lento. Si aún no tienes WSL, se instala con wsl --install desde PowerShell abierto como administrador, según la guía oficial de Microsoft.

1. Node.js 24 o superior
Recomendamos tener la versión v24 o superior. Con la 20 el proyecto no arranca (make setup se para con Unknown file extension ".ts"); con la 22 arranca, pero con una pantalla de avisos EBADENGINE porque el proyecto pide la 24. La versión LTS (long term support, la de soporte largo) de nodejs.org/en/download cumple.

2. make
Comprueba que make está instalado con make --version. Si no responde: en macOS ejecuta xcode-select --install; en Linux y en WSL, sudo apt install make.

3. Tu fork, en la rama de partida
Necesitas el proyecto en la rama s4/start, sobre tu propio fork de github.com/LIDR-academy/flowsync-ai4devs. Si clonas directamente el repo del curso, no tendrás permiso de push — y lo descubrirías justo al intentar subir tu trabajo.

# 1. Fork desde la web: botón "Fork" en github.com/LIDR-academy/flowsync-ai4devs-202609-1

# 2a. Si AÚN NO has clonado: clona TU fork (no el del curso)
git clone git@github.com:<tu-usuario>/flowsync-ai4devs-202609-1.git
cd flowsync-ai4devs
git remote add upstream git@github.com:LIDR-academy/flowsync-ai4devs-202609-1.git

# 2b. Si YA clonaste el del curso: no vuelvas a clonar, recoloca los remotos
git remote rename origin upstream
git remote add origin git@github.com:<tu-usuario>/flowsync-ai4devs-202609-1.git

# 2c. Si ya venías trabajando sobre tu fork: solo comprueba que están los dos
git remote -v          # origin = TU fork · upstream = el repo del curso

# 3. Trae las ramas nuevas del curso y colócate en la de este módulo
git fetch upstream
git checkout -b s4/start upstream/s4/start

# 4. Comprueba que el fork quedó bien montado: esto tiene que funcionar
git push -u origin s4/start
📌 Un fork es una foto del momento, y el curso sigue publicando ramas. Las que aún no se han publicado todavía no existen en tu fork, y tu fork no se actualiza solo: por eso el git fetch upstream va antes del checkout. Si el comando te contesta "pathspec did not match", casi siempre es porque esa rama todavía no existe en tu fork: o no se ha publicado aún, o te faltó el git fetch upstream. Si te contesta "'upstream' does not appear to be a git repository", falta el git remote add del paso 2. Y si el push del paso 4 te rechaza por permisos, origin sigue apuntando al repo del curso: vuelve al 2b.

📌 Si te sale Permission denied (publickey), es SSH, no el fork. Los comandos de arriba usan URLs SSH (git@github.com:…), que necesitan una clave subida a tu cuenta de GitHub. O súbela ahora, que son cinco minutos y te sirve para el resto del curso, o cambia las URLs por su versión HTTPS (https://github.com/<tu-usuario>/flowsync-ai4devs.git y https://github.com/LIDR-academy/flowsync-ai4devs.git). Cualquiera de las dos vale; lo que no vale es descubrirlo el día del directo.

4. Dependencias instaladas y el proyecto levanta
Desde la raíz del proyecto. Este es el paso que conviene adelantar, así que hazlo hoy: descubrir que algo no compila con el directo empezado es el peor momento posible.

make setup   # solo la primera vez: instala backend y frontend, crea los dos .env, genera la clave y migra la base de datos
make start   # levanta el backend en <http://localhost:3333> y el frontend en <http://localhost:5173>, a la vez
make start se queda ocupando la terminal mientras los servidores corren: Ctrl-C los para a los dos, y si uno se cae arrastra al otro. make a secas lista todos los atajos disponibles. Abre otra terminal y comprueba que todo vive: curl -s localhost:3333/ tiene que devolver {"hello":"world"}, y http://localhost:5173 en el navegador tiene que mostrar FlowSync. El frontend espera el backend en http://localhost:3333; si lo arrancas en otro puerto, actualiza VITE_API_URL en frontend/.env.

🔧 Si algo falla, casi siempre es una de estas: make: command not found → falta make; Unknown file extension ".ts" durante make setup → tu Node es anterior a la 22; ❌ Faltan dependencias. Ejecuta primero: make setup → te saltaste el setup; un puerto en uso → tienes otro proyecto corriendo en el 3333 o en el 5173: ciérralo y vuelve a lanzar.

Sin make, los mismos pasos a mano:

Ejecuta npm install dentro de backend/ y dentro de frontend/.

Copia .env.example a .env en cada una.

Desde backend/, ejecuta node ace generate:key y luego node ace migration:run.

Arranca cada parte con npm run dev, en dos terminales separadas.

5. La suite de tests corre y sale en verde
Lánzalo desde backend/ con npm test. Si estás en la raíz del proyecto, usa (cd backend && npm test) — los paréntesis hacen que vuelvas a la raíz al terminar. Todos los tests tienen que pasar en verde. Si algo falla, es un problema de entorno: mejor resolverlo ahora que descubrirlo con el directo empezado.

6. Abre openspec/specs/
Busca la spec viva de la gestión de tareas. Cada carpeta dentro de openspec/specs/ es una capability: un ámbito del comportamiento del sistema, descrito como debe comportarse, no como está implementado. Dentro encontrarás los requisitos y, asociados a cada uno, los scenarios — los ejemplos concretos contra los que se verifica el código. Familiarízate con su estructura antes de empezar: la tarea parte de ahí.

7. Claude Code arranca y lee tu contexto
Abre .claude/agents/ y anota qué subagentes tienes ya definidos, aunque la respuesta sea "ninguno": es la carpeta donde vas a trabajar, y el objetivo de este paso es saber desde dónde partes. Si no tienes ninguno de revisión, no es un problema: un subagente es simplemente un archivo Markdown con su propio prompt y sus permisos, y crearlo lleva un minuto.

8. Crea tu rama
git checkout -b trazabilidad-<tus-iniciales>
Todo lo que produzcas va en esa rama.

📋 La tarea
En este ejercicio vas a trabajar sobre el requisito «Lo que cada tarea muestra de su responsable», que está en openspec/specs/tasks/spec.md — el mismo sobre el que trabajará el mentor en el directo. Lo intentas tú primero, con tus propios prompts. El objetivo es construir una matriz de trazabilidad: revisar, scenario a scenario, si cada uno tiene un test que lo cubre, y escribir los que falten. Son dos partes: la primera con el reloj puesto, la segunda sin él para reflexionar sobre lo que encontraste.

⚠ Guarda cada prompt tal cual lo lanzas, desde el primero. Estos se entregan junto con la matriz y no se aceptan reconstruidos: el prompt que reescribes mentalmente diez minutos después no es el que lanzaste, y esa diferencia es precisamente lo que se quiere ver.

Dónde va cada cosa:

La matriz de trazabilidad y las tres líneas van juntas en docs/verificacion/<tus-iniciales>.md. Es una carpeta nueva: la crea tu archivo.

Los tests que escribas van en backend/tests/functional/tasks/, siguiendo el estilo de los que ya hay en backend/tests/functional/auth/. No toques nada fuera de backend/tests/.

Trabájalo en la rama propia que creaste al dejar el entorno listo.

⚠ Reserva unos 45 minutos y pon el reloj. Es importante que cronometres el tiempo. Si lo dejas para la noche anterior, es fácil terminar rellenando la matriz a ojo, sin dedicar tiempo a pensar en cada respuesta. Y precisamente eso es lo que la tarea quiere que detectes: la diferencia entre completar la matriz por cumplir y dedicarle el tiempo necesario para que sea realmente útil.

🅰 Parte A: la matriz y los tests que faltan, con reloj
Antes de empezar, tres términos que usarás en esta parte:

Requisito: una regla de comportamiento del sistema. Define qué debe ocurrir en una situación concreta.

Scenario: un ejemplo concreto asociado a un requisito — con su par de cuándo y entonces — contra el que se comprueba esa regla.

Capability: un grupo de requisitos que cubre un ámbito de comportamiento completo.

Con un agente, trabaja sobre el requisito «Lo que cada tarea muestra de su responsable» y produce dos entregables. Déjalos escritos en archivos versionados del repositorio, no en el chat.

Trabaja solo ese requisito, no la capability entera, aunque quepa o el agente se ofrezca a cubrirla. La unidad es el requisito porque es lo que cabe en el tiempo disponible. Además, este en particular tiene peso real: define qué datos de una persona aparecen junto a cada tarea — y es lo primero que se rompe sin que nadie lo note.

A.1 · La matriz de trazabilidad
La matriz mapea, scenario a scenario, si el requisito está cubierto por los tests. El formato lo fija esta lección y no es negociable: una fila por scenario y cuatro columnas. Encima, dos números: cuántos scenarios tiene el requisito y cuántos resultaron cubiertos — el primero se anota al empezar, el segundo al terminar.

El scenario, en una línea. Qué se espera y en qué situación. Si no cabe en una línea, es que estás juntando dos.

Qué test lo cubre, con el nombre exacto que aparece en la suite. Sin el nombre concreto, la columna va vacía: "seguro que algo lo cubre" no es una fila.

Cubierto · No cubierto · No lo sé. Los tres estados son válidos, y el tercero no es un fallo: es el resultado más informativo de los tres.

Si pusiste "no lo sé", qué te faltó para decidirlo. Media línea. Suele ser una de dos: no encontraste dónde se comprueba, o encontraste algo que se le parece y no dice exactamente lo mismo.

Así queda la tabla. Los dos números van encima — el primero antes de empezar, el segundo al terminar:

Scenarios en el requisito: 4 · Cubiertos: ___

Scenario Test que lo cubre Estado Qué te faltó (ejemplo) La tarea muestra el nombre del responsable cuando tiene uno asignado show_assignee_name_when_present Cubierto — … … … …

⚠ El nombre de un test no es prueba de cobertura. Un test puede llamarse igual que el scenario y comprobar otra cosa, o solo la mitad. Para marcar cubierto hay que abrir el test y leer lo que afirma. Es la columna que más caro sale rellenar de memoria, y es justo la que esta tarea quiere que mires.

A.2 · Los tests que faltan
Por cada fila en No cubierto, escribe el test que falta — uno por scenario — siguiendo el estilo de los que ya existen en el proyecto. Sin tocar nada fuera de la carpeta de tests. Cuando los tengas, ejecútalos.

⚠ Pase lo que pase, no arregles el código ni ajustes el test para que pase. Si algo se pone en rojo, se queda en rojo y se entrega en rojo: el objetivo es saber qué está mal, no ocultarlo. Quien verifica no arregla, porque quien arregla deja de ver.

⚠ Cuando suene el reloj, para. Aunque esté a medias. Aunque falten filas, aunque haya tests sin escribir, aunque justo estuvieras a punto de comprobar una cosa.

Una matriz con cuatro filas rellenas y el resto en blanco es información: dice exactamente hasta dónde llegaste. Una fila completada de memoria diez minutos después es ruido con formato, y encima es indistinguible de la buena.

🅱 Parte B: las tres líneas
Los tres puntos que se piden a continuación van en el mismo archivo que la matriz — docs/verificacion/<tus-iniciales>.md —, justo debajo de ella: una línea cada uno, no más. No en un archivo separado, no en el chat. Esta parte es obligatoria: es lo mínimo que hay que entregar.

Cuántos scenarios creías cubiertos antes de mirar, y cuántos lo estaban. El primer número se anota antes de lanzar el primer prompt — a ojo, sin abrir nada todavía. El segundo, al terminar. Los dos exactamente como quedaron, sin redondear ni explicar.

El scenario en el que no supiste si faltaba un test o faltaba la regla en la spec. Indica cuál fue y qué te hizo dudar. Las dos opciones se confunden fácilmente: en un caso la regla existe pero nadie la comprobó; en el otro, la regla no está escrita en ninguna parte — la estabas definiendo tú.

Algo que el scenario no determinaba y tuviste que decidir al escribir el test. Un valor concreto, un límite, qué pasa cuando el dato viene vacío — ese tipo de decisiones. Casi ningún scenario determina su test del todo, y el hueco que cubriste sin notarlo es lo que más se parece a un defecto futuro.

⚠ Ninguna de las tres tiene una respuesta correcta. De hecho, la segunda y la tercera son más útiles cuanto más incómodas sean. Un "no sabía si esto me correspondía decidirlo a mí" dicho con honestidad aporta mucho más que una matriz completa llena de certezas inventadas.

Cómo saber que la has hecho bien
Las tres líneas están escritas y son concretas. Si la tercera dice "el scenario lo decidía todo", vuelve a mirar el test que escribiste: los valores que pusiste vinieron de algún sitio, y ese sitio eras tú.

Los dos números de la primera línea no coinciden. Casi nunca coinciden, y eso no es un fallo tuyo: es el dato entero de la tarea.

Hay al menos un "no lo sé" en la matriz. Significa que abriste los tests en vez de fiarte de sus nombres.

La matriz cabe en una pantalla. Si no cabe, saliste del ámbito del requisito y estás cubriendo la capability entera otra vez.

Hay algún test tuyo en rojo, o sabes decir por qué no lo hay. Las dos respuestas valen; lo que no vale es no haberlo mirado.

📤 Cómo se entrega
El entregable principal son las tres líneas de la parte B, no completar toda la matriz. Puedes escribirlas aunque la matriz esté a medias; si se acaba el tiempo, deja la matriz como esté y pasa a escribir esas tres líneas.

Y una cosa importante: que la matriz no tenga ningún «no lo sé» no significa que esté bien hecha. Más bien puede ser una señal de alerta. Cuando examinas un requisito de verdad, es normal que aparezcan dudas o cosas que no puedes confirmar.

🧠 prompts.md no es papeleo, y es la mitad de lo que se revisa. Lo que se mira no es solo el resultado, es cómo lo pediste: un resultado flojo con un prompt bueno y un resultado flojo con un prompt vago necesitan respuestas distintas, y sin ese archivo no se distinguen. Pega los prompts tal cual los lanzaste, con su modelo y su herramienta, e incluye también los que no funcionaron, que suelen ser los más útiles de leer.

🎯 Qué te llevas del Módulo 4
El modelo mental:

Tests verdes ≠ correcto: un test verde prueba lo que pregunta, no lo que ignoró.

Verificar es trazar cada criterio hasta su prueba y su código.

La revisión adversarial refuta en vez de validar: un subagente independiente que contrasta el resultado contra la spec viva.

La documentación viva vive en el repo: el diagrama, el contrato de la API y el README se generan del código; el ADR se decide y se escribe una vez — todo versionado, y lo que se genera se regenera en CI.

El ancla de todo es la spec viva: mientras esté al día, lo que cuelga de ella también.

Lo que queda en el proyecto:

Una matriz de trazabilidad que dice qué criterio tiene prueba y cuál no.

Los bugs que el revisor adversarial cazó con la suite en verde, corregidos y con su prueba añadida.

El proyecto no queda "casi listo" — queda verificado y documentado.

👥 Qué te llevas según de dónde vengas.

Si eres dev: lo nuevo no es escribir pruebas: es cruzar cada criterio con la suya y dejar de tratar «la suite pasa» como respuesta. Y tienes una pieza que montas hoy: un revisor con permisos recortados y un encargo escrito para refutar, no para aprobar.

Si vienes de producto o gestión: el criterio de aceptación que escribes es lo que aquí se comprueba, así que uno vago no se puede verificar ni a mano ni con IA. Pide evidencia (archivo, línea y regla rota) en vez de un «lo he revisado», y exige que el porqué de cada decisión quede escrito, porque es el único documento que no se puede sacar del código.

Si no tienes background técnico: «está en verde» es una afirmación sobre lo que alguien decidió probar, no sobre lo que se pidió. Y el movimiento de fondo no es de código: separar a quien construye de quien critica.

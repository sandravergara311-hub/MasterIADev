Los cuatro artefactos de documentación viva 🔴 — 16 min
Antonio Perez
⏳ Tiempo estimado: 16 min

La documentación viva no consiste en mantener documentos a mano. Se apoya en cuatro artefactos: tres se generan a partir de lo que ya existe —código, specs y backlog— y uno se decide, porque recoge un porqué que no está escrito en ningún otro sitio.

Los cuatro viven en el repositorio y se versionan junto con el código. Aquí vamos a ver qué es cada uno, de dónde sale y qué papel cumple.

📌 Estos cuatro no cubren todo. Se reparten la arquitectura, el contrato de la API y el código, pero la documentación operacional (runbooks, guardias, procedimientos de despliegue) y el comentario a nivel de función (el TSDoc que documenta cada función por dentro) juega con otras reglas: la escribe quien está de guardia, se prueba cuando algo se rompe a las tres de la mañana, y no se genera de nada. No entra en estos cuatro, y no por olvido.

👥 Tres de los cuatro son responsabilidad del desarrollo. Uno no, y probablemente es el que te corresponde a ti.

Si eres dev, los cuatro te afectan. Y el que más tiempo puede ahorrarte es el contrato de la API, porque deja de depender de que alguien lo mantenga a mano.

Si vienes de producto, negocio o gestión, presta especial atención al ADR. Es el único de los cuatro que no puede salir del código: registra por qué se tomó una decisión, y ese contexto solo existe si alguien lo deja escrito. También es el que más se echa de menos cuando falta: llega el día en que alguien pregunta por qué el sistema hace algo de una determinada manera y la única respuesta es "nadie se acuerda".

Y si no tienes background técnico, quédate con una sola idea: tres de estos documentos se generan y uno se decide.

📖 Glosario exprés. Esta lección usa varios términos que conviene tener claros:

OpenAPI (antes conocido como Swagger) es un formato estándar para describir una API: qué endpoints tiene, qué recibe cada uno y qué devuelve.

Es un archivo, no una web. A partir de ese archivo se pueden generar tanto la documentación navegable de la API como los clientes para consumirla.

Structurizr: una herramienta donde describes tu arquitectura una sola vez en un lenguaje de texto y ella genera todas las vistas. La opción cuando necesitas varias vistas coordinadas del mismo modelo, en vez de diagramas sueltos.

Docs-as-code: tratar la documentación igual que el código: vive en el repositorio, se revisa en el mismo pull request y se regenera automáticamente. No es una herramienta; es una decisión sobre dónde vive la doc y quién la revisa.

GitHub Pages: el servicio de alojamiento web de GitHub que convierte una carpeta de documentación en un sitio con URL propia. Gratuito en repositorios públicos; en privados requiere un plan de pago (Pro, Team o Enterprise), que es el caso de la mayoría de los repos de empresa.

Spec viva: el documento del repo que describe cómo debe comportarse cada parcela del sistema, escrito en escenarios, y que se actualiza en el mismo cambio que el código para no quedarse desactualizada.

CI (integración continua): el servicio que, cada vez que subes un cambio, lanza automáticamente un conjunto de tareas: tests, linters y, en este contexto, también regenerar y publicar la documentación.

Harness: el andamiaje con el que configuras a tu copiloto para un proyecto concreto: qué lee, qué herramientas puede usar y qué reglas sigue.

Delta-spec: en lugar de reescribir la especificación entera, describes solo lo que cambia con este trabajo. Al aplicarla, esos cambios se incorporan a la spec viva y queda el registro de qué se modificó y cuándo.

1. Arquitectura: C4 + Mermaid (diagramas como código)
Mermaid es texto en un bloque de código que GitHub/GitLab renderizan como diagrama. C4 (Simon Brown) organiza la arquitectura en cuatro niveles — de ahí el nombre: Contexto, Contenedor, Componente y Código —; el cuarto casi nunca se dibuja, porque a ese nivel el código ya es el diagrama. El resultado: un diagrama que vive en el repo, se versiona en el diff y se mantiene al día junto con el código.

Se genera leyendo la estructura del repo:

Analiza la estructura de este proyecto (controladores, modelos, capa de datos,
frontend) y genera un diagrama de contenedores estilo C4 en Mermaid.
Guárdalo en la carpeta de documentación del proyecto.
Esto es lo que obtuvimos con una aplicación que tiene API en AdonisJS y frontend en React. Nadie lo dibujó: salió de leer el código.

💡 Mermaid vs. Structurizr: usa Mermaid cuando el diagrama es ad-hoc, vive en un README/ADR y no necesita vistas coordinadas. Usa Structurizr DSL (defines el modelo una vez, genera todas las vistas C4) cuando sí necesitas varias vistas coordinadas del mismo modelo (contexto, contenedores y componentes a la vez) o la arquitectura es un entregable formal. Con una sola vista, como la de arriba, Mermaid en el README basta.

2. ADR: la memoria institucional (el "por qué")
Un Architecture Decision Record registra una decisión técnica significativa: contexto, opciones consideradas y por qué se eligió una. Captura lo único que el código nunca te cuenta: el porqué.

Criterio pragmático de cuándo escribir uno: "¿si un dev nuevo viera este código, se preguntaría 'por qué lo hicieron así'?" Si sí, hay un ADR pendiente.

Formato: el original es Nygard, con cinco apartados: título, contexto, decisión, estado y consecuencias. El estado es lo que evita que un ADR se edite: cuando la decisión cambia, se marca como reemplazado y se escribe otro. Una variante muy usada es MADR (añade "opciones consideradas" con pros/cons — más útil cuando lo rellena un agente). Usa el que adopte tu equipo; el curso trabaja con el de Nygard.

El flujo eficiente no es escribir el ADR: es transcribir la decisión que ya tomaste a formato ADR. Si está en un hilo o en la descripción de un PR, pégalo. Pongamos que tu equipo acaba de decidir algo de este calibre:

Mi equipo ha decidido usar las delta-specs (la descripción de lo que cambia en el
comportamiento del sistema, en vez de reescribir la spec entera) como fuente de
verdad viva del proyecto. Genera el ADR que registra esa decisión: contexto, las
alternativas que se consideraron y por qué se eligió esta. Guárdalo junto a las
demás decisiones de arquitectura.
💡 Anti-hype: el agente no se lo inventa: lo redacta desde las decisiones que ya tomaste y que están escritas en el repo, en el hilo o en el PR. Pero el ADR lo revisas tú: la IA redacta el registro; la decisión y su validez son humanas.

3. API: OpenAPI/Swagger desde el código
Lo importante es esto: el contrato de la API sale del código, no de un documento que alguien tenga que mantener a mano.

Con un generador de OpenAPI instalado —en AdonisJS, por ejemplo, un paquete de la comunidad, no del core, como @foadonis/openapi— solo necesitas configurarlo y registrar su ruta. A partir de ahí, el spec se construye a partir de las rutas y controladores reales: qué endpoints existen, qué parámetros reciben y qué respuestas devuelven.

⚠ Antes de casarte con un generador, mira si declara tu versión. Un paquete que no declara con qué versiones del framework funciona no te va a avisar cuando deje de hacerlo: simplemente generará algo incompleto o dejará de generar. En npm, eso se lee en sus peer dependencies. Un paquete con esa lista vacía no es más compatible: es menos honesto. Míralo también en la fecha del último commit.

Sobre nuestra API de tareas: el spec muestra el endpoint de listado con su filtro por estado —que rechaza con un error de validación un estado que no existe— y el campo calculado que marca una tarea como vencida solo si su fecha pasó y no está terminada. Cada uno con su tipo, sus valores admitidos y sus respuestas posibles, tal como el código los expone hoy. Si el código cambia, regeneras y el contrato se actualiza. Un frontend, un cliente móvil o un partner lo consume sin preguntarte nada.

💡 Cierra el círculo: puedes pedirle al harness que contraste el OpenAPI generado con los scenarios de openspec/specs/: ¿algún endpoint documentado se desvía de la spec? La documentación no solo describe: verifica. (code-first vs design-first son ambos válidos; hoy hacemos code-first porque ya hay código: el patrón docs-as-code es el mismo.)

4. README por módulo
Qué hace cada módulo y cómo se usa, generado desde su código:

Genera un README para el módulo de tareas: propósito, endpoints, cómo correrlo
y probarlo. Guárdalo junto al código de ese módulo.
Docs-as-code: versionar y publicar
Los cuatro artefactos viven dentro del repo, junto al código que describen, y se commitean con la feature, en el mismo PR. Y se publican solos:

Un sitio de docs (MkDocs o Docusaurus, da igual para empezar; el patrón es el mismo) construye un sitio estático.

Un job de CI regenera y publica en GitHub Pages en cada push.

💡 Nadie "se acuerda" de actualizar la doc: el pipeline lo hace, igual que un hook de formato, una acción que el copiloto dispara solo al terminar de editar, deja el código formateado sin que se lo pidas. Guardarraíles, no buena voluntad.

❓ Preguntas que quizá te estás haciendo

"¿Tengo que montar los cuatro para empezar?" No. De hecho, intentar montar los cuatro de golpe es una buena manera de acabar sin ninguno.

El orden útil depende de qué necesitas responder. Si la pregunta es cómo se consume la API, empieza por el contrato generado. Si la pregunta es por qué el sistema hace algo de una determinada manera, empieza por el ADR.

El diagrama de arquitectura probablemente sea el que más impresiona a primera vista, pero también es el que menos suele urgir al principio.

• "Cuatro documentos vivos suenan a cuatro cosas más que mantener." Solo una lo es. Tres se regeneran —el diagrama, el contrato de la API y el README salen del código cada vez—, así que mantenerlos al día es un comando en CI, no trabajo manual. El ADR es el único que alguien escribe a mano, y aun así tampoco se mantiene en el sentido habitual: cuando la decisión cambia, no se edita el ADR anterior; se escribe uno nuevo y el anterior queda marcado como reemplazado. Así el porqué queda fechado y puedes ver qué se pensaba en cada momento, en lugar de acabar con una wiki sobrescrita donde nadie recuerda ya el razonamiento original.
• "¿Y si el diagrama o el contrato que genera están mal?" Pueden estarlo. Pero ahí está precisamente la diferencia con una doc escrita a mano: como estos tres salen del código, el error se reproduce en cuanto regeneras. Eso significa que o lo arreglas en el código o lo arreglas en la spec — no hay un tercer lugar donde pueda quedar sin corregir. Un documento manual equivocado, en cambio, se queda equivocado hasta que alguien lo lee con atención, y eso casi nunca pasa.

Qué te llevas de esta lección
Mermaid/C4: diagrama como texto, nace del código y se actualiza con él. Structurizr solo si escala.

ADR: transcribe la decisión que ya tomaste; el "por qué" lo pones (y lo revisas) tú.

OpenAPI desde el código: el contrato sale del código, no de un documento que alguien tenga que mantener; y puede contrastarse contra la spec.

README por módulo: qué hace y cómo se usa, generado desde el código de ese módulo.

Docs-as-code: los cuatro viven en el repo, se revisan en el PR y CI los regenera y publica solos. La spec viva es el ancla que los mantiene honestos.

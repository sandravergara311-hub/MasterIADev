🔁 Cómo funciona este módulo
Tiene tres momentos. Conocerlos de antemano cambia cómo aprovechas cada uno.

1. Lo intentas tú. Sobre el proyecto, con tu agente y con el reloj puesto. Entregas lo que te salga tal como esté. No pasa nada si queda a medias: este paso no se puntúa por completarlo.

2. Lo ves resuelto en el directo. El mentor hace esta misma auditoría, sobre este mismo proyecto. Si no te salió, ahí ves que se puede y cómo. Por eso conviene mirar sin teclear: lo vas a repetir con calma después.

3. Lo replicas. Los prompts que use el mentor te llegan por escrito. Con ellos vuelves a tu entorno y rehaces el recorrido, que es donde se asienta.

⚠ Cuando repitas el recorrido en el paso 3, los resultados no serán exactamente iguales. No es un fallo tuyo. El agente no produce el mismo resultado dos veces: con el mismo prompt y el mismo repositorio pueden cambiar la redacción, el orden de las filas y hasta cuántas devuelve. Lo que se repite es la forma del recorrido, no el texto exacto.

🛠 Deja el entorno listo
Primero, lo que necesita tu máquina. El proyecto funciona en macOS, en Linux y en Windows a través de WSL (Windows Subsystem for Linux: un entorno Linux que corre dentro de Windows). En PowerShell no: los atajos del Makefile están escritos para macOS y Linux, y en PowerShell fallan aunque consigas instalar make.

🪟 Si trabajas en Windows, haz todo lo de esta lección dentro de la terminal de WSL — el clon, Node y make. WSL es un entorno separado: lo que tengas instalado en Windows no está disponible dentro de él, y lo que instales dentro no afecta a Windows. Clona el proyecto en tu carpeta de Linux (~/…), no en /mnt/c: desde ahí npm install va muy lento. Si aún no tienes WSL, se instala con wsl --install desde PowerShell abierto como administrador, según la guía oficial de Microsoft.

1. Node.js 24 o superior
Recomendamos tener la versión v24 o superior. Con la 20 el proyecto no arranca (make setup se para con Unknown file extension ".ts"); con la 22 arranca, pero con una pantalla de avisos EBADENGINE porque el proyecto pide la 24. La versión LTS (long term support, la de soporte largo) de nodejs.org/en/download cumple.

2. make
Comprueba que make está instalado con make --version. Si no responde: en macOS ejecuta xcode-select --install; en Linux y en WSL, sudo apt install make.

3. Tu fork, en la rama de partida
Necesitas el proyecto en la rama s5/start, sobre tu propio fork de github.com/LIDR-academy/flowsync-ai4devs-202609-1. Si clonas directamente el repo del curso, no tendrás permiso de push — y lo descubrirías justo al intentar subir tu trabajo.

# 1. Fork desde la web: botón "Fork" en github.com/LIDR-academy/flowsync-ai4devs-202609-1

# 2a. Si AÚN NO has clonado: clona TU fork (no el del curso)
git clone git@github.com:<tu-usuario>/flowsync-ai4devs-202609-1.git
cd flowsync-ai4devs
git remote add upstream git@github.com:LIDR-academy/flowsync-ai4devs-202609-1.git

# 2b. Si YA clonaste el del curso: no vuelvas a clonar, recoloca los remotos
git remote rename origin upstream
git remote add origin git@github.com:<tu-usuario>/flowsync-ai4devs-202609-1.git

# 2c. Si ya venías trabajando sobre tu fork: solo comprueba que están los dos
git remote -v          # origin = TU fork · upstream = el repo del curso

# 3. Trae las ramas nuevas del curso y colócate en la de este módulo
git fetch upstream
git checkout -b s5/start upstream/s5/start

# 4. Comprueba que el fork quedó bien montado: esto tiene que funcionar
git push -u origin s5/start
📌 Un fork es una foto del momento, y el curso sigue publicando ramas. Las que aún no se han publicado todavía no existen en tu fork, y tu fork no se actualiza solo: por eso el git fetch upstream va antes del checkout. Si el comando te contesta "pathspec did not match", casi siempre es porque esa rama todavía no existe en tu fork: o no se ha publicado aún, o te faltó el git fetch upstream. Si te contesta "'upstream' does not appear to be a git repository", falta el git remote add del paso 2. Y si el push del paso 4 te rechaza por permisos, origin sigue apuntando al repo del curso: vuelve al 2b.

📌 Si te sale Permission denied (publickey), es SSH, no el fork. Los comandos de arriba usan URLs SSH (git@github.com:…), que necesitan una clave subida a tu cuenta de GitHub. O súbela ahora, que son cinco minutos y te sirve para el resto del curso, o cambia las URLs por su versión HTTPS (https://github.com/<tu-usuario>/flowsync-ai4devs.git y https://github.com/LIDR-academy/flowsync-ai4devs.git). Cualquiera de las dos vale; lo que no vale es descubrirlo el día del directo.

4. Dependencias instaladas y el proyecto levanta
Desde la raíz del proyecto. Este es el paso que conviene adelantar, así que hazlo hoy: descubrir que algo no compila con el directo empezado es el peor momento posible.

make setup   # solo la primera vez: instala backend y frontend, crea los dos .env, genera la clave y migra la base de datos
make start   # levanta el backend en http://localhost:3333 y el frontend en http://localhost:5173, a la vez
make start se queda ocupando la terminal mientras los servidores corren: Ctrl-C los para a los dos, y si uno se cae arrastra al otro. make a secas lista todos los atajos disponibles. Abre otra terminal y comprueba que todo vive: curl -s localhost:3333/ tiene que devolver {"hello":"world"}, y http://localhost:5173 en el navegador tiene que mostrar FlowSync. El frontend espera el backend en http://localhost:3333; si lo arrancas en otro puerto, actualiza VITE_API_URL en frontend/.env.

🔧 Si algo falla, casi siempre es una de estas: make: command not found → falta make; Unknown file extension ".ts" durante make setup → tu Node es anterior a la 22; ❌ Faltan dependencias. Ejecuta primero: make setup → te saltaste el setup; un puerto en uso → tienes otro proyecto corriendo en el 3333 o en el 5173: ciérralo y vuelve a lanzar.

Sin make, los mismos pasos a mano:

Ejecuta npm install dentro de backend/ y dentro de frontend/.

Copia .env.example a .env en cada una.

Desde backend/, ejecuta node ace generate:key y luego node ace migration:run.

Arranca cada parte con npm run dev, en dos terminales separadas.

5. Ejecuta la suite de tests y comprueba que todo pasa
Desde backend/, ejecuta npm test. Si estás en la raíz del proyecto, puedes usar (cd backend && npm test). Los paréntesis hacen que, al terminar, vuelvas a la raíz.

Todos los tests deben pasar. Si alguno falla, resuélvelo antes del directo para evitar problemas de entorno durante la sesión.

Léelas completas. No necesitas memorizar cada detalle. Lo importante es saber dónde están y qué tipo de instrucciones contienen, porque serán parte de la tarea que viene a continuación.

📋 La tarea
⚠ Guarda cada prompt exactamente como lo envías, desde el primero. Tendrás que entregarlos junto con la tabla. No los reconstruyas después, porque los cambios que harías al revisarlos también forman parte de lo que queremos analizar.

El encuadre, y no es un consuelo
El entregable no es la tabla. Son las tres líneas de la parte B. Puedes escribirlas aunque la tabla todavía no esté completa.

Antes de empezar, ten en cuenta algo importante: el resultado no depende de ti. Lo determina el historial del repositorio. Puede mostrar que varias reglas se incumplen, que muchas no se pueden comprobar o que todas se cumplen. Cualquiera de esos resultados es válido. Lo importante es que puedas justificarlo con evidencia.

Si todas las reglas se cumplen, la pregunta sigue siendo útil: ¿lo sabías antes de revisar el historial o simplemente lo dabas por hecho?

Qué vas a auditar: las reglas de proceso que acabas de localizar en el paso 6. Para comprobar si se cumplen, tendrás que contrastarlas con los últimos 15 commits del mismo repositorio. Es la misma auditoría que hará el mentor durante el directo, pero aquí la intentas antes con tus propios prompts.

⚠ Reserva unos 45 minutos y usa un temporizador. Cuando se acabe el tiempo, detente aunque la tabla no esté completa. La tarea también busca mostrar qué puedes comprobar con evidencia dentro de un tiempo limitado.

🅰 Parte A: la auditoría, con reloj
Antes de empezar: registra tu expectativa
Abre el archivo de instrucciones del agente y localiza las reglas de proceso. Son las que indican qué hacer antes de modificar código, cuándo crear commits y qué debe hacerse al cerrar el trabajo.

Sin comprobar todavía el historial, marca cuáles crees que se están cumpliendo. Basta con una palabra por regla: sí, no o ni idea.

Te llevará unos treinta segundos. El objetivo es dejar constancia de lo que pensabas antes de revisar la evidencia. Así podrás comparar después tu expectativa con lo que realmente muestra el historial.

La tabla
Con ayuda del agente, contrasta las reglas con los últimos 15 commits del repositorio y el estado actual de los archivos del proyecto. Guarda el resultado en docs/auditoria/<tus-iniciales>.md, no en el chat.

Usa una fila por regla y completa estas cinco columnas:

Qué pide la regla. Resúmela en una frase y con tus propias palabras. Si necesitas varias frases, puede que estés mezclando más de una regla.

Qué se revisó para comprobarla. Indica el comando ejecutado o el archivo consultado. Sin esta información no hay forma de saber en qué se apoya el veredicto.

Veredicto. Solo puede ser se cumple, no se cumple o no se puede comprobar con la información disponible. Este último caso también es un resultado válido. Significa que la regla no deja suficiente evidencia para verificarla.

Evidencia. Escríbela en una línea. Si la regla no se cumple, indica dónde se incumple. Si no se puede comprobar, explica qué información falta.

Qué harías con ella. Elige una opción: dejarla, borrarla o convertirla en una comprobación automática.

⚠ Esto es una auditoría, no una tarea de corrección. Indica al agente que no modifique ningún archivo. Si empieza a corregir lo que encuentra, cambiará el estado que estás intentando analizar y perderás parte de la evidencia original.

⚠ Cuando termine el tiempo, detente aunque la tabla esté incompleta. No completes después las filas de memoria.

Una fila parcial también aporta información porque muestra hasta dónde llegaste dentro del tiempo disponible. Completarla después sin volver a comprobar la evidencia puede hacer que el resultado parezca más sólido de lo que realmente es.

🅱 Parte B: las tres líneas
Debajo de la tabla, en el mismo archivo, añade estas tres líneas. Esta parte es obligatoria y debe estar completa.

La regla en la que más te equivocaste. Compara tu expectativa inicial con el veredicto final y elige la que más se alejó de lo que pensabas. Si acertaste todas, indícalo y explica en una frase en qué te apoyaste para acertar. Si solo era una impresión, también conviene dejarlo por escrito.

Una regla que no se puede comprobar con la información disponible. Explica en una frase qué tendría que cambiar para poder verificarla. Puede ser reformularla, convertirla en una comprobación automática o aceptar que no deja una evidencia clara.

La regla que eliminarías y por qué. Hay dos casos habituales: una regla que ya garantiza otra herramienta o una que nadie sigue y que tampoco aporta valor. Elige una y explica a cuál de los dos casos pertenece.

⚠ No hay una respuesta correcta para estas tres líneas. Lo importante es que reflejen lo que descubriste durante la auditoría, incluso si el resultado contradice lo que esperabas al empezar.

🎯 Qué te llevas del Módulo 5
El modelo mental: una regla escrita en un archivo es una petición, no una garantía. Puede cumplirse durante tanto tiempo que dejes de comprobarla, por eso cada regla debe colocarse según su forma de fallar. Si puede fallar en silencio, conviene moverla a una capa que la ejecute y la verifique.

Automatizar la generación de algo no significa automatizar su utilidad. Muchas veces, lo primero que compensa automatizar es lo más repetitivo: comprobar que lo generado sigue coincidiendo con su fuente.

Un agente puede revisar cambios sin que nadie lo invoque, pero su utilidad no depende solo del modelo. También importa dónde aparecen los hallazgos, quién los revisa y quién toma la decisión final.

Un guardarraíl también puede dejar de ser útil aunque acierte. Si genera demasiados avisos poco relevantes, el equipo termina ignorándolos. Por eso conviene calcular su coste por ejecución y observar cuántos hallazgos terminan provocando cambios reales.

Lo que queda en el proyecto: una auditoría de sus reglas de proceso, que muestra cuáles se cumplen, cuáles no y cuáles no se pueden comprobar.

También queda una comprobación automática y reproducible que verifica que el contrato versionado de la API sigue coincidiendo con el código. Además, se ha comprobado que puede fallar cuando existe una diferencia, en lugar de asumir que funciona solo porque aparece en verde.

Los trabajos de integración continua ejecutan esa comprobación y activan el revisor automático cuando se propone un cambio.

Por último, queda un archivo de calibración que define qué se considera grave y cuántas sugerencias menores puede generar el agente, junto con el informe de la primera revisión automática y los problemas que detectó por sí solo.

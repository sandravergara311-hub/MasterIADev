Repositorio: Blog Legacy

Es la última lección del módulo y la que más se subestima. Leerla son diez minutos; hacerla, cerca de una hora. Todo lo que hay que traer al directo está aquí, y solo aquí.

Cuatro partes. La primera explica cómo funciona el módulo, y conviene leerla aunque tengas prisa. La segunda deja el entorno listo. La tercera es la tarea, que es la que lleva tiempo de verdad. La cuarta es cómo se entrega.

🔁 Cómo funciona este módulo
Hay tres momentos, y saberlos cambia cómo aprovechas cada uno.

1. Lo intentas tú. Sobre el proyecto de abajo, con tu agente, con el reloj puesto. Entregas lo que te salga, con lo que tenga. La entrega a medias no es un problema: este paso no se puntúa por completarlo.

2. Lo ves resuelto en el directo. El mentor ejecuta esta misma auditoría, sobre este mismo proyecto. Si no te salió, ahí ves que se puede y cómo. Por eso conviene mirar sin teclear: lo vas a repetir con calma después.

3. Lo replicas. Los prompts que use el mentor te llegan por escrito. Con ellos vuelves a tu entorno y rehaces el recorrido, que es donde se asienta.

⚠ En el paso 3 no esperes salidas idénticas, y no es un fallo tuyo. El agente no es determinista: con el mismo prompt y el mismo código cambian los nombres de las variables, la redacción y hasta cuántos hallazgos devuelve. Lo que se repite es la forma del recorrido, no el texto.

🛠 Deja el entorno listo
Todo lo necesario para levantar el proyecto está en esta sección, en orden. Esta lección y el README.md del repositorio cuentan lo mismo, así que con leer una de las dos basta.

1. Comprueba lo que necesita tu máquina
Dónde funciona. En macOS y en Linux, tal cual. En Windows, dentro de WSL (Windows Subsystem for Linux, el Linux que corre dentro de Windows), y no en PowerShell: los atajos del proyecto están escritos para la terminal de macOS y Linux (usan cp, test y rm), así que en PowerShell fallan aunque consigas instalar make.

🪟 Si trabajas en Windows, haz TODO lo de esta lección dentro de la terminal de Ubuntu de WSL: el clon, Node y make. Lo que tengas instalado en Windows no existe dentro de WSL, y al revés, así que un node -v que responde en PowerShell no dice nada sobre WSL. Si aún no tienes WSL, se instala con wsl --install desde PowerShell abierto como administrador, según la guía oficial de Microsoft.

Tres comprobaciones, en la terminal donde vas a trabajar:

Node.js 24 o superior. node -v tiene que responder v24 o más. Con la 20 el proyecto no arranca: make setup se para con Unknown file extension ".ts". Con la 22 arranca, pero te llena la pantalla de avisos EBADENGINE porque el proyecto pide la 24, así que no cuentes con ella. La versión marcada como LTS (long term support, la de soporte largo) en nodejs.org/en/download cumple.

make. make --version tiene que responder con un número. Si no responde: en macOS se instala con xcode-select --install; en Linux y en WSL con Ubuntu, con sudo apt install make.

git con acceso a GitHub, por SSH o por HTTPS, y Claude Code instalado y con sesión iniciada (claude --version responde).

2. Forkea y clona el proyecto
Es un blog pequeño con posts, autores, categorías, etiquetas y comentarios, en un monorepo con la API y la web dentro.

Forkea github.com/LIDR-academy-temp/blog-legacy-ai4devs-202609-1 con el botón Fork de arriba, y clona tu fork. Sobre un clon directo del repositorio del curso no tienes permiso de escritura, y aquí vas a crear una rama y commitear.

# 1. Clona TU fork
git clone git@github.com:<tu-usuario>/blog-legacy-ai4devs-202609-1.git
cd blog-legacy-ai4devs

# 2. Añade el repositorio del curso como "upstream"
git remote add upstream git@github.com:LIDR-academy-temp/blog-legacy-ai4devs-202609-1.git
git fetch upstream

# 3. Sitúate en la rama de partida, traída del curso
git checkout -b s6/start upstream/s6/start
📌 La rama de partida se trae del curso, no de tu fork, y no es un rodeo. Un fork es una foto del momento, y además el formulario de Fork de GitHub trae marcada la casilla de copiar solo la rama por defecto: si la dejas así, tu copia se lleva main y nada más. Trayéndola de upstream funciona en los dos casos, hayas marcado lo que hayas marcado. Si git checkout te responde error: pathspec … did not match, es que te saltaste el git remote add upstream de arriba.

📌 Si te sale Permission denied (publickey), es SSH y no el fork. Es el fallo más común de este paso y no tiene que ver con los permisos del repositorio. La guía oficial está en docs.github.com/es/authentication/connecting-to-github-with-ssh.

3. Instálalo y levántalo
Este proyecto no tiene package.json en la raíz: la API vive en backend/, la web en frontend/, y el Makefile de la raíz ya invoca los comandos de cada una por ti. Si escribes make a secas, te lista todos los atajos.

En una primera terminal, desde la raíz del proyecto y en este orden:

make setup    # instala las dependencias de la API y de la web, y prepara backend/.env
make db       # crea la base de datos SQLite y la siembra con los datos de ejemplo
make api      # levanta la API en <http://localhost:3401> y se queda corriendo
make api se queda ocupando la terminal, que es lo normal: no la cierres.

En una segunda terminal, también desde la raíz del proyecto:

make web      # levanta la web en <http://localhost:5401> y se queda corriendo
Comprueba las dos antes de seguir, porque la tarea de abajo las necesita vivas:

La API: curl -s localhost:3401/posts en una tercera terminal tiene que devolver una lista de posts en JSON.

La web: abre http://localhost:5401 en el navegador y entra en un post. Al final de la página están sus comentarios, que es la parte del blog que vas a auditar.

Los dos puertos son fijos: la web busca la API exactamente en el 3401, así que no sirve levantarla en otro.

🔧 Si algo falla, casi siempre es una de estas:

make: command not found: falta make, vuelve al paso 1.

Unknown file extension ".ts" durante make setup: tu Node es anterior a la 22. Instala la 24 y repite make setup.

make api o make web dicen que el puerto está en uso: tienes algo corriendo en el 3401 o en el 5401, casi siempre una ejecución anterior de este mismo proyecto. Ciérrala y vuelve a lanzar.

El curl no devuelve nada, o la web carga sin posts: falta make db, o se cerró la terminal de make api.

4. Corre la suite y anota lo que salga
make test
Apunta el resultado tal cual salga, incluido lo que esté en rojo. No lo arregles.

Ese apunte es tu punto de partida: la única forma honesta de saber si un cambio empeora algo es comparar contra lo que ya pasaba antes, no contra un ideal.

5. Comprueba que tu agente puede trabajar aquí
Abre tu sesión de Claude Code en el proyecto y pídele dos cosas: que te resuma los últimos commits, y que busque en qué archivos aparece una palabra cualquiera del dominio. Si no puede ejecutar git o no puede buscar por el proyecto, resuélvelo antes: sin eso no se audita nada.

6. Crea tu rama
git checkout -b auditoria-<tus-iniciales>
Ahí va todo lo que produzcas. El directorio docs/auditoria/ ya existe: ahí va el archivo de la tarea, y ahí se queda, porque una auditoría es un artefacto versionado y no una conversación.

📋 La tarea
Son unos 45 minutos y hay que ponerles un reloj. Léete entero el encuadre antes de empezar, porque el entregable no es el que parece.

El entregable no es la lista ordenada. Son las tres líneas de la parte B, y esas se escriben igual de bien con la lista a medias.

De hecho, si terminas con una lista ordenada y estás seguro del orden, vuelve a mirarla: casi nadie lo está en la primera pasada, y el motivo no es la herramienta.

El reloj tampoco es una crueldad de diseño. En una auditoría real tampoco te dan tiempo infinito: te dan la tarde que hay antes de la reunión. Lo que sale en 45 minutos es exactamente la parte que depende de tener criterio, y no la que depende de tener una herramienta mejor.

⚠ Ve guardando cada prompt tal cual lo lanzas, desde el primero. Se entregan junto con la tabla, y no valen reconstruidos: el prompt que arreglas mentalmente diez minutos después no es el que lanzaste, y es justo la diferencia que interesa mirar.

🅰 Parte A: la auditoría
Con un agente, produce la auditoría priorizada de la feature de comentarios y déjala escrita en docs/auditoria/comentarios.md, no en el chat.

Una feature es una funcionalidad del blog de punta a punta: sus rutas en la API, su tabla en la base de datos y lo que la web enseña de ella. Este blog tiene cinco (posts, comentarios, autores, categorías y etiquetas), y la tuya es comentarios: crear, editar, borrar y listar comentarios, en esas tres capas. Es la misma que audita el mentor en el directo.

Solo esa feature. No el sistema entero, aunque quepa y aunque el agente se ofrezca.

Y el orden, con el mismo criterio que usa el mentor: primero la precedencia (lo que abarata o desbloquea a otro hallazgo va antes), y dentro de cada nivel, el daño dividido por el radio. Si un hallazgo tiene el daño más alto y la precedencia más baja a la vez, se parte en dos filas, una contención que corta el daño hoy y el arreglo de fondo que espera su turno. Y las propuestas que nadie ha medido todavía van fuera de la tabla, con lo que habría que medir escrito al lado.

El formato no es negociable: una fila por hallazgo, con estas seis casillas.

Qué es. Una frase. Si necesitas tres, es que hay dos hallazgos.

Dónde está, con la línea que lo demuestra. Sin esta casilla, la fila no se escribe.

Qué se rompe, y quién lo nota. El efecto concreto y a quién le llega. "Nadie todavía" es una respuesta válida y buena.

Cuántos sitios hay que tocar. Contados, no estimados.

¿Se deshace con un revert? Sí o no, y si es que no, por qué no.

¿Bloquea o desbloquea a otro hallazgo? Nombrando al otro. "A ninguno" es la respuesta más frecuente.

⚠ Cuando suene el reloj, para. Aunque esté a medias. Aunque falten filas, aunque haya casillas en blanco, aunque justo estuvieras a punto de comprobar una cosa.

Una fila con tres casillas rellenas y tres en blanco es información: dice exactamente hasta dónde llegaste. Una fila completada de memoria diez minutos después es ruido con formato, y encima es indistinguible de la buena.

🅱 Parte B: las tres líneas
Debajo de la tabla, en el mismo archivo. Esta parte no se puede fallar, y es la que hay que traer sí o sí.

Cuántos hallazgos devolvió el agente, y cuántos comprobaste tú abriendo el archivo. Los dos números, tal cual salieron. No los redondees ni los expliques.

El hallazgo del que no supiste decidir la prioridad, y en una frase, por qué. Lo que interesa es qué dos cosas se contradecían: lo grave contra lo que bloquea, lo urgente contra lo caro, lo que te pedían contra lo que veías.

Algo que el agente afirmó y no pudiste verificar. Ojo al matiz: no es lo que dijo mal. Es lo que no pudiste comprobar ni a favor ni en contra, y te tocó dejar en el aire.

⚠ Ninguna de las tres tiene respuesta correcta. La segunda y la tercera son mejores cuanto más incómodas: un "no supe decidir entre estos dos" honesto vale más que una lista ordenada con seguridad fingida.

Cómo saber que la has hecho bien
Las tres líneas están escritas y son concretas. Si la tercera dice "nada, todo era verificable", vuelve a mirar: es la respuesta que da alguien que comprobó leyendo el hallazgo en vez de abriendo el archivo.

El número de comprobados es menor que el de devueltos. Casi siempre lo es, y eso no es un fallo tuyo: es el dato.

Hay al menos una casilla en blanco. Significa que respetaste el reloj y que no rellenaste de memoria.

La tabla cabe en una pantalla. Si no cabe, te saliste de comentarios y estás auditando el sistema entero otra vez.

📤 Cómo se entrega
Un pull request desde tu fork, con dos cosas dentro y ni una más:

Tu archivo de auditoría en docs/auditoria/, con la tabla y las tres líneas.

prompts.md, en la raíz del proyecto. Ya está ahí con la plantilla puesta.

git add docs/auditoria prompts.md
git commit -m "auditoria: comentarios + prompts"
git push -u origin auditoria-<tus-iniciales>
Con la rama empujada, GitHub te ofrece arriba el botón para abrir el pull request. Va contra el repositorio del curso, no contra tu fork.

🧠 prompts.md no es papeleo, y es la mitad de lo que se revisa. Lo que se mira no es solo lo que te salió, es cómo lo pediste: un resultado flojo con un prompt bueno y un resultado flojo con un prompt vago necesitan respuestas distintas, y sin ese archivo no se distinguen. Pega los prompts tal cual los lanzaste, con su modelo y su herramienta, e incluye también los que no funcionaron, que suelen ser los más útiles de leer.

El plazo
Antes del directo. Lo que llegue a tiempo recibe el feedback de tu TA antes de la sesión, que es el único momento en que te sirve: llegas sabiendo dónde fallaste y miras la sesión buscando eso. Lo que llegue después se marca como recibido, pero ya no se revisa.

Entrégalo con lo que tenga, y sin maquillarlo: lo que le falta es la mitad de lo interesante.

🚀 Y después, si quieres llevártelo al trabajo
Cuando hayas hecho el paso 3, repite el recorrido sobre un proyecto tuyo de verdad: uno del trabajo, que lleve años en marcha y que no escribieras tú entero. No hace falta que sea grande. Hace falta que sea un sistema sobre el que no puedas responder de memoria "si cambio esto, qué se rompe".

Eso es opcional y no se entrega, pero es donde esto deja de ser un ejercicio. Los prompts son los mismos.

🎯 Qué te llevas del Módulo 6
El modelo mental: heredado no es viejo, es lo que nadie puede explicar, y la medida útil no es un porcentaje de sector sino cuánto tardas en responder, con evidencia que otro pueda comprobar, qué se rompe si tocas algo; el cuello de una auditoría es comprobar, no encontrar, así que el presupuesto de verificación es el que manda y el tamaño de la lista es propiedad de cómo cortaste el trozo que auditas, no del sistema; lo más grave no va primero, porque ordenar por gravedad produce retrabajo, y cuando el daño y la precedencia se contradicen la salida es partir el hallazgo en contención y arreglo en vez de mover la fila; y un encargo de una línea no es vago, es uno cuyo contexto vive escrito en el arnés, que en un sistema heredado hay que escribir a mano porque el código dice de dónde viene y nunca hacia dónde va.

Lo que queda en el proyecto: un archivo de auditoría versionado de una sola feature, la de comentarios, con una lista corta comprobada una a una y una fila por hallazgo que trae dónde se demuestra, qué se rompe y quién lo nota, cuántos sitios hay que tocar, si lo deshace una vuelta atrás y a qué otro hallazgo bloquea; con las casillas que nadie pudo responder en blanco a propósito y las propuestas sin medir fuera de la tabla, con su experimento escrito al lado. Debajo, las tres líneas que dicen dónde se te acabó el tiempo, qué no supiste priorizar y qué no pudiste verificar. Y tests de caracterización que fijan el comportamiento de hoy, bugs incluidos, para poder cambiar algo sin descubrir por accidente qué dependía de ello.

👥 Qué te llevas según de dónde vengas.

Si eres dev: un agente encuentra y cuenta bien cuántos sitios toca cada hallazgo, pero quién usa eso y qué hay alrededor lo pones tú. Y antes de cambiar nada heredado, fija con pruebas lo que hace hoy, fallos incluidos.

Si vienes de producto o gestión: ahora te llega una lista de cuarenta cosas producida en cuatro minutos por algo que no sabe cuáles importan. Tu trabajo no es elegir las graves: es preguntar, en cada una, cuántos sitios hay que tocar a la vez y qué tiene que ir antes, que son las dos respuestas que deciden el calendario.

Si no tienes background técnico: heredado no significa viejo, significa que nadie lo puede explicar: una casa antigua cuyos planos se perdieron. Y lo más grave no siempre va primero.

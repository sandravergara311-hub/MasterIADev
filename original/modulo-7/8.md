🔁 Cómo funciona este módulo
El trabajo se divide en tres pasos:

1. Lo intentas tú. Trabaja con tu agente sobre los repositorios indicados más abajo. Entrega lo que consigas, tal como esté. No pasa nada si queda a medias: este paso no se puntúa por completarlo. La práctica está pensada para que encuentres dificultades, no para que todo te salga a la primera.

2. Lo ves resuelto en el directo. El mentor configura las mismas reglas y mecanismos de control sobre los mismos repositorios. Si no te salió, ahí verás cómo hacerlo. Conviene mirar sin teclear: después lo repetirás con calma.

⚠ Al repetir los pasos, no esperes resultados idénticos. No es un fallo tuyo. El agente no es determinista: con el mismo prompt y el mismo código pueden cambiar los nombres que elige, la redacción y cuántos resultados devuelve. Lo que debes repetir es el proceso, no el texto exacto.

1. Crea los tres forks y prepara sus carpetas
El proyecto es un blog dividido en tres repositorios independientes: uno busca por significado, otro proporciona los artículos a través de una API y otro los muestra en el navegador.

Crea un fork de cada repositorio con el botón Fork de su página en GitHub. Trabajarás sobre tus copias para poder crear ramas y subir tus commits:

blog-ai: https://github.com/LIDR-academy-temp/blog-ai-ai4devs-202609-1

blog-api: https://github.com/LIDR-academy-temp/blog-api-ai4devs-202609-1

blog-web: https://github.com/LIDR-academy-temp/blog-web-ai4devs-202609-1

🚨 Al crear cada fork, desmarca la casilla «Copy the main branch only» («Copiar solo la rama main»). Si la dejas marcada, copiarás únicamente main y no las demás ramas, incluida s7/start, que necesitas para este ejercicio.

🚨 Los tres proyectos deben quedar dentro de una misma carpeta, con estos nombres exactos: blog-ai, blog-api y blog-web. Como los repositorios llevan el sufijo -ai4devs, tendrás que indicar el nombre de destino al clonarlos, como muestran los comandos de abajo. El ejercicio depende de esta estructura; si algún nombre es incorrecto, make setup detectará el problema y se detendrá antes de instalar las dependencias.

Crea la carpeta que contendrá los tres proyectos y entra en ella:

mkdir blog && cd blog
Prepara los proyectos uno por uno y en el orden indicado, porque cada uno necesita el anterior. Cada make up mantiene el servicio en ejecución y ocupa su terminal. Deja esa terminal abierta y abre otra en la carpeta blog/ para preparar el siguiente proyecto. Al terminar tendrás tres terminales abiertas.

📌 Si aparece Permission denied (publickey), revisa la configuración de SSH. Ese mensaje indica un problema de autenticación con GitHub, no con la creación del fork. Sigue la guía oficial para conectar con GitHub mediante SSH.

2. Arranca blog-ai: los otros dos lo necesitan
Desde la carpeta blog/, ejecuta estos comandos. Sustituye <tu-usuario> por tu usuario de GitHub:

git clone git@github.com:<tu-usuario>/blog-ai-ai4devs-202609-1.git blog-ai
cd blog-ai
git remote add upstream git@github.com:LIDR-academy-temp/blog-ai-ai4devs-202609-1.git
git fetch upstream
git checkout -b s7/start upstream/s7/start
make setup
make up
make setup solo se ejecuta la primera vez y es el paso que más tarda: descarga los dos modelos locales, que suman algo más de 2 GB, y arranca una base de datos en un contenedor. Hazlo con tiempo; no lo dejes para el día anterior. Después bastará con make up, que arranca el servicio en el puerto 8402 y mantiene ocupada esa terminal.

Comprueba el servicio desde otra terminal:

curl -s localhost:8402/salud

La respuesta debe incluir "ollama_alcanzable": true. Revisa ese campo: estado puede devolver "ok" aunque Ollama no esté disponible.

💡 Si tienes poca memoria disponible, activa el modo ligero. Al usar el modelo pequeño para redactar las respuestas, los dos modelos consumen 1,8 GB en vez de 2,8 GB. Antes de ejecutar make setup, descarga el modelo:

ollama pull qwen2.5:1.5b-instruct
En el archivo .env de blog-ai, configura el modelo de generación así:

MODELO_GENERACION=qwen2.5:1.5b-instruct
Qué cambia, según las mediciones: el modelo pequeño responde más del doble de rápido. Tarda alrededor de un segundo en generar una respuesta, mientras que el predeterminado tarda algo más de dos segundos. Redacta igual de bien, pero cita con menos precisión los artículos de los que extrae la información. Esto no afecta al objetivo del ejercicio: comprobar qué reglas se cumplen y cuáles no.

cd blog-api

El servicio arranca en el puerto 3402. Compruébalo desde otra terminal:

curl -s localhost:3402/saludcurl -s 'localhost:3402/posts?por_pagina=3'

La primera respuesta debe indicar que blog_ai está alcanzable; la segunda debe devolver tres artículos. Si blog_ai no está disponible, comprueba que el servicio del apartado anterior siga en ejecución.

4. Arranca blog-web: muestra el blog en el navegador
Abre una terminal nueva, deja la anterior abierta y vuelve a la carpeta blog/:

git clone git@github.com:<tu-usuario>/blog-web-ai4devs-202609-1.git blog-web
cd blog-web
git remote add upstream git@github.com:LIDR-academy-temp/blog-web-ai4devs-202609-1.git
git fetch upstream
git checkout -b s7/start upstream/s7/start

La web arranca en el puerto 5402. Abre localhost:5402 en el navegador: debes ver el blog con sus artículos. Es normal que la búsqueda todavía no devuelva resultados; la prepararás en el siguiente apartado.

Comprueba también las carpetas. Al ejecutar ls desde blog/, deben aparecer blog-ai, blog-api y blog-web, las tres al mismo nivel.

📌 Qué es s7/start y por qué la traemos del repositorio del curso. Es la rama con el punto de partida de este módulo en los tres repositorios. git fetch upstream la descarga del repositorio del curso y git checkout crea tu rama local a partir de ella. Así puedes obtenerla aunque tu fork solo incluya main. Sitúate en s7/start en los tres proyectos, aunque solo vayas a hacer commits en uno: todos deben partir del estado previsto para el ejercicio.

💡 Si algo no arranca, ejecuta make check antes de investigar. Está disponible en los tres proyectos y no modifica nada. Comprueba los requisitos e indica qué falta y cómo resolverlo. En blog-ai revisa el nombre de la carpeta, la versión de Python, que el motor de contenedores esté en ejecución y que Ollama responda. Empieza por ahí: los errores que aparecen al arrancar no siempre dejan clara la causa.

⚠ make setup resuelve dos problemas que conviene conocer si preparas el proyecto a mano. En blog-api, la migración necesita una carpeta tmp/ que Git ignora y no se incluye al clonar. Si falta, aparece cannot open database because the directory does not exist, sin indicar qué carpeta necesitas crear. En blog-ai, usar una versión antigua de Python puede hacer que la instalación de dependencias falle con un error sobre el conector de PostgreSQL, sin mencionar la versión de Python. En ambos casos, el mensaje puede llevarte a buscar el problema en el sitio equivocado.

5. Prepara el índice de búsqueda
Con los tres servicios en ejecución, indexa los artículos una vez para que aparezcan en las búsquedas:

curl -s -X POST localhost:3402/indexar

La respuesta indica cuántos artículos se han indexado y en cuántos fragmentos se han dividido. Si devuelve cero, comprueba que los servicios estén funcionando. Sin artículos en el índice, la búsqueda devolverá una lista vacía y no podrás observar cómo colaboran los repositorios.

6. Comprueba que tu agente funciona desde los dos repositorios de la práctica
Inicia una sesión de Claude Code desde la carpeta blog-api y otra desde blog-ai. En cada una, pídele algo sencillo, como resumir el proyecto. Confirma que responde y puede ejecutar comandos.

La carpeta desde la que inicias la sesión es una parte central de este módulo. Compruébalo ahora para que durante el directo puedas hacerlo sin detenerte a resolver problemas.

7. Localiza tres cosas en cada repositorio
Revisa blog-api y blog-ai sin cambiar nada. Solo necesitas localizar:

El archivo de instrucciones del agente, si existe. Suele llamarse CLAUDE.md o AGENTS.md y estar en la raíz.

Las comprobaciones automáticas que se ejecutan al editar archivos o integrar cambios, si las hay.

Los atajos del equipo, si los hay.

Si alguno de los repositorios no tiene estos elementos, también es una respuesta válida: no tienes que añadirlos. Lo que necesitas es saber explicar qué hay y qué falta.

Esta parte no introduce conceptos nuevos. Harás una práctica pequeña para observar qué ocurre al aplicar las reglas: algunas dificultades solo se entienden al encontrarlas.

Trabajarás sobre blog-api y blog-ai, los dos repositorios que acabas de comprobar. blog-web no entra en la práctica, pero déjalo en ejecución porque forma parte del sistema.

🅰 Parte A: crea una regla en la carpeta que contiene los proyectos y configura instrucciones, un hook y una skill en cada repositorio
Es la misma práctica que hará el mentor en el directo, con las mismas reglas y la misma tarea. Los prompts los escribirás tú.

1. Crea una regla fuera de todos los repositorios. Desde blog/, la carpeta que contiene los tres proyectos, ejecuta este comando. Creará el único archivo de la práctica que va fuera de un repositorio:

cat > CLAUDE.md <<'FIN'
# Reglas de este espacio de trabajo

## REGLA-PADRE

Este archivo no vive dentro de ningún repositorio: está en la carpeta que los contiene.

Por eso, **toda respuesta que des aquí termina con esta línea, sola y literal**:

REGLA-PADRE aplicada: gobierno desde fuera de todos los repositorios.
FIN
2. Prepara tres piezas en cada repositorio: blog-api y blog-ai. Con la sesión del agente iniciada en blog-api, pídele que cree lo siguiente en ambos repositorios, sin cambiar nada más:

Un CLAUDE.md en la raíz con una sola regla propia del repositorio. En blog-api: este repositorio es el dueño del contenido y todo archivo nuevo debe empezar con un comentario que lo indique. En blog-ai: los nombres de los campos del contrato público deben escribirse en español, nunca en inglés. Las reglas son distintas para poder reconocer después cuál se aplicó.

Un hook que se ejecute al escribir o editar un archivo, mediante PostToolUse para las herramientas Write y Edit. Debe añadir una línea a MARCADORES-<nombre-del-repo>.txt, en la raíz de su propio repositorio, con la fecha, la herramienta utilizada y la ruta del archivo modificado. Pide que use rutas absolutas: el hook tendrá que registrar cambios en archivos situados fuera de su repositorio.

Una skill sencilla llamada marcador-<nombre-del-repo>, cuya descripción indique a qué repositorio pertenece.

3. Inicia una sesión nueva desde blog-api, con blog-ai añadido. Cierra la anterior y vuelve a iniciarla para cargar los guardarraíles que acabas de crear. No uses el modo de aceptación automática: el agente puede editar mediante scripts de shell, y el hook de esta práctica solo registra las herramientas Write y Edit.

claude --add-dir ../blog-ai
4. Un encargo en el repositorio añadido y tres preguntas. Pídele que añada a la clase ResultadoBusqueda, en ../blog-ai/app/esquemas.py, un campo que indique cuántos fragmentos del artículo han coincidido con la búsqueda. Indica que debe modificar solo ese archivo y utilizar la herramienta de edición de archivos, nunca un script.

Al terminar, pídele que responda por separado:

Qué archivos CLAUDE.md se cargaron al iniciar la sesión, citando la regla de cada uno.

Qué skills tiene disponibles.

Qué nombre ha dado al campo y por qué.

5. Comprueba los dos archivos de marcadores. Desde blog/, lee ambos, no solo aquel donde esperas encontrar el registro:

cat blog-api/MARCADORES-blog-api.txt
cat blog-ai/MARCADORES-blog-ai.txt
Compara su contenido con lo que dijo el agente en el paso 4. Después, deshaz el cambio del campo ejecutando git checkout -- app/esquemas.py dentro de blog-ai y borra el CLAUDE.md de blog/ para que sus instrucciones no sigan aplicándose a los proyectos de esa carpeta.

🅱 Parte B: las dos frases
Escribe dos frases, una por punto:

Qué dijo el agente en el paso 4: qué archivos CLAUDE.md dijo haber cargado, qué skills tenía disponibles y qué nombre dio al campo.

Qué encontraste en cada archivo de marcadores y qué indica sobre dónde se ejecuta cada guardarraíl.

La segunda es la clave. Debe basarse en haber revisado los dos archivos, no solo el que esperabas. Algunos fallos no muestran avisos: necesitas comprobar los registros para detectarlos.

⚠ Lo que se pide es que anotes lo observado. No necesitas dejarlo funcionando, completar todos los pasos ni encontrar una solución. Si te quedas a medias, indica dónde y qué viste. Esa observación también es válida.

Cómo saber que la has hecho bien
📌 Has revisado los dos archivos de marcadores, no solo el de blog-api, y puedes explicar qué contiene cada uno o indicar si no existe. También has comparado lo que el agente dijo tener cargado con lo que los archivos registran que se ejecutó. Son dos cosas distintas; reconocer esa diferencia es el objetivo de la práctica.

📌 Dedica entre veinte y cuarenta y cinco minutos. Si necesitas más tiempo, para y anota hasta dónde llegaste y qué observaste. Lo que hayas observado hasta ese momento también sirve para la entrega.

Por qué está planteado así
Una configuración puede funcionar al principio y dejar de hacerlo sin avisar. Leer una advertencia no permite ver dónde ocurre; esta práctica busca que lo compruebes.

No se trata de adivinar una solución ni de escribir el comando correcto. La protección que ofrece un guardarraíl depende de dónde está configurado y desde dónde se ejecuta. Lo que interesa es que observes dónde deja de aplicarse y puedas relacionarlo con la explicación del directo.

Avanzas descubriendo cómo funciona el mecanismo, aunque no consigas resolverlo durante la práctica.

📤 Cómo se entrega
Abre un pull request desde tu fork de blog-api-ai4devs, usando la rama creada en el paso 8. Incluye solo estos dos archivos:

prompts.md, en la raíz del proyecto. Ya incluye la plantilla que debes completar.

Después de escribir ambos archivos, ejecuta:

mkdir -p docs
git add docs/frontera.md prompts.md
git commit -m "frontera: dos frases + prompts"
git push -u origin frontera-<tus-iniciales>
Sustituye <tus-iniciales> por las que usaste al crear la rama. Después de subirla, GitHub te mostrará un botón para abrir el pull request. El pull request va contra el repositorio del curso, no contra tu fork.

🧠 prompts.md es la mitad de lo que se revisa. Importa tanto el resultado como la forma en que lo pediste. Un resultado que no funciona puede venir de un prompt preciso o de uno ambiguo; cada caso necesita un feedback distinto. Pega los prompts tal como los enviaste, indica el modelo y la herramienta utilizados e incluye los que no funcionaron.

🎯 Qué te llevas del Módulo 7
El modelo mental:

Separar repositorios es hacer una predicción sobre qué cambios serán independientes. Deja esa decisión escrita junto al límite entre ambos para poder contrastarla después con el historial.

La carpeta desde la que arrancas el agente condiciona qué instrucciones y mecanismos se cargan. Que pueda acceder a otro repositorio no significa que se apliquen sus guardarraíles. Un resultado correcto aislado no demuestra que exista una garantía.

La documentación debe estar donde pueda actualizarse en el mismo cambio propuesto que el código que describe. Puedes centralizar su consulta, pero la fuente se mantiene junto al código.

Un cambio que cruza dos repositorios pierde la atomicidad: ya no puedes aplicarlo todo de una vez. Necesitas una ventana de compatibilidad documentada, añadir antes de quitar y fijar la fecha de cierre desde el principio.

Compartir no es copiar. Comparte las herramientas y configuraciones comunes con una versión identificable. Escribe las reglas de negocio de cada repositorio donde se aplican, aunque algunas se repitan.

Lo que queda en el proyecto:

El alcance real de los guardarraíles, comprobado y mostrado en el directo: qué instrucciones se cargaron, qué hooks se ejecutaron y sobre qué archivos, con registros que puedes volver a consultar.

Una deriva del contrato reproducida y revertida, en sus dos formas: la que falla e indica dónde está el problema y la que sigue respondiendo sin mostrar un fallo evidente.

Un plan escrito para la ventana de compatibilidad, con los pasos en orden, los estados intermedios, la comprobación que permite cerrarla y la fecha de cierre.

Tus dos frases, con lo que dijo el agente y lo que encontraste en los marcadores.

👥 Qué te llevas según tu experiencia.

Si eres dev: revisa un trimestre de tu historial y cuenta cuántos cambios necesitaron tocar dos repositorios para quedar completos. Comprueba también qué reglas carga tu agente desde la carpeta donde lo arrancas: que una regla se cumpla una vez no garantiza que vuelva a hacerlo.

Si vienes de producto o gestión: pregunta cuántas peticiones recientes han necesitado cambios en ambos repositorios. Eso ayuda a entender por qué algunas funcionalidades requieren más coordinación. Si un cambio cruza ese límite, necesita un periodo de convivencia entre versiones y una fecha de cierre definida desde el inicio.

Si no tienes experiencia técnica: dividir un sistema supone que sus partes podrán cambiar por separado. Puedes comprobar si esa decisión funciona mirando los cambios anteriores. Compartir con versiones permite saber qué usa cada proyecto y cuál necesita actualizarse; copiar archivos no ofrece ese seguimiento.

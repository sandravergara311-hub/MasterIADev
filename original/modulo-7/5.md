Un cambio que cruza dos repositorios no es un cambio 🔴 — 11 min
Antonio Perez
⏱ Lectura ~11 min · 🔴 Obligatoria. Léela antes del directo.

El servicio de contenidos de un blog devuelve los posts con un campo autor que contiene el nombre como una cadena de texto. El buscador, que está en otro repositorio, consume ese campo y lo guarda para mostrarlo en los resultados.

Ahora se necesita enlazar a la página del autor, así que se decide convertir autor en un objeto con nombre y slug.

Cada repositorio tiene su propio ciclo de publicación. Integrar uno de los cambios no garantiza que el otro también se haya integrado o desplegado.

Esa falta de una actualización conjunta es el problema central de la lección: cómo cambiar el formato del dato sin interrumpir el funcionamiento del sistema.

Lo primero que se pierde es la garantía de cambiar «a la vez»
En un solo repositorio, un PR permite integrar juntas las modificaciones del servicio que proporciona los datos y del que los utiliza. La integración es conjunta, aunque eso no garantiza que ambos servicios se desplieguen al mismo tiempo.

Con dos repositorios, los cambios se integran por separado: aceptar el PR del servicio de contenidos no integra también el del buscador. Los despliegues también son independientes. Si el servicio de contenidos empieza a devolver autor como un objeto mientras el buscador todavía espera una cadena de texto, este puede dejar de procesar los datos correctamente.

Para evitarlo, se establece una ventana de compatibilidad. Por ejemplo, primero se actualiza el buscador para que pueda interpretar tanto la cadena de texto como el objeto. Después, el servicio de contenidos empieza a devolver el nuevo formato. Cuando se comprueba que los datos almacenados y los servicios que los consumen ya utilizan el objeto, se retira el soporte para la cadena de texto.

Así, cada servicio puede actualizarse por separado sin romper el contrato durante la transición. La ventana debe tener un inicio y un criterio de cierre para que el soporte del formato anterior no se mantenga indefinidamente.

📖 Glosario exprés

Productor y consumidor: el productor proporciona el dato y el consumidor lo utiliza. En este ejemplo, el servicio de contenidos es el productor y el buscador, el consumidor.

Publicación o release: puesta a disposición de una nueva versión. Cada servicio del ejemplo tiene su propio ciclo de publicación.

Ventana de compatibilidad: periodo durante el cual se mantiene la compatibilidad con el formato anterior mientras se adopta el nuevo. Puede requerir que el productor ofrezca ambos formatos o que el consumidor sepa interpretar los dos, según el orden de actualización.

Cambio incompatible o breaking change: modificación que rompe el funcionamiento de un consumidor existente si este no se adapta. Sustituir una cadena de texto por un objeto en el mismo campo puede provocar ese fallo.

Añadir el objeto autor antes de retirar el campo de texto
Los pasos no son técnicamente difíciles. La dificultad está en seguir el orden correcto: ofrecer el nuevo formato de autor sin retirar el anterior hasta que todos los consumidores hayan migrado, aunque mantener ambos temporalmente vaya en contra del impulso de dejar el código limpio.

Presta atención a la tercera columna, qué es cierto del sistema en cada momento. Durante el primer paso, el sistema ofrece dos formatos del mismo dato. Durante el tercero, sigue ofreciendo uno que los consumidores ya han dejado de usar. Ambos estados son correctos, transitorios y deliberados. Hay que documentarlos para que quien los encuentre entienda que forman parte de la migración y no los confunda con un fallo.

El paso que suele faltar en los planes es el cuarto: comprobar con evidencia que ningún consumidor utiliza ya el formato anterior. Que el buscador haya migrado no basta para retirarlo: otros servicios o aplicaciones pueden seguir dependiendo del campo de texto, incluidos consumidores que el equipo haya perdido de vista con los años.

Retirar el formato anterior también hay que planificarlo
El último paso puede romper producción si todavía queda algún consumidor que depende del formato anterior. Pero también suele aplazarse, porque retirar lo viejo no añade ninguna funcionalidad.

Los cuatro primeros pasos tienen una necesidad inmediata: permiten completar el cambio. El quinto puede esperar porque el sistema sigue funcionando sin él. Así, una ventana de compatibilidad prevista para dos semanas puede acabar abierta durante dos años.

Mantenerla tiene un coste. Hay que seguir ofreciendo el formato anterior, probarlo y explicar por qué sigue ahí. Si se acumulan varias migraciones sin cerrar, un servicio puede terminar manteniendo tres versiones de un campo. Después, nadie se atreve a retirar ninguna porque no está claro quién utiliza cada una.

Para evitarlo, define la fecha de cierre al abrir la ventana, junto con la evidencia necesaria para retirar el formato anterior. Si esa evidencia no llega, revisa el plazo antes de eliminarlo.

💡 Por qué la ventana necesita un plan de cambio

Las specs del productor y del consumidor describen el comportamiento esperado al terminar la migración: uno ofrece el nuevo campo y el otro lo utiliza. Pero esos estados finales no explican por sí solos cómo pasar de la versión actual a la nueva sin romper la compatibilidad.

Durante la transición hay estados intermedios deliberados: se ofrecen ambos formatos, algunos consumidores ya han migrado y otros todavía no. Esa convivencia también debe quedar documentada.

El plan del cambio recoge qué formato se ofrece en cada paso, en qué orden se actualizan los servicios, cuándo se retirará el anterior y qué evidencia permite hacerlo. Las specs describen el resultado; el plan explica cómo llegar a él.

La frecuencia de estas migraciones ayuda a evaluar el acoplamiento
Este procedimiento exige cinco pasos, cambios en dos repositorios, coordinación y seguimiento de una fecha de cierre. Para una migración ocasional, ese coste puede compensar las ventajas de desplegar cada servicio por separado.

La frecuencia ayuda a detectar cuándo conviene revisar la separación:

Si necesitas coordinar una migración así cada semana, revisa el acoplamiento entre los servicios y si la separación entre repositorios sigue siendo adecuada.

Si cada cambio en el servicio de contenidos exige modificar también el buscador y coordinar ambos despliegues, los dos servicios apenas pueden evolucionar por separado. El equipo mantiene dos repositorios y dos ciclos de publicación, pero sigue necesitando trabajar sobre ambos para completar cada cambio. En ese caso, conviene revisar cómo se reparten las responsabilidades y el contrato entre los servicios, para entender por qué necesitan cambiar juntos con tanta frecuencia.

Qué te llevas de esta lección
No cuentes con una integración atómica entre dos repositorios. Planifica una ventana de compatibilidad para que los servicios puedan actualizarse por separado.

Ofrece el nuevo formato antes de retirar el anterior. Mantener ambos temporalmente permite migrar a los consumidores sin interrumpir su funcionamiento.

Documenta la ventana en el plan del cambio. Indica qué formato se ofrece en cada paso, hasta cuándo y qué evidencia permite retirar el anterior. Las specs del estado final no describen por sí solas esa transición.

Define la fecha de cierre al abrir la ventana. Si no se cumplen las condiciones para cerrarla, revisa el plazo; no retires el formato anterior sin comprobar su uso.

Usa la frecuencia de estas migraciones para evaluar el acoplamiento. Los cambios coordinados ocasionales son esperables; si se repiten cada semana, revisa las responsabilidades y el contrato entre los servicios.

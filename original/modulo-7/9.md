Para saber qué gobierna al agente y qué no
📖 How Claude remembers your project (Cómo recuerda Claude tu proyecto), documentación oficial de Anthropic. Explica cómo se descubren los archivos de instrucciones. Dos apartados son especialmente relevantes: la carga al inicio de los archivos CLAUDE.md y CLAUDE.local.md situados en la jerarquía superior al directorio de trabajo, y el comportamiento de los directorios adicionales. Sobre estos últimos, indica: «By default, CLAUDE.md files from these directories are not loaded». También documenta la variable CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD para activar su carga. Revisa cómo se configura: establecerla en tu máquina no hace que tus compañeros la reciban al clonar el proyecto. code.claude.com

Esta documentación puede cambiar entre versiones. La pregunta con la que conviene leerla sigue siendo la misma: ¿qué se carga, desde dónde y qué queda fuera?

Para la documentación compartida entre repositorios
📦 Fission-AI/OpenSpec, repositorio de la herramienta, con licencia MIT. Su propuesta de almacenes permite mantener la planificación en un repositorio independiente: «planning in a repo of its own». Conserva la estructura openspec/, con specs y cambios, y comparte el contenido mediante Git. Al utilizarlo, distingue entre los documentos compartidos y la configuración local que conecta cada proyecto con el almacén: publicar unos no demuestra que hayas compartido la otra. github.com

📖 TechDocs, documentación de Backstage. Muestra cómo centralizar la consulta sin mover los documentos originales: «Engineers write their documentation in Markdown files which live together with their code». La documentación permanece junto al código y se publica en un portal común. Sirve para entender este enfoque aunque no vayas a instalar Backstage. backstage.io

📖 Git Tools: Submodules (Herramientas de Git: submódulos), capítulo del libro Pro Git. Empieza aquí si necesitas incorporar un repositorio dentro de otro. La idea clave es esta: «Git sees it as a particular commit from that repository». El repositorio principal registra un commit concreto del submódulo; no incorpora automáticamente los últimos cambios de una rama. Entenderlo evita diferencias inesperadas entre las versiones que utiliza cada integrante del equipo. git-scm.com

Para los cambios que afectan a dos repositorios
📄 Parallel Change (Cambio en paralelo), de Danilo Sato. Describe cómo introducir cambios incompatibles en una interfaz mediante tres fases: expandir, migrar y contraer. En el original: "a pattern to implement backward-incompatible changes to an interface in a safe manner, by breaking the change into three distinct phases: expand, migrate, and contract". Primero se añade la nueva interfaz sin retirar la anterior, después se migran los consumidores y finalmente se elimina la antigua. Es el patrón en el que se apoya la ventana de compatibilidad de esta lección. martinfowler.com

📖 Versionado semántico, especificación en español. Define cómo comunicar el alcance de un cambio mediante el número de versión. Su resumen establece: «La versión MAYOR cuando realizas un cambio incompatible en el API». Esta convención permite que el consumidor identifique una actualización incompatible, siempre que el productor la aplique correctamente. semver.org

💡 Un ejercicio breve para aplicar lo leído

Elige un sistema tuyo repartido entre varios repositorios y revisa los cambios de los últimos tres meses. Clasifica cada cambio según si se completó en un solo repositorio o necesitó modificaciones en otro para completarse.

Una primera revisión de treinta cambios puede darte una señal inicial. Para calcular una proporción representativa del trimestre, revisa todos los cambios del periodo con el mismo criterio.

Si los cambios conjuntos son una minoría, el historial respalda la independencia entre las partes. Si se acercan a la mitad, conviene revisar qué dependencias los provocan y cuánto cuesta coordinarlos. El porcentaje no decide por sí solo, pero aporta evidencia para evaluar una decisión anterior en lugar de defenderla por costumbre.

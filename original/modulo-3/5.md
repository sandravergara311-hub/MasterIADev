Aquí está el criterio para no usar OpenSpec, que es la mitad que evita salir de este módulo aplicándolo a todo.

Tener un change de OpenSpec no garantiza que el agente lo respete: hay que asegurarse de que lee y sigue la spec en vez de improvisar. Aquí ves cómo conectar specs y agente durante la implementación, el criterio para no usar OpenSpec, y la capa que LIDR monta encima.

📖 Glosario exprés. Cinco términos que esta lección da por sabidos, en una línea cada uno:

TDD red/green: escribir primero un test que falla (rojo) y después el código mínimo que lo hace pasar (verde). El test define el objetivo antes de que exista la solución.

Spike: un trabajo corto de exploración cuyo objetivo es responder una pregunta ("¿esto es viable con esta librería?"), no dejar código que se quede.

Pull request (PR): la propuesta de integrar un conjunto de cambios, que otra persona revisa antes de que entren. Es el sitio clásico donde se discute un cambio, y por eso importa tanto discutirlo antes.

Invariante: una condición que tiene que cumplirse siempre, sin excepciones y sin criterio de por medio. "Nunca se sube una credencial al repositorio" es una invariante.

Gobernanza: las reglas de quién decide qué y cómo se controla. Aplicada aquí a tu configuración: quién puede cambiarla, cómo se revisa, y qué pasa contigo cuando la herramienta de debajo cambia.

Tres patrones para que el agente respete la spec
De menos a más control:

Patrón A · Referencia explícita en el primer turno (el más usado)
Implementa el change openspec/changes/add-task-due-date/.
Lee primero proposal.md, specs/*.md, design.md y tasks.md.
Sigue tasks.md paso a paso. Pregúntame antes de desviarte
de cualquier requisito de specs/.
Pros: cero setup, funciona en cualquier herramienta. Contras: tienes que acordarte de la coletilla; si abres sesión nueva y se te olvida, el agente puede improvisar. (Con el perfil core, /opsx:apply ya hace esto por ti: el patrón A es útil cuando trabajas el change "a mano".)

Patrón B · Skill SDD-aware
Lo conviertes en una skill: un archivo de instrucciones versionado en el repo que el agente carga cuando la tarea encaja, p. ej. .claude/skills/openspec-implement/SKILL.md. Instruye: leer los 4 archivos en orden, implementar tarea por tarea marcando la checklist, detenerse y preguntar ante cualquier desviación de specs/, y correr los tests al final. Pros: workflow explícito, repetible, auditable. Contras: hay que mantener la skill cuando OpenSpec evoluciona.

📌 Qué parte de openspec/ es de solo lectura. proposal.md, design.md y specs/ son input: el agente los lee y no los toca. tasks.md es la excepción, y es la que hace que el change sirva de checklist viva: conforme avanza, el propio agente cambia - [ ] por - [x]. No es una licencia general para reescribir el change, es el único archivo donde escribir forma parte del trabajo.

Patrón C · Skill + hook validador (el más estricto)
Añades un hook Stop que valida que lo implementado coincide con la spec (corre los tests derivados de los scenarios; si fallan, el agente recibe el error y entra en loop de reparación). Pros: el ciclo se cierra solo, el agente no cierra el turno con los tests en rojo sin que tú te enteres. Contras: requiere infra de validación, y el bloqueo no es infinito: Claude Code ignora el hook y cierra el turno tras 8 bloqueos consecutivos, precisamente para que un check mal escrito no deje al agente girando en vacío. Es un tope de seguridad, no un fallo, pero significa que un hook que nunca puede pasar acaba cediendo. Para flujos productivos.

💡 Recomendación: empieza con A (o directamente /opsx:apply). Cuando notes que copias la misma coletilla tres veces, salta a B. C llega cuando el proyecto ya tiene su validación automatizada y quieres que el agente entre en ella.

🔗 Dónde encaja /opsx:verify en esta escala. Cae entre B y C, y es importante no confundirlo con C: verify es la IA releyendo tu código y opinando, así que puede callarse. El hook de C ejecuta los tests y falla. Misma intención, garantía distinta: uno interpreta, el otro se ejecuta. Si te importa de verdad que algo se cumpla, necesitas C aunque tengas verify activado. (Ojo: verify no viene en el perfil core. Ese perfil instala seis comandos: propose, explore, apply, update, sync y archive. Para tener verify hay que ampliar el perfil con openspec config.)

Patrón complementario · README-driven development
El término lo acuñó Tom Preston-Werner (cofundador de GitHub) en 2010, y sigue vivo en el agentic coding: Simon Willison construyó así una herramienta entera, escribiendo primero el README con detalle y volcándoselo después a Claude Code para que la implementara con TDD red/green. La receta es esa: escribe el README/spec antes de pedir la implementación, con todo el detalle que puedas (incluidos edge cases), y luego pide implementar con TDD red/green a partir de él. Es SDD informal, aplicable a cualquier scope (un script de 50 líneas, no solo un change formal). Útil justo cuando OpenSpec es overkill.

Cuándo NO usar OpenSpec (anti-dogma)
Esto es lo que evita que salgas creyendo "OpenSpec siempre". No lo uses para:

Cambios acotados (añadir un filtro por estado a un listado que ya existe, ajustar un valor por defecto, meter un log) → delegación directa.

Bug fixes donde el cambio es obvio.

Spikes / prototipos desechables → si vas a tirar el código, escribir su spec es desperdicio. La regla práctica: prototipos, scripts de un solo uso y spikes de menos de dos horas no pagan una spec.

El coste de un change de OpenSpec (setup + minutos de propose/revisión/archive) solo se paga cuando el cambio perdura, toca varias capas o necesita trazabilidad. Para lo demás, delegación directa o README-driven. Saber elegir es la habilidad; usar OpenSpec no lo es.

Tu workflow es portable (gobernanza)
Una lección de gobernanza que conviene interiorizar: las herramientas cambian (planes, pricing, releases con bugs), pero lo que tienes versionado en tu repo es tuyo y se mueve contigo:

AGENTS.md/CLAUDE.md, .claude/skills/, .claude/agents/, hooks, y openspec/.

Trata esos archivos como código: van en PR, se revisan (los hooks siempre: ejecutan código en las máquinas del equipo).

Los comandos /opsx:* que OpenSpec genera también son archivos del repo (.claude/commands/, .claude/skills/): se clonan con él, así que tu compañero los tiene sin instalar nada. Lo único que se queda en tu máquina es la configuración global, que solo decide el perfil por defecto de los proyectos nuevos.

Distinción clave: lo que vive en AGENTS.md es interpretado por el modelo; lo que vive en un hook es ejecutado por código. Para invariantes de seguridad/compliance, siempre hooks.

💡 Tu seguridad no está en el plan que pagas, está en que tu workflow sea portable. Un openspec/ versionado y un harness en .claude/ valen más que cualquier prompt cuando la herramienta tiene un mal día.

lidr-specboot: la capa de LIDR sobre OpenSpec
La propia academia mantiene lidr-specboot, una capa de convenciones construida sobre OpenSpec. Lo que conviene saber:

El paso verificado es /enrich-us (enriquecer historias): confirma que LIDR pone una capa de "historias primero" encima de OpenSpec.

Por encima, specboot orquesta el resto del flujo (enriquecer → proponer → aplicar → verificar → revisar → archivar → commitear), apoyándose por debajo en los comandos reales de OpenSpec (/opsx:propose, /opsx:apply, /opsx:archive).

Entre el apply y el archive, specboot mete pasos propios de verificación y revisión adversarial: no da la implementación por buena solo porque las tareas estén marcadas.

📌 No te preocupes por specboot ahora. Solo has de saber que existe y que es OpenSpec por debajo.

❓ Preguntas que quizá te estás haciendo

"Si esta herramienta desaparece mañana, ¿qué me queda?" Conviene separarlo, porque no todo sobrevive igual. Sobrevive lo que es texto plano versionado en tu repositorio (las specs, las instrucciones, las skills, los hooks) y sobre todo el vocabulario: escribir el contrato antes que el código no es propiedad de nadie. No sobrevive la configuración global de tu máquina ni la memoria muscular de unos comandos concretos. La atadura de verdad nunca es la herramienta: es un flujo que solo existe en la cabeza de una persona.

"Si el patrón C es el único que garantiza algo, ¿por qué no empezar directamente ahí?" Porque un validador se escribe contra criterios que todavía no tienes: hasta que no has hecho el ciclo a mano un par de veces, no sabes qué querías comprobar, y acabas con un check que falla por motivos que no entiendes. La escala A → B → C no mide tu nivel: cada escalón se paga cuando el anterior empieza a doler, y antes de eso es coste sin contrapartida.

"Si escribo el README antes, ¿no es la misma burocracia con otro nombre?" No, y la diferencia es el destinatario. Un change formal produce artefactos que se archivan, se auditan y le sirven a alguien dentro de seis meses. Un README escrito antes solo tiene que servirle a quien implementa a continuación, que puede ser un agente o puedes ser tú dentro de una hora. Se borra sin ceremonia y no deja rastro que mantener: es spec-first sin contabilidad.

Lo accionable de esta lección
Asegura que el agente lea la spec: patrón A (o /opsx:apply) para empezar; skill (B) cuando se repita; hook validador (C) para producción.

README-driven cuando OpenSpec es overkill pero quieres spec-first informal.

No uses OpenSpec para lo acotado/desechable: ese es el criterio que te llevas.

Tu workflow es portable: openspec/ + .claude/ versionados son tuyos; los hooks se revisan siempre.

lidr-specboot = OpenSpec + orquestación: añade verificación y revisión entre el apply y el archive.
